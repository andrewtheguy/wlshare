# 架構

[English](architecture.md) | [简体中文](architecture.zh-CN.md) | 繁體中文

wlshare 透過以 wlroots 為基礎的 Wayland 合成器的公開協定連線到該合成器。它是一個處理程序，分為兩半，兩者之間共用一個影格緩衝區。

```text
wlroots compositor ── Wayland socket ──▶ compositor thread ──▶ Framebuffer ──▶ session tasks ──▶ TCP
                     screencopy           (calloop)            + damage log     (tokio)          RFB clients
                     image-copy-capture                       + cursor image
                     output-management                        ◀── Commands ◀──
                     virtual keyboard/pointer
                     data-control
```

- `crates/wlshare-proto` 是 wlshare 私有擴充的位元組，兩個方向都在其中：VP9 和圖塊編碼的訊框封裝（framing）以及用戶端為它們列出的內容，密度、輸出、音訊、攝影機和麥克風擴充，捲動訊息，要求「旁邊的另一個顯示器」的 ClientInit 位元組，以及為它們全體命名的協定版本。它是 zDesk 閘道所相依的唯一一個 crate，閘道在其 `wlshare` 功能（feature）之後依它的 `proto-v<N>` 標籤固定其版本，因此常駐程式和閘道用同一份程式碼建構和剖析每一個私有位元組（[協定版本](#協定版本)）。它只相依於 `thiserror`，不使用任何作業系統 API，每個建構函式都針對一個依據文件中的配置撰寫的解碼器進行測試，並由它的剖析器讀回。
- `crates/wlshare-vp9` 是 VP9 編碼器：固定由一個品質刻度（quality dial）控制的 libvpx，8 位元 4:4:4 或 4:2:0，連同位於它前面的各個平面、它的解碼器、品質遊走（quality walk），以及工作階段交給它的內容的擷取檔。它不決定任何關於傳輸的事情，也不使用任何作業系統 API。它目前的預先建置封存檔涵蓋 macOS arm64、Linux x86_64 和 aarch64，以及 Windows x86_64 MSVC。請參閱[VP9 編碼](#vp9-編碼)。
- `crates/wlshare` 是常駐程式。`rfb/` 決定傳輸中不屬於私有擴充的每一個位元組：交握、訊息的剖析與建構、RSA-AES 及其訊框、ZRLE 編碼器、建立在 `wlshare-vp9` 之上的 VP9 編碼器、圖塊編碼器、音訊擴充的編碼器，以及游標和剪貼簿編碼。音訊擴充的 FLAC 編碼器是 `sound-flac` 自己的，以純 Rust 撰寫；它的 Opus 編碼器則是 `sound-opus` 之下的 libopus，一個預先建置的靜態封存檔。它的測試用一個獨立的解碼器解碼每個編碼器的輸出，用用戶端的剖析器（`rfb/client.rs`）讀回每則伺服器訊息，並針對一個依據規格撰寫的用戶端執行 RSA-AES 交換。`compositor.rs` 是 Wayland 執行緒及其指令處理器；`capture.rs`、`cursor.rs`、`outputs.rs`、`input.rs` 和 `clipboard.rs` 是它所使用的各個協定，`sway.rs` 是 sway 的 IPC，用來為用戶端的虛擬顯示器建立和拔除無頭輸出；`audio.rs`、`camera.rs` 和 `microphone.rs` 是 PipeWire 這一側，`decode.rs` 是攝影機的 libavcodec 解碼器，`h264.rs` 是透過同一個 libavcodec 的 H.264 編碼器（使用主機的硬體或 libx264），用於圖塊畫面中的移動區域；`framebuffer.rs` 是共用的像素和變更區域（damage）；`session.rs` 是一個用戶端；`auth.rs` 檢查 RSA-AES 登入，`pam.rs` 是該檢查的系統那一半；`state.rs` 告訴連線到狀態通訊端的任何一方桌面是否被佔用，`watch.rs` 是 `wlshare watch`，也就是追隨該通訊端並為每種狀態執行一道指令的處理程序；`shared.rs` 是在合成器執行緒和各工作階段之間傳遞的內容。它的配置器是 jemalloc，以靜態方式連結為 `malloc` 本身，因此它所連結的 C 函式庫也透過它配置記憶體：glibc 的每執行緒 arena 會保留每個執行緒釋放的記憶體，而 zDesk 閘道在它們之上的記憶體用量隨每個工作階段增長。arm64 建置把 jemalloc 的頁面大小設為 64K，這樣可以在 arm64 開發板所搭載的 4K、16K 和 64K 核心上執行。

它的用戶端是 zDesk 閘道，每位觀看者都透過閘道存取桌面。

## 同一時間一個工作階段

桌面屬於一個用戶端。完成交握的連線會接管桌面，原先佔用桌面的用戶端的連線會被關閉，常駐程式會在記錄中記下是哪一個接管了——這與 Windows 遠端桌面所做的取捨相同，也是接管發生在交握*之後*的原因：未經驗證的連線，或登入被拒絕的連線，永遠不會取代進行中的工作階段。RFB 的 ClientInit 共用旗標不會被解讀為任何此類含義；它沒有對應的設定，也沒有辦法與別人一起觀看。唯一不接管桌面的連線，是該用戶端自己的第二個連線，它為用戶端顯示另一個輸出（[旁邊的另一個顯示器](#旁邊的另一個顯示器)）。

合成器執行緒持有這兩者各自的用戶端 id，因此規則只是一次比較：來自其他任何一方的輸入、尺寸調整和密度都會被捨棄，被取代的工作階段最後那些仍在傳送途中的訊息正是這類訊息；輸出選擇和剪貼簿只屬於桌面上的用戶端，旁邊的顯示器要求切換時，得到的回覆是原樣的清單。接管會放開前一個用戶端按住的按鍵和按鈕、它待處理的尺寸調整和排隊中的宣告，並結束它旁邊的顯示器；擷取從第一次交握開始執行，直到桌面上的用戶端離開。

誰在哪裡是一個 `watch`，而不是廣播事件之一：一個慢到落後於廣播的工作階段會遺失事件，而遺失這一個事件會讓兩個用戶端同時留在桌面上。watch 只保留最新的值，因此被取代的工作階段會依據它在那裡讀到的值結束——並且在結束之前一直被忽略。

這個 watch 與整個工作階段競爭，而不只是與工作階段中的空檔競爭。工作階段在一個 `select!` 中讓它的訊息迴圈與接管相互競爭，因此一個已停止讀取其通訊端的用戶端，會在阻塞於該通訊端的那次寫入途中被切斷，而不是在它拒絕讀取的整段期間一直佔著它的擷取和它的工作。用戶端 id 只會增加，正是這一點讓工作階段可以透過比較而不是透過確認來做出判斷：一個高於自身 id 的作用中 id，就是在它之後加入的連線，無論它是否曾在那裡看到過自己。這就是對競爭另一端的解答——兩個連線的加入被一起排入佇列，第二個在第一個尚未訂閱之前就已經在桌面上了。

### 狀態通訊端

`state_socket` 指定一個 Unix 通訊端，常駐程式在上面告知是否有用戶端在桌面上，以便圍繞該用戶端重新安排工作階段：可以讓 sway 停用各個顯示器，這會把它們的工作區移到向用戶端顯示的無頭輸出上，並在用戶端離開後重新啟用這些顯示器。常駐程式本身不對工作階段做任何事，也不執行任何東西：要做什麼由合成器和管理員決定，察覺常駐程式已經結束也是如此，因為不能指望常駐程式自己說出這一點。

無人觀看時，無頭輸出不必存在。設定的 `output` 是一項偏好：沒有該名稱的輸出時，常駐程式會共用另一個輸出，並在設定的輸出每次出現時把桌面移到它上面——僅在它出現時這麼做，因此之後指定了另一個輸出的用戶端會停留在它所要求的位置。用戶端在其 ServerInit 之前而不是之後接管桌面，因此在用戶端尚未被告知任何尺寸時，通訊端就已經回報 `held`；設定了 `output_wait_secs` 時，找不到該名稱輸出的工作階段會等待它這麼長的時間：追隨該通訊端的程式會啟用它，而用戶端最先被告知的尺寸就是該輸出的尺寸，而不是某個顯示器的尺寸——用戶端只會被短暫地顯示那個顯示器，而且無法變更它的模式。出現的輸出在被列出之前就已被共用，因此等待會在該輸出被列出的那一刻結束，否則就會逾時，用戶端從在此期間共用的輸出開始。已經存在但未被共用的該名稱輸出，是用戶端選擇了另一個輸出的結果，任何等待都不會撤銷這項選擇，因此不會為它等待。桌面在整個過程中都被佔用，因此等待還會與用戶端關閉其連線、以及之後的連線接管桌面相互競爭，其中任何一種情況都會讓工作階段就此結束。啟用它不是常駐程式的職責：合成器在回報一個被停用的顯示頭（head）時不帶位置，因此透過 wlr-output-management 啟用它的常駐程式就等於在選擇把它放在哪裡。

連線會被告知桌面目前的狀態——`held` 或 `free`，每行一個詞——並在每次狀態變化時再次被告知；連線自己什麼也不說，而且只有常駐程式執行時所用的帳號才能連線。這些詞追隨的是桌面，而不是連線：接管是桌面從一個用戶端轉到另一個用戶端，前後都被佔用，因此不算變化；旁邊的顯示器不佔用任何東西。每個連線讀取的都是各工作階段所讀取的同一個座位（seat）`watch`，因此它被告知的是桌面此刻的狀態，無論其間發生了多少次加入和離開。

串流的結束是追隨者被告知的第三件事，也是這裡使用通訊端而不是由常駐程式執行指令的原因。常駐程式結束時，無論它是停止了、發生了 panic 還是被當場終止，核心都會關閉這個通訊端，因此一個沒來得及說出桌面已空閒的常駐程式，也同樣說出了這一點。依序停止的常駐程式會刪除該檔案，否則由下一個常駐程式取代它。仍有回應的通訊端屬於另一個常駐程式：第二個常駐程式會拒絕在它上面啟動，而不是搶走它的追隨者；常駐程式只在該檔案仍是它自己建立的那個時才刪除它。

### 監看程式

`wlshare watch --held COMMAND --free COMMAND` 就是這個追隨者：一個獨立的處理程序，由工作階段啟動——作為常駐程式的使用者單元旁邊的另一個使用者單元，或者透過合成器的 `exec`——帶有工作階段的環境，並讀取同一個設定檔來確定通訊端的位置。有用戶端在桌面上時，它透過 `sh -c` 執行 *held*；在 `--free-after-secs` 時長內都沒有用戶端在桌面上時，執行 *free*。它無法連線到的常駐程式不佔用任何東西，通訊端每秒重試一次，因此兩者的啟動順序無關緊要，重新啟動的是其中哪一個也無關緊要。

它讓工作階段維持在某個狀態，而不是回報狀態的轉換。它執行的第一道指令是對應它啟動時桌面狀態的那一道，因為它無法知道先前的監看程式留下了什麼；在得知該狀態之前——常駐程式已經告知，或者無法連線——它什麼也不執行，因此在有用戶端時啟動的監看程式永遠不會先釋放桌面；此後，只有當桌面的狀態與上一道指令所表示的不同時，才會執行指令。因此，兩道指令都必須能夠安全地在已經處於其執行後狀態的工作階段上執行。*free* 之前的等待，使時斷時續的連線不會讓顯示器也跟著時開時關，也使被其單元重新啟動的常駐程式不會造成同樣的情況：在這段等待之內回來的用戶端，無論是透過同一個常駐程式還是下一個，都不會讓任何一道指令執行。

同一時間只執行一道指令。指令結束時，如果桌面*此刻*的狀態與上一道指令所表示的不同，就執行對應此刻狀態的指令，因此一個緩慢的 *held* 之後若發生離開，接著會執行 *free*；而一個緩慢的 *held* 之後若發生離開又返回，則什麼也不執行。指令執行期間桌面仍受監看，因此等待從用戶端離開時開始計時，而不是從指令結束時開始。到 `--timeout-secs` 時仍在執行的指令會被終止，而不是繼續等待它，因為把顯示器恢復回來的那道指令正是管理員所仰賴的；每道指令都作為自己的處理程序群組執行，被終止的是整個處理程序群組，因此 shell 啟動的東西也會隨之結束；工作在其執行期間被捨棄的指令也會受到同樣的處理。指令的結束狀態會被寫入記錄，除此之外不改變任何東西。

在上一道指令表示桌面被佔用時停止的監看程式——收到 SIGINT 或 SIGTERM 時——會在結束前執行 *free*，不經等待，並在任何仍在執行的指令之後執行。被當場終止的監看程式會讓工作階段保持原樣，而由其單元啟動來取代它的監看程式會執行對應桌面目前狀態的指令，正是這一點讓一切恢復正常。

## 擷取

透過 wlr-screencopy 的 `copy_with_damage` 複製到一個 `wl_shm` 緩衝區，同一時間只有一個影格在進行中，依 `max_fps` 控制節奏。合成器只在有內容變更時才回應僅限變更區域（damage）的複製，因此閒置的桌面不會產生任何開銷。有變更的矩形在影格緩衝區的鎖之下複製進影格緩衝區，世代計數器（generation）隨之遞增，並透過一個 `watch` 喚醒每個工作階段。

尚未持有任何像素的影格緩衝區是例外，而且兩方面都是。它要求的是一般的 `copy`，而不是僅限變更區域的複製，因為僅限變更區域的複製只在輸出變更時才會得到回應，而一個無人操作的輸出可能好幾分鐘都不變——這會讓用戶端停留在空白螢幕上，或停留在它剛離開的那個輸出的最後畫面上，直到有人移動滑鼠。而且，無論合成器回報哪裡變了，傳回的影格都會被整個採用：變更區域是相對於上一個影格衡量的，而剛建立、剛調整尺寸或剛指向另一個輸出的影格緩衝區沒有上一個影格，因此只複製回報的矩形會讓其餘部分保持空白。這兩點都取決於 `painted`（影格緩衝區在每次調整尺寸時清除它），也取決於影格的尺寸：以影格緩衝區尚未具備的尺寸宣告的影格，同樣會直接以一般複製要求，因為否則閒置的輸出永遠不會送來那個讓影格緩衝區調整尺寸的影格。完全不回報變更區域的影格也會被整個採用。

影格緩衝區保存一份 `(generation, rect)` 記錄。工作階段要求自己上次傳送的那個世代之後的變更區域，得到合併後的聯集；落後於記錄的工作階段，或尚未看到任何內容的工作階段，得到整個影格緩衝區。工作階段在鎖之下取得所需的像素——對 Raw 和 ZRLE 是複製出來，對圖塊是複製進編碼器自己的圖像，對 VP9 是直接轉換進串流的平面——並在釋放鎖之後才編碼，因此為慢速用戶端編碼更新永遠不會拖住擷取。

### 游標

指標不包含在影格中（`overlay_cursor = 0`）。在無頭輸出上，這需要 wlroots 0.19 或更新版本，其無頭後端把游標放在獨立的平面上，而不是把它們永久畫進輸出。同一個 wlroots 把該平面匯出為輸出的 ext-image-capture-source 的指標游標，而 `cursor.rs` 在有用戶端位於桌面期間，在其上保持一個 ext-image-copy-capture 游標工作階段：它的影格就是指標下方的應用程式所選擇的游標圖像，採用輸出的像素，也就是影格緩衝區的像素。同一時間總有一個影格在進行中，wlroots 只在游標緩衝區變更（新的形狀、新的縮放）時才回應它，因此只是移動的指標不會產生任何開銷。工作階段的 `enter` 和 `leave` 表明游標是否位於共用的輸出上並且可見；在兩者之外沒有圖像。工作階段需要一個 `wl_pointer`，而 seat 在從未有過指標之前會拒絕提供，在失去指標時會讓它失效，因此工作階段會等待 seat 指定一個指標（wlshare 自己的虛擬指標就是一個），並在每次開啟時取得一個新的 `wl_pointer`：每次切換輸出時都是如此，此時重新指向虛擬指標會讓 seat 短暫失去指標。

圖像會被裁切到它實際繪製的像素及其熱點，並在每次變更時以單獨的一次更新傳給每個用戶端。每個用戶端都必須在每個 `SetEncodings` 中列出標準 Cursor 虛擬編碼（`-239`），因此也就必須在要求影格緩衝區像素之前列出；同時列出 Cursor With Alpha（`-314`）的用戶端會收到原樣的預乘 RGBA，以 Raw 編碼，其餘用戶端則收到依其自身格式的像素，外加一個在 alpha 一半處截斷的遮罩，這會失去陰影和反鋸齒邊緣。沒有圖像——隱藏的指標，或位於另一個輸出上的指標——就是一個空矩形。RFB 游標的尺寸以影格緩衝區像素計，與擷取的圖像相同，因此以其自身尺寸傳送。用戶端把它放在自己已經在指標事件中傳送的座標處。因此游標移動從不等待擷取的影格。

任何把輸出鎖定為軟體游標的操作——另一個用戶端以畫入游標的方式進行 screencopy，例如 `grim -c`——都會把游標從其平面上移走。此時 wlroots 會把它畫進該輸出的每一次擷取，包括這一次擷取，而游標工作階段會回報游標已消失。

### 影格配置

影格緩衝區一律是 XRGB8888，各列由上而下排列，但擷取的影格未必兩者都符合，因此 `FrameLayout` 記錄進行中的影格有何不同，再由複製把它整理好。這兩種差異都來自合成器，而不是來自對它提出的任何要求：y 翻轉逐影格回報，而提供的唯一一種 shm 格式就是轉譯器偏好讀回的格式。因此，在 Intel 內顯（iGPU）上的合成器交出的紅色和藍色，與以軟體合成的合成器順序相反，而只有這次複製知道這一點：過了它，影格就是 XRGB8888、各列由上而下，編碼器不必區分任何情況。

`FrameLayout::bytes` 是一種排列置換，而不是轉換——即影格緩衝區的四個位元組各自位於影格自身像素中的哪個位置——因此它能吸收的是每通道八位元的所有 32 位元排列順序，僅此而已：

| 合成器提供的格式           | 記憶體中   | 來源 |
| ------------------------- | ---------- | ---- |
| `XRGB8888`, `ARGB8888`    | `B G R X`  | pixman, GLES2, Vulkan |
| `XBGR8888`, `ABGR8888`    | `R G B X`  | pixman, GLES2, Vulkan |
| `RGBX8888`, `RGBA8888`    | `X B G R`  | pixman |
| `BGRX8888`, `BGRA8888`    | `X R G B`  | pixman |

這就是 wlroots 的 screencopy 能為桌面提供的全部格式：它的 GLES2 轉譯器把 `GL_IMPLEMENTATION_COLOR_READ_FORMAT` 解析為前四種之一，它的 Vulkan 轉譯器回報材質自身的格式，而它的 pixman 轉譯器回報輸出材質的格式，這又增加了未使用位元組在前的那四種。

#### 刻意不處理的內容

原則上，wlroots 可以回報該表之外的格式，而每一種都需要真正轉換為影格緩衝區的每通道八位元，而不只是重新排列位元組：

- **10 位元**（`XRGB2101010` 及其七個同類格式）。在深色彩輸出上可能遇到；這是此處唯一一個看起來有未來的項目。它需要收窄各通道，而誠實的做法是為它單獨設一條路徑，而不是擴大這個排列置換。
- **緊縮 24 位元**（`RGB888`、`BGR888`），每像素三個位元組，而 `Framebuffer::apply` 中以四位元組計算的列跨距（stride）假定不存在這種情況。
- **16 位元**（`RGBA4444` 及其同類格式），只有非常舊的 GLES 驅動程式會回報。
- **`RGB565`、`BGR565`、5551 系列，以及 `XBGR16161616`(`F`)**。wlroots 可以回報這些格式，但 neatvnc 同樣沒有處理它們的分支，因此與其說這是相對於 wayvnc 的缺口，不如說是所有 wlroots VNC 伺服器共同的缺口。

在所測量的一般桌面上，Sway 不會給出其中任何一種；而且未處理的格式不會悄無聲息：擷取會記錄提供了什麼、需要的是什麼，並會重試，而不是提供一個凍結的畫面。

## 傳送像素

用戶端在已經要求（`FramebufferUpdateRequest`，或透過持續更新一次性要求）且存在變更區域時得到像素更新。每次像素更新是一個由合併後的矩形組成的 `FramebufferUpdate`，最多 32 個矩形，在該用戶端自己的 deflate 串流上以 ZRLE 編碼；對於清單中 ZRLE、VP9 和圖塊都沒有列出的用戶端則用 Raw——或者，對於列出 VP9 編碼的用戶端，是涵蓋整個影格緩衝區的一個矩形（[請見下文](#vp9-編碼)），對於列出圖塊編碼的用戶端，則是它的 PNG 圖塊和區域串流（[請見下文](#圖塊編碼)）。

協商了 Fence 時，每次像素更新都以一個由用戶端回傳的 fence 結束，下一輪像素會等待該回傳。隨要求一起傳送的游標、音訊和幾何資訊宣告先於該要求的任何像素，並且沒有自己的 fence。同一時間只有一輪像素在進行中，因此慢速連線永遠不會被淹沒，其間各影格會在影格緩衝區中合併。zDesk 同時協商 ContinuousUpdates 和 Fence。

回傳代表什麼由用戶端決定；當畫面是 VP9 串流時，zDesk 會一直壓著回傳，直到瀏覽器取走該影格，而不是在影格抵達的那一刻就回應（[請見下文](#用戶端的繪製)）。

尺寸變更會先送出，作為單獨的一次更新——一個 ExtendedDesktopSize 矩形，其原因說明是誰要求的（伺服器、該用戶端、另一個用戶端），或者對於沒有該擴充的用戶端是一個 DesktopSize 矩形——整個影格緩衝區在下一次更新中跟上。兩者都沒有協商的用戶端無法得到通知，會在其下一次更新時被中斷連線，而不是被傳送它不知道尺寸的像素。回應該虛擬編碼的 ExtendedDesktopSize 宣告也是一次更新，並像其他更新一樣等待要求。

## 協定版本

下文的各個私有擴充共用一個版本，兩端所使用的必須完全相同：沒有任何擴充在新配置旁保留舊配置，因此版本不同的閘道和常駐程式不會少讀一些位元組，而是會把對方的位元組讀錯。它是 `wlshare-proto` 中的 `PROTOCOL_VERSION`，也就是該 crate 的主版本號，crate 的版本為 `<N>.0.0`。對這個 crate 的任何變更都是一個新版本。帶來新版本的那次發行會把它的提交加上 `proto-v<N>` 標籤，zDesk 閘道固定的就是這個標籤，因此不變更這個 crate 的發行對閘道沒有任何要求；如果某次發行的 crate 與其版本既有標籤中的內容不同，發行工作流程會拒絕它。`wlshare --version` 會列出這個版本，常駐程式開始監聽時也會在記錄中寫出它。

- **版本**，用戶端 → 伺服器：虛擬編碼 `0x574c5600`（`WLV` 加一個零位元組）加上版本號，在每個列出了任何私有編碼的 `SetEncodings` 中都要列出——私有編碼即最高兩個位元組為 `WL` 的任何編碼。列出了其中任何一個卻沒有版本，或者列出了兩個版本的清單，都是致命錯誤。
- **回應**，伺服器 → 用戶端：第一個帶有版本的清單會得到回應，回應先於常駐程式傳送的任何其他內容，也不等待要求，是一個只含一個空矩形的更新，矩形的編碼列出常駐程式自己的版本。如果用戶端的版本與之不同，常駐程式在送出回應後關閉連線，而用戶端已從回應中得知常駐程式的版本，會把兩者都指明。之後的清單帶有同一個版本，不會再次得到回應。

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | `0`，FramebufferUpdate |
| 1 | U8 | 填補 |
| 2 | U16 | 矩形數，`1` |
| 4 | U16 | x，0 |
| 6 | U16 | y，0 |
| 8 | U16 | 寬度，0 |
| 10 | U16 | 高度，0 |
| 12 | S32 | 編碼，`0x574c5600` + 版本 |

zDesk 把回應當作它的清單之後的第一則訊息來讀取；如果某個 `wlshare` 目標的伺服器先傳送了別的內容，zDesk 就拒絕它：不為擴充標示版本的伺服器，不是它能對其使用這些擴充的伺服器。

## VP9 編碼

一種私有編碼 `WLSV`（`0x574c5356`），為 zDesk 閘道而設：把整個桌面作為一路 VP9 串流，供寧願要會動的畫面、也不要精確畫面的用戶端使用。在影格緩衝區不超過其視訊上限時，zDesk 會為設定了 `subtype = "wlshare"` 的目標上的每個瀏覽器列出它，並把每個影格原樣傳給瀏覽器，因為這正是 zDesk 否則要從 ZRLE 的像素編碼出來的串流——採用目標自己的刻度（dial）和瀏覽器的色度，兩者由它在該編碼旁邊指明，請見下文。不列出它的用戶端不受影響。

列出它並在旁邊附帶一個品質（請見下文）的用戶端會得到它，而不是標準的像素編碼，無論它在清單中的什麼位置；列出它卻不附帶品質則是致命錯誤。此後每次像素更新是一個涵蓋整個影格緩衝區的矩形，其主體是該影格編碼時的刻度、一個長度字組和一個 VP9 影格：

```text
u8 quality   the 1–100 dial the frame was coded at
u32 length   the frame's bytes
u8[length]   one VP9 frame
```

品質是編碼該影格時遊走（walk）所處的刻度，對收斂（settle）的影格則是上限（兩者均請見下文）：閘道不解碼就轉送這些影格，因此這是它無法自行從影格中讀出的唯一資訊，也是它在工作階段結束時記錄下來、用來判斷慢速連線的依據。連續的矩形是同一路串流，每個影格都參照之前的影格編碼，因此用戶端以一個解碼器依序解碼全部影格。編碼由 libvpx 完成，依 `wlshare-vp9` 的設定：量化器固定在刻度上，沒有前瞻延遲（lag），不丟棄影格，不產生未經要求的關鍵影格，色彩在位元串流中宣告。`crates/wlshare/src/rfb/vp9.rs` 負責影格緩衝區像素的輸入，以及依矩形的訊框封裝輸出影格，而訊框封裝屬於 `wlshare-proto` 的 `vp9` 模組——品質位元組、長度字組及其上限。影格所包含的內容是固定的：

- **8 位元 4:4:4、VP9 profile 1，除非清單要求 4:2:0。** 每個像素一個色彩樣本：4:2:0 對桌面造成的損失是文字的顏色——一像素寬的彩色筆畫與三個背景像素共用同一個樣本——而任何量化器都無法把它找回來。但沒有任何瀏覽器的硬體 VP9 解碼器支援 profile 1，而沒有軟體解碼器的瀏覽器，即 iOS 和 iPadOS 上的 Safari，會拒絕它，因此對於這樣的瀏覽器，閘道會列出 `WLSS`（請見下文），串流就是 4:2:0、VP9 profile 0，所有解碼器都支援。
- **有限範圍（studio swing）的 BT.601**，從影格緩衝區的 `B, G, R, X` 轉換而來，並在關鍵影格標頭中宣告，因此解碼器會用同一個矩陣轉換回來。用戶端的像素格式不適用。
- **隨連線變化的量化器和影格速率。** 1–100 的刻度（越大越精細）對應到 VP9 的量化器 63 到 8，與 zDesk 的刻度一樣；位元率控制固定在刻度所在的位置，沒有位元率，沒有適應性量化，也不丟棄影格。工作階段從用戶端清單所指定的上限（`WLQ`，請見下文）開始，從不超過它，並在用戶端落後時向下遊走，直到下限 20——即 `wlshare-vp9` 的 `walk`。下限是常數而不是設定鍵，所有適應性串流都是如此：WebRTC 的品質縮放器（quality scaler）在它自己的臨界值處從量化器轉為調整解析度和影格速率，而這裡的遊走則轉為調整影格速率，下文的收斂會在上限處讓靜止的桌面重新變清晰。一個影格的排隊時間是它的 fence 往返時間——在用戶端拿到該影格後回應，對 zDesk 來說就是瀏覽器取走該影格之後（[請見下文](#用戶端的繪製)）——減去最近一分鐘中最短的往返時間，這樣距離就不會被當成排隊；關鍵影格計入這個最小值，但不作為判定。沒有 Fence 時——以及對於固定的刻度，無論有沒有 fence——排隊時間就是寫入該影格阻塞了多久，其中 20 ms 即算落後。最近四個影格中有兩個落後（排隊 60 ms 或以上）就降低品質：降十個點，150 ms 時降二十個點，400 ms 時降三十個點；一旦刻度已在下限，就改為把擷取的影格間隔加倍，在預設的 `max_fps` 下從 33 ms 直到 133 ms，而在 400 ms 時兩者同時進行。影格間隔在下一個影格到期時讀取，因此上一個影格的 fence 帶來的一步就會決定該影格的節奏。游標、音訊宣告和尺寸發生變更的桌面從不等待被放慢的影格的輪次。每秒最多走一步（降低之後延遲在 150 ms 或以上時，半秒後即可再走一步，這樣的一步只降低品質而不動影格速率）；當延遲仍在以每秒為上一步時數值的五分之一的速度下降——即上一步留下的佇列正在清空——時，不再走下一步，因為那一步已經足夠；關鍵影格之後，判定要等兩秒，因為它後面的影格要排在它的傳輸之後。一秒的順暢影格（30 ms 或以下），且至少四個，會先恢復影格速率，然後恢復品質，只要連線持續接受，步長就從三開始加倍直到二十四，並且在連線接受了一步之後，只要這些影格的排隊都不超過 15 ms，半秒的順暢影格就足夠；連線在四秒內拒絕的一步，會在 300 ms 後退回到它出發時的品質，並且在十五秒內，遊走最多只回升到朝被拒絕的品質的一半處。刻度在執行中的編碼器上移動，因此移動不需要關鍵影格，而以新尺寸建立的編碼器從刻度目前所在之處開始。被放慢的工作階段自己為影格控制節奏；未被放慢的工作階段則由擷取及其唯一一個進行中的 fence 控制節奏。
- **用戶端在它旁邊列出的內容決定串流的形態**，就像 Tight 的品質等級搭載在 `SetEncodings` 上一樣——用虛擬編碼而不是訊息，因為不是 wlshare 的伺服器會忽略它不認識的編碼，而它不認識的訊息會結束連線，也因為它們搭載在指定該編碼的清單上，所以第一個影格就已經是所要求的樣子。`0x574c5100` 加上 1–100 的品質（`WLQ` 及其值）指定遊走永不超過的上限；`WLSD`（`0x574c5344`）把刻度固定在那裡，此時遊走對 fence 中的資訊置之不理——只有寫入阻塞的影格會使它移動，無論有沒有 fence——收斂也只針對這種影格所造成的粗糙；`WLSS`（`0x574c5353`，subsampled）要求 4:2:0 的串流。閘道依據目標的設定鍵列出前兩者，因此 `video_quality` 和 `render_adaptive` 在透傳的串流上與在閘道自己編碼的串流上意義相同，並依據瀏覽器能解碼什麼列出 `WLSS`。在每次 `SetEncodings` 時讀取：新的上限會移動執行中編碼器的刻度，並以該刻度把畫面傳送一次，就像收斂那樣，無論桌面是否變更；而新的遊走設定只移動刻度。兩者都不需要關鍵影格；新的色度則是一路新串流，從關鍵影格開始。指定 VP9 卻不帶品質的清單是致命錯誤，就像格式錯誤的訊息一樣：wlshare 沒有自己的品質，閘道在每個清單上都會在該編碼旁邊指定一個，而不是閘道的用戶端——一般的 `vnc` 目標透過 RFB 基準功能讀取 wlshare——根本不會列出 VP9。沒有 `WLSD` 時串流會遊走，沒有 `WLSS` 時串流為 4:4:4。沒有前瞻延遲，並採用具備列層級和 tile 層級平行處理的多執行緒：編碼器使用機器的核心數減二個執行緒，最多八個，因為一次編碼是另一端的人要等待的突發工作。串流的結構依照畫面的寬度和這些執行緒而定，是為了解碼器：寬度小於 1440 時一個 tile 欄，1440 起兩個，2048 起四個，5760 起八個，永遠不超過執行緒數；四個或以上 tile 欄的串流在編碼時不使用迴路濾波器。編碼畫面一半或以上的畫面間影格——捲動的頁面、播放中的影片——以 libvpx 的 speed 9（其即時 VP9 最快的速度）搜尋，其他每一個影格，包括關鍵影格和收斂影格，都以 speed 7 編碼，速度在執行中的編碼器上切換，不需要關鍵影格：在保存的擷取上以 4:4:4、品質 90 測得，speed 9 下捲動或影片每個影格耗用的處理器時間少 37–44%，位元組在 4K 下多 1–15%、在 1080p 下多 7–37%，移動期間的畫面最多低 0.4 dB；而拖曳或揭開的視窗只佔畫面的四分之一到三分之一，speed 9 下會傳送 1.4 到 2.3 倍的位元組，所以維持 speed 7。從影格緩衝區像素到平面的轉換由 `yuv` crate 完成，它在執行階段選擇 AVX2 或 NEON 路徑：常駐程式依目標平台的基準建置，對處理器沒有其他要求。
- **靜止的桌面會以上限變清晰，而遊走保持原位。** 遊走只在有影格送出時執行。通常只有在內容變更時才會送出影格，因此一個在連線剛把畫面變粗糙後就停下來的桌面，會一直保持那個畫面，直到它再次變更。一旦一個低於上限編碼的影格已送達——其 fence 已得到回應，或在沒有 Fence 時其寫入已完成——且此後 500 ms 內沒有傳送任何內容，未變更的畫面就會在用戶端要求的下一次更新時再次送出，作為一個處於上限的畫面間影格（inter frame），整體編碼而不是依其變更區域編碼：用戶端所持有的粗糙區塊的殘差以更精細的量化器編碼，用戶端已精確持有的區塊保持原樣，因此它不需要關鍵影格就能讓整個桌面變清晰（`a_settle_sharpens_the_picture_and_leaves_the_dial` 保證了這一點）。編碼器只為這一個影格重新調整，之後恢復到遊走的品質，而且這個影格不作為判定：螢幕停止變化並不說明連線的任何情況，而經測量，每一陣動態都從上限開始遊走，會讓畫面在每一陣動態中都落後半秒。靜止之前的順暢影格也不跨越靜止期：遊走的連續順暢影格計數在收斂時重新開始，因此一陣動態要憑它自己的影格贏回向上的一步，而不是在第一個影格就拿到一步。以上限整體送出的影格不欠任何東西，在它之後變靜止的桌面什麼也不傳送；以上限編碼的變更區域影格只讓它所編碼的區塊變清晰，因此在它之前被變粗糙的畫面仍欠一次收斂。
- **只在解碼器需要時才傳送關鍵影格**：列出該編碼後的第一個影格、新尺寸或新色度下的第一個影格（這兩種情況都會重新建立編碼器），以及回應非增量要求的影格。沒有週期性的關鍵影格；在 TCP 上不會遺失任何內容。

只要有任何變更區域，就會傳送一次一般的 VP9 更新；非增量要求、品質上限的變更以及上文所述的收斂也可能需要傳送一次。影格是整個畫面，而未變更的部分在位元組和時間上都幾乎不花費任何代價：工作階段把用戶端上一個影格以來的變更區域交給編碼器，編碼器轉換變更區域中的矩形並編碼它們所觸及的 16×16 區塊，其他每個區塊都保持用戶端所持有的樣子，放在一個解碼器不再讀取其中任何內容的區段（segment）中。轉換直接從影格緩衝區出發，在其鎖之下進入編碼器的平面，鎖釋放之後再從這些平面編碼影格：中間不會在任何地方複製像素，除非這些影格正在被擷取。編碼器的測量結果就放在為其測量的常數旁邊，位於 `crates/wlshare-vp9` 中。關鍵影格、編碼器的第一個影格、收斂影格，以及變更區域記錄已無法追溯到的用戶端，都整體編碼。編碼在工作階段的工作執行緒上執行，該執行緒會被告知這是阻塞操作，而 fence 像對標準像素更新一樣保持只有一個影格在進行中。去掉該編碼的 `SetEncodings` 會以它所選擇的標準編碼（列出 ZRLE 時為 ZRLE，否則為 Raw）回應整個影格緩衝區，因為用戶端持有的是有損畫面。

libvpx 以 `wlshare-vp9` 連結它的方式存在於常駐程式中，來自 `libvpx-prebuilt` 的靜態封存檔，它也是 VP9 編碼的測試讀回每個影格所用的解碼器（`wlshare_vp9::Decoder`）。如果 libvpx 沒有產出影格，就不傳送任何內容：變更區域保持未被看到，關鍵影格也仍然欠著，留給下一次變更帶來的影格。

### 擷取交給編碼器的內容

以 `--capture-frames DIR` 啟動的常駐程式會為每個工作階段精確寫下其 VP9 編碼器所收到的內容：每個影格的時間、尺寸、當時的刻度（dial）、是否要求了關鍵影格、變更區域（damage）矩形或沒有矩形這件事，以及這些矩形所跨越的各列，依影格緩衝區中保存的樣子，即 `B, G, R, X`。該檔案是 `wlshare-vp9` 的 `capture` 模組的擷取檔，其配置在那裡有完整說明：它是本儲存庫自己的格式，在這裡讀寫，與編解碼器毫無關係，因為一份擷取就是編碼器面前的像素，無論那是哪個編碼器。每個工作階段一個 `<unix millis>-client<id>.wlcap`，在把像素交給編碼器的那唯一一處呼叫中寫入，因此涵蓋該工作階段在調整尺寸過程中建立的每一個編碼器。途中沒有任何有損環節，這正是重點所在：編碼器是在桌面實際顯示的畫面及其附帶的矩形上重新執行，而不是在某個串流的解碼結果上執行。擷取只針對 4:4:4 串流，這是其每一種用途所關心的色度，也是其工具重播它時所用的色度（`examples/vp9cap.rs`）：用戶端要求 4:2:0（`WLSS`）的工作階段，在此期間不寫入任何影格。這些檔案未經壓縮且很大——一個 4K 完整影格就是 33 MB——之後再用 `zstd` 壓縮。

該旗標只存在於命令列上，設定中沒有對應的鍵，這是刻意的：擷取會把每個工作階段的每一個影格寫入磁碟且不刪除任何內容，因此只有在有人親手輸入它的地方才會開啟，用於一次他們親手啟動並會親手停止的執行。套件中的單元不會指定它，被指定了它的單元會在啟動時被拒絕：systemd 會在 `SYSTEMD_EXEC_PID` 中說明它啟動的是哪個處理程序，在其中發現自己的 id 且設定了該旗標的常駐程式不會執行。在 systemd 啟動的工作階段中從終端機啟動的常駐程式具有另一個 id，不會被當成單元啟動的常駐程式。

`docker/capture/` 不需要人工就能完成這一切：一個執行在 wlroots 0.19 上的無頭 sway；常駐程式由容器的指令碼帶著該旗標啟動，在 loopback 上不做身分驗證；以及 `vp9-sink`（`crates/wlshare/examples/`），即容器中唯一的用戶端，它以一個品質列出 VP9，並列出 Fence、ContinuousUpdates、ExtendedDesktopSize 和 Cursor，設定桌面尺寸，回傳 fence，丟棄影格，依提示在一段時間內延遲讀取，並輸入情境要它輸入的內容，讓按鍵像人的按鍵一樣經由常駐程式到達桌面。內容是 `docker/capture/scenarios/`，每個情境一個指令碼，可在任何 sway 桌面上播放，也可以在常駐程式正在擷取的桌面上手動執行：安靜的情境有：在終端機中輸入並捲動、一個放著不動的頁面，以及一個位於頁面上方、被移到一旁並關閉的視窗；繁忙的情境有：被隨機彩色文字列淹沒的終端機（`flood.sh`，以及 `busy-lines.sh`，它會淹沒執行它的任何終端機）、捲動的頁面、拖曳的視窗，以及一段全螢幕並裁切至填滿螢幕的影片，因此每個像素都屬於影片：即 `--video` 交給容器的檔案，video 和 walk 兩個情境需要它。`run.sh` 在每個尺寸下播放它們，每個情境外面都包著一個工作階段——第一個情境把尺寸調整到該尺寸，video 情境中途要求一個關鍵影格，而 walk 情境是在 sink 延遲讀取時播放的影片，於是 fence 回來得晚，刻度下降，然後回升，然後影片在目前位置暫停，以便對它的一個影格進行收斂（settle）——每個情境都有自己的工作階段，因此有自己的檔案。指令碼會在擷取它的工作階段連線之前開啟視窗並宣告已就緒，並在該工作階段收到第一個影格後開始播放，如此每份擷取都以情境的視窗已繪製好開始，而不是以視窗開啟期間的空白桌面開始：視窗在該尺寸下的另一個專屬工作階段中開啟，該工作階段隨後結束、其擷取被丟棄，因為常駐程式的影格緩衝區只從用戶端取得尺寸，而且只在有用戶端連線時保留其畫面，而這個畫面就是新連線的用戶端首先收到的內容。flood 情境的工作階段會超過其時長繼續執行，直到滿一百五十個影格：它的每一個影格都是全新的完整畫面，是編碼最慢的情況，大桌面每秒只能得到其中幾個影格。失敗的情境，或其 sink 失敗的情境，不會留下擷取並會使整次執行失敗，因此以某個情境命名的檔案絕不會是別的東西。`scripts/capture-frames.sh` 建置並執行它，只針對工作區自己的編碼器，別無其他。zDesk 閘道並未為此加入擷取功能：它在 Standard 模式下的 Mac 和透過 RDP 的 Windows 交給它的都是同類桌面的精確像素，因此在它們的尺寸下的 wlshare 擷取可以代表它們。

擷取是來源，用來測試解碼器並為其計時的串流都由它們製作而成：`vp9cap`（`crates/wlshare-vp9/examples/`）把一份擷取再次送入編碼器，每個影格帶著它的矩形，以它當初編碼時的刻度，在要求了關鍵影格的地方產生關鍵影格。因此，品質遊走（walk）的各步及其收斂都在它產生的串流中，不必重播慢速連線；而對桌面編碼方式的變更——無論是在 `wlshare-vp9` 中，還是升級其 libvpx——只需在已保存的擷取上執行一次 `scripts/vp9-samples.sh`，而不必重播桌面。該指令碼寫出 vp9-wasm 的效能測試所讀取的內容：對每個尺寸，一個安靜樣本和一個繁忙樣本，各 120 個影格，分別取終端機擷取的開頭和影片擷取中回報變更像素最多的那一串連續影格，每個都以當時畫面的關鍵影格開頭，並依串流本身的關鍵影格標頭所述（而不是依編碼器的規則）命名為 `<scenario>-<WxH>-<tile columns>col-<lf|nolf>`。使用 `--streams` 時，它還會完整編碼每份擷取，擷取在某個尺寸下持續三十個影格或以上的每一段各產生一個串流，以 IVF 格式輸出，旁邊附一個 CSV，記錄每個影格的時間、位元組數、是否為關鍵影格和刻度。每個串流都會得到 libvpx 解碼出的每個影格的 MD5（由 ffmpeg 產生），若 ffmpeg 自己的 VP9 解碼器（與 libvpx 不共用任何程式碼）對某個串流解出不同的畫面，執行就在該串流處停止。那裡的編碼器無論機器為何都使用四個執行緒，因為一個寬度被編碼成的圖塊欄數受執行緒數限制，而一個樣本無論在哪裡產生都必須是同一個串流。編碼器在擷取本身上測量，快速執行時則在擷取的部分上測量：`scripts/capture-samples.sh` 用 `vp9cap trim --frames` 把每份擷取以其原名裁切為 120 個影格，選取方式與樣本相同，即安靜情境取開頭、繁忙情境取最繁忙的部分，裁切後的第一個影格是當時的完整畫面，並要求關鍵影格；`walk` 則完整複製，因為它的刻度在整個過程中下降、回升並收斂。

遊走也以同樣的方式在擷取上測量，無需對連線整形：`walk-sim`（`crates/wlshare-vp9/examples/`）像工作階段那樣把一份或幾份擷取送入編碼器和 `QualityWalk`，一個影格在途，送往一個 zDesk 把串流轉給瀏覽器的模型——影格一到就交給瀏覽器的連線，在它之前交出的影格都已繪製時立即回應它的 fence，否則等最早的那一個欠過連線的 ping 往返時間後再回應，最多 500 ms——連線的速率（可在給定時刻變更）和往返時間由參數給出。它回報桌面的每次變更過了多久才被繪製、每秒影格數、移動編碼時的刻度和所用的連線，加上 `--timeline` 時還有每一個影格。時間是模型的時間，因此一次執行只需幾秒；`--encode` 固定一次編碼所用的時間，以便兩種遊走在相同的影格上比較。

### 用戶端的繪製

上面的品質遊走只有在它所計時的 fence 可信時才可信，而影格一到達就立即回傳的 fence，計時的只是到閘道的連線，別無其他。一個無法以桌面繪製的速度接收影格的瀏覽器，會被讀成一個健康的用戶端：伺服器會繼續以該刻度編碼，而使用者看到的是一個延遲的畫面，所有測量卻都說連線暢通。

因此，zDesk 會依瀏覽器那一端的連線對先前各影格的處理情況來扣住每次回傳，這由瀏覽器在其繪製器完成繪製後傳送的 `paintAck` 測量。如此，一個影格到達螢幕所經過的路徑就落在品質遊走所讀取的往返時間之內；而且由於伺服器在回傳到達之前不傳送任何內容，瀏覽器原本只會在未被看到的情況下覆蓋掉的影格根本不會被編碼。不在繪製的瀏覽器不能有辦法讓桌面停下，因此任何回傳都不會被扣住超過 500 ms——即 zDesk 的 `FENCE_HOLD_LIMIT`，其繪製時間窗的寬限期。

## 圖塊編碼

`WLSV` 之外的第二種私有畫面編碼 `WLST`（`0x574c5354`），供 zDesk 閘道在頻寬充裕的連線上使用：桌面靜止之處為精確的 PNG 圖塊，每個移動區域各有一路自己的視訊串流，即 H.264——主機的硬體，或 libx264。它是閘道依目標做出的選擇，而不是取代：`WLSV`，即涵蓋整個桌面、隨連線調整品質的一路串流，仍是慢速連線上的畫面，在那裡以較少位元組傳輸的有損串流才是連線承受得起的。本編碼花費連線擁有的位元組，換來較少的編碼器時間和最終精確的畫面；而在允許其刻度遊走的清單上，它會像 `WLSV` 一樣跟隨連線：連線落後時，靜止部分以有損 WebP 傳送，連線有餘裕後再次精確，因此在頻寬並非始終充裕的連線上也想節省編碼器時間的目標同樣能得到滿足。它就是 zDesk 的 Motion，那個閘道之所以捨棄它，是因為它夾在原生協定和頁面之間——在 RDP 上，它解碼主機已編碼的內容只為再編碼一次，在 Mac 上它疊加在 ZRLE 之上——而它屬於這裡，在這裡合成器的像素和變更區域只編碼一次。`crates/wlshare/src/rfb/tiles.rs` 是編碼器，`wlshare-proto` 的 `tiles` 模組是其訊框封裝格式。

列出它並在旁邊附帶品質（`WLQ` 及其值，與 VP9 相同）、並在希望刻度固定而非遊走時附帶 `WLSD`（與 VP9 的清單表達方式相同）的用戶端，無論它在清單中的什麼位置，都會得到它，而不是標準像素編碼。不帶品質列出它是致命錯誤，同時列出它和 `WLSV` 的清單也是：它們是兩種畫面，用戶端只想要其中一種。此後，一次像素更新就是任意數量的該編碼矩形，依序繪製，每個都是桌面的一個矩形，其主體以一個種類開頭：

```text
u8 kind
0 PNG     u32 length | u8[length]                          a PNG of exactly the rectangle's pixels
1 START   u8 stream | u32 length | u8[length]              a region stream's first frame
2 FRAME   u8 stream | u32 length | u8[length]              the stream's next frame
3 END     u8 stream                                        the stream is over
4 WEBP    u32 length | u8[length]                          a lossy WebP of the rectangle's pixels
```

PNG 就是桌面在該處的精確像素，8 位元 RGB 或其調色盤形式，不依賴它之前的任何內容。WEBP 是同一矩形的有損版本，即其像素在遊走目前所處刻度下的 WebP，同樣不依賴它之前的任何內容，並且欠一份精確版本；它只在刻度遊走的清單上傳送。START 在其 id 上、在其矩形範圍內開始一個串流，內容是一個該尺寸（邊長無條件進位為偶數）的 H.264 關鍵影格，用戶端從其左上角裁切到該矩形；該 id 上的每個 FRAME 是該串流在同一矩形上的下一個影格；END 表示串流已結束，其最後的畫面一直保留，直到有內容繪製在其上。串流的矩形上的 PNG 只會出現在其 END 之後，因此依序把每個矩形繪製到它所說的位置，得到的就是畫面。

- **靜止即精確。** 桌面從 (0,0) 開始劃分為 64×64 的圖塊。自用戶端上次更新以來的變更區域在鎖定下從影格緩衝區複製到編碼器保留的一幅畫面中，並在那裡與用戶端持有的內容逐圖塊比較，因此合成器重繪其顯示的內容時不會傳送任何東西。發生了變更且沒有串流承載的圖塊以 PNG 傳送：一列中連續的一串，切成 64 列高的條帶，合為一張影像。重新開始的畫面——編碼新被列出、新的尺寸、非增量要求——立即以同樣方式完整傳送，而 Motion 會先以串流傳送它，之後反正還要把每個圖塊以 PNG 傳送：在頻寬充裕的連線上，那個串流是白費工夫。PNG 採用閘道的圖塊編碼器：像素最多 256 種顏色時用不加過濾的調色盤，否則用 RGB 並為每列選擇過濾方式，採用 `png` 的快速壓縮。
- **移動的部分是視訊。** 採用 Motion 的規則：一個圖塊在最近 8 個十分之一秒中有 4 個發生變更時即為移動中；移動圖塊合併為 4 連通元件，不足 5 個圖塊的元件交給 PNG，邊界框會合併，除非合併後的框超過移動圖塊的兩倍，而且同時最多有 4 個區域以串流傳輸。區域最多每 500 ms 重新配置一次：縮小的區域保留其串流，擴大的區域從關鍵影格重新開始，一秒內沒有移動的區域結束。一個區域最大為整個桌面，其上限與 `WLSV` 的整桌面串流相同：閘道只為其瀏覽器解碼器能接受的桌面列出該編碼，與列出 `WLSV` 時一樣，因此 wlshare 不對區域施加自己的上限。每個區域都是只涵蓋其矩形的一個編碼器，並像 `WLSV` 那樣被告知其中的變更區域，因此編碼器的時間取決於移動的面積而不是整個桌面。它是 4:2:0 的 H.264（請見下文），所有瀏覽器都能解碼，包括其硬體解碼器；它的損失只在區域移動期間存在，因為收斂會使其變得精確。它的刻度就是下文中遊走的刻度。
- **刻度會遊走，除非清單固定它。** 清單給出的刻度是一個上限，工作階段對連線的品質遊走——與移動 `WLSV` 刻度的是同一個遊走（請見上文 VP9 編碼一節），閾值和步長都相同——依每次更新的 fence、在沒有 fence 時依其寫入阻塞的時長，把這種畫面的刻度移到上限之下。攜帶 START 或完整畫面的更新像關鍵影格一樣穿越連線，不作為判據；其他任何更新都是判據。每個區域的串流都從一個 IDR 開始跟隨刻度的移動，因為兩種編碼器都不能在執行中的串流上接受新的恆定量化參數（請見下文），攜帶它的更新也被算作關鍵影格；被放慢的遊走像控制 `WLSV` 的影格那樣控制更新的節奏。靜止部分同樣跟隨它：在上限處，靜止部分是精確的，即 PNG；在上限之下則是該刻度下的有損 WebP——libwebp 的 VP8，使用其最快的方法，4:2:0，所有瀏覽器都能解碼，依目標的基線靜態連結——但像素能放進調色盤的靜止部分例外：文字、線條和面板，精確傳送的開銷不比有損更大，它保持為 PNG，直到遊走放慢了影格率，此時所有靜止部分都以有損傳送。每個以有損傳送的圖塊都欠一份精確版本，與串流承載過的圖塊一樣，而在遊走被放慢期間這些欠款會等待：落後的連線不會再被塞入它已經擁有的內容的精確畫面。它們只等到桌面靜止兩秒為止，不會更久：靜止的桌面不傳送任何更新，也就沒有能讓品質遊走回升的判據。清單旁附帶 `WLSD` 時，刻度被固定，所有靜止部分都精確，串流維持在該刻度，被寫入阻塞推動的遊走只控制更新的節奏：針對頻寬充裕的連線，在那裡遊走只會停在上限處。之所以使用 `WLSV` 的遊走而不是自己的一套，是因為判據相同——更新在連線上的排隊——而第二套閾值就是第二件需要測量的東西。2026-10-26 在一台 8 核心 AMD EPYC（Milan）虛擬機上測量，libx264 使用六個執行緒，每種情境 120 個影格，遊走固定在 50 和 20：1080p 影片從上限處的 19.3 MB 降到 5.6 和 3.5 MB，CPU 時間不增反減（1073 ms 對 1027 和 932），其靜止部分在上限處為 9.6 MB 的 PNG，遊走時為 0.6 MB 的 WebP 外加結尾一次精確傳送；4K 影片從 51 MB 降到 14 和 9；全部是串流的捲動從 22 MB 降到 16 和 12；視窗拖曳的靜止部分全是調色盤圖塊，仍為 PNG，位元組只隨串流的刻度下降；移動期間的畫面為 38.6 和 34.7 dB，而上限處為 44.6；每個擷取最終都精確。
- **H.264 由 wlshare 選擇：主機的硬體，或 libx264。** 每個區域都是 H.264，由啟動時一次性找到的編碼器編碼；用戶端沒有發言權，START 也不指明編解碼器。在 GPU 具有某個 VA-API 驅動程式可以存取的 H.264 編碼器的主機上——透過設定中的 `hardware_h264 = true`（預設值）來尋找——使用的就是該編碼器，這正是這種畫面的用途：處理器只需負擔到 NV12 的轉換，而不負擔任何搜尋。在沒有這種編碼器、或關閉了該鍵的主機上，使用的是 `ultrafast` 預設集的 libx264，它每個影格耗用的處理器時間約為 VP9 的三分之一，位元組數約為其兩倍，適用於有這些位元組可用的連線（測量請見下文）。`crates/wlshare/src/h264.rs` 就是該編碼器，即透過已為攝影機連結的 libavcodec（Debian 的版本，它本身連結了 libx264）使用的 libavcodec 的 `h264_vaapi` 或 `libx264`，以及常駐程式圖塊編碼器的 `RegionCoder`，它為每個區域開啟一個這樣的串流。編碼方式與 VP9 一樣是固定的：固定量化參數，刻度對應到 QP 40 至 16，沒有位元率，不丟棄任何影格，沒有 B 影格，一個影格進一個影格出，串流的 VUI 中為有限範圍（studio swing）的 BT.601；畫面為區域尺寸無條件進位為偶數邊長，這是 libx264 的要求，因此奇數邊長的區域（例如位於奇數尺寸桌面邊緣的區域）會被編碼得大一個像素，下方重複其最後一列，右側為黑色，由閘道裁掉；每個影格是一個 Annex B 存取單元，每個 IDR 之前都有參數集，在串流的 START 處有一個 IDR，刻度變更後再有一個，因為 VA-API 的量化參數在其編碼器的整個生命週期內不變，而 x264 的重新設定只攜帶 rate factor 而不攜帶恆定量化參數，因此 libx264 的編碼器也以同樣方式重新建立。硬體編碼器的是帶 CABAC 的 High profile；libx264 的是 Constrained Baseline，即 `ultrafast` 最終對應的設定檔，調校為 `zerolatency`——沒有前瞻（lookahead），畫面依 VP9 編碼器的執行緒數切片——沒有場景切換偵測，並在串流的第一個 IDR 之前帶有其版本 SEI，解碼器會略過它。閘道依據該參數集宣告這個串流，即 `avc1.` 加上其設定檔（profile）和層級（level），瀏覽器的解碼器在有硬體解碼器時以硬體接收它。啟動時，常駐程式依序嘗試每個渲染節點，先是低功耗編碼器——Intel 的固定功能單元，它把執行單元留給桌面，且不需要 HuC 韌體就能進行 CQP 編碼——然後是著色器編碼器，再來是 libx264，每個都在一幅小畫面的一個影格上嘗試，因為驅動程式列出的設定檔多於它能開啟的；記錄會說明找到了什麼，什麼都沒找到時常駐程式不會啟動：區域沒有其他編解碼器可用。無法為工作階段的圖塊畫面開啟的編碼器、拒絕某個串流的編碼器，或在中途使某個串流失敗的編碼器，都會結束該工作階段，與任何編碼器失敗時一樣。每個工作階段自行開啟裝置，因此一個 VA display 只屬於一個執行緒。整桌面的 `WLSV` 串流無論清單如何都是 VP9：品質遊走的量化參數每個影格都在變，而硬體編碼器的量化參數不會。2026-10-21 在 Intel UHD 630 的低功耗編碼器上測量，在一個雙核心容器中，被淹沒的 1280×800 終端機，品質 90 下 20 s：H.264 區域以常駐程式 6 s 的 CPU 時間傳送了 598 個影格，而 VP9 以 17 s 傳送了 176 個，兩者都被 FFmpeg 自己的解碼器完整讀回（常駐程式 crate 中的 `examples/tiles-sink.rs` 就是所執行的用戶端，並為此保留每個串流）。2026-10-22 在一台沒有 GPU 的六核心機器上測量，在無頭 labwc 下，同樣被淹沒的 1280×800 終端機，品質 90，20 s，每個編碼器使用四個執行緒：libx264 `ultrafast` 以常駐程式 15–17 s 的 CPU 時間傳送了 590 個影格，而 VP9 以 33 s 傳送了 395 個，即每個影格約 27 ms 處理器時間對 83 ms，每個影格的位元組數約為 VP9 的 1.8 倍，100–135 Mbit/s 對 37 Mbit/s；libx264 的 `superfast` 和 `veryfast` 帶 CABAC 且搜尋更多，約 535 個影格耗費 42 s，並不比 VP9 少，這就是預設集選用 `ultrafast` 的原因。常駐程式的單元測試在每台機器上用 libx264 編碼影格，並在硬體上編碼影格，再用 libavcodec 的軟體解碼器解碼；在沒有編碼器的機器上，硬體的測試附帶一句說明而通過。
- **它會收斂為無損。** 串流承載過的每個圖塊，以及以有損傳送的每個靜止部分，在靜止半秒後都欠一個精確的 PNG。每四分之一秒查找一次欠下的內容，每次最多 40 個圖塊，每次查找都是一次更新，與其他更新一樣等待要求和 fence，而遊走被放慢期間，在桌面靜止兩秒之前不查找，因此停下的桌面會在頁面上變得精確，而一旦精確，就不再傳送任何內容。
- **與其他編碼一樣按輪進行。** 每次更新以其 fence 結束，同一時間只有一個在傳輸中。新尺寸會結束所有串流且不傳 END——尺寸先送出，隨後是完整畫面——而非增量要求以各自的 END 結束它們。去掉該編碼的清單會得到以其所選標準編碼傳送的整個影格緩衝區。

常駐程式 crate 中的 `examples/motion-bench.rs` 把保存的擷取透過本編碼器和 `WLSV` 播放，兩者都像頁面那樣解碼：圖塊的更新經過用戶端的剖析器，WebP 由 `image-webp` 的純 Rust 解碼器解碼，每個區域由 libavcodec 的軟體 H.264 解碼器解碼；`--walk-at` 把圖塊的遊走固定在上限之下，此時靜止部分以有損傳送。它的區域是
常駐程式自己的 H.264——`h264.rs`，依常駐程式的方式找到，或使用 `--libx264` 時為 libx264——因此在常駐程式能建置的地方它就能執行。下面的數字是在區域還是由 libvpx 以 speed 9 編碼的 VP9、尚未改為 H.264 時測得的。Motion 之外的規則都由它選定：被告知其變更區域而不是整幅編碼時，串流的編碼器的成本取決於移動的部分；在 speed 9 下，移動耗用的 CPU 為 4:2:0、speed 7 的 `WLSV` 的 44–72%，而 speed 7 時為 73–98%，移動期間的畫面最多比 speed 7 低 1.3 dB，大多在半個 dB 以內；第一幅畫面用 PNG 而不是串流，使整份擷取的 CPU 減少 1–15%，終端機的減少十分之九；沒有串流觸及的條帶只傳送其變更的圖塊而不是整條傳送，在變更區域鬆散的地方少傳送 3–15% 的位元組。與 4:2:0、speed 7 的 `WLSV` 相比，在 1080p 和 4K 下：打字耗用其 CPU 的 3%；移動為 44–72%，幾乎所有節省都來自 speed 9，因為 speed 9 的 `WLSV` 耗用的 CPU 與圖塊編碼相當；移動期間的畫面最多好 3 dB，最差低 0.6 dB，終端機的畫面自始至終精確，而 `WLSV` 的為 53 dB；每份擷取都以精確結束，而 `WLSV` 結束於 23.9–52.7 dB，位元組數是 `WLSV` 的 1.2–13 倍：最高 53 Mbit/s，被變更淹沒的桌面在 1080p 和 4K 下分別為 95 和 129。這些比例從 1280×800 到 4K 都成立。它的 `check` 要求編碼器在收斂後不再傳送任何內容（經過 5 s 的靜默和 10 次對頁面已有像素的重繪），並以精確結束；`still` 擷取是為它準備的，不用於任何測量。

## 密度擴充

標準 RFB 沒有表達像素密度的說法。這個擴充是一個虛擬編碼 `0x574c5348`（`WLSH`）和一個雙向的訊息類型 `0xE0`；縮放是 16.16 無號定點數，因此 `0x0002_0000` 為 2.0，`0x0001_8000` 為 1.5。兩則訊息採用同一種配置：

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | 訊息類型，`0xE0` |
| 1 | U8 | 填補 |
| 2 | U16 | 寬度，像素 |
| 4 | U16 | 高度，像素 |
| 6 | U32 | 縮放，16.16 定點 |

- **OutputScale**，伺服器 → 用戶端，十個位元組：類型、填補、以像素計的寬度和高度、縮放。作為對*每一個*列出該虛擬編碼的 `SetEncodings` 的回應傳送——這是宣告支援的唯一方式——並且每當共用輸出的尺寸或縮放改變時（包括另一個輸出成為共用輸出）也會傳送，且在以新尺寸擷取影格之前傳送，因此這份報告會先於調整尺寸的矩形到達。
- **ClientDensity**，用戶端 → 伺服器，十個位元組，採用 OutputScale 的配置：類型、填補、以像素計的寬度和高度、縮放。用戶端每次都同時說明它希望輸出以什麼縮放繪製，*以及*它希望在該縮放下的尺寸，因此一次密度變更就是一次輸出設定：只給出縮放會改變邏輯尺寸，直到隨後再調整一次尺寸，而每個應用程式都會重繪兩次。密度不變時的調整尺寸用 `SetDesktopSize`。只接受列出了該虛擬編碼和 ExtendedDesktopSize 的用戶端發出的宣告，縮放只接受 0.5–8 範圍內的值，尺寸不能為空。伺服器透過 wlr-output-management 在一次設定中設定輸出的模式和縮放，只要求有差異的部分，規則與調整尺寸相同——無頭輸出——並且**對每一個宣告都以一則 OutputScale 回應**：在合成器的 head 縮放改變之後回應，或者在宣告與目前一致、遭到拒絕或無法套用時，立即以輸出的目前狀態回應。合成器接受但沒有改變縮放的設定也會得到回應：`succeeded` 之後接著一次 `wl_display.sync` 往返，若在此之後沒有收到縮放變更，就回報輸出的目前狀態。同一時間只有一個宣告的設定在進行中，它的事件與其他宣告的事件區分開來，因此每個宣告只回應一次：期間到達的宣告會等它塵埃落定，而較新的宣告會取代它，被取代的那個以輸出的目前狀態回應。合成器因為配置在其底下改變而*取消*的設定——新增或移除了一個輸出，用戶端的虛擬顯示器就會這樣——會針對新配置再做一次，僅此一次；第二次取消即視為拒絕。新尺寸以一個 ExtendedDesktopSize 矩形到達用戶端，其原因（reason）是該用戶端，與 SetDesktopSize 的情況一樣。

精確的縮放來自 wlr-output-management 的 head，包括小數縮放；當該協定不存在時，退而使用 `wl_output.scale`，而 wlroots 會將它無條件進位。

## 輸出擴充

一個影格緩衝區就是一個輸出，因此對於有兩個顯示器的桌面，必須詢問要傳送哪一個。標準 RFB 對此同樣沒有說法——`ExtendedDesktopSize` 描述的是*一個*影格緩衝區之內的螢幕——所以這是第二個私有擴充，形式與第一個相同：一個虛擬編碼 `0x574c534f`（`WLSO`），以及一個雙向的訊息類型 `0xE1`。

- **OutputList**，伺服器 → 用戶端：類型、伺服器依要求最多建立的虛擬顯示器數量（[虛擬顯示器](#虛擬顯示器)）、計數、共用輸出的 id，接著是每個輸出一個項目——id、以像素計的寬度和高度、以 16.16 定點數表示的縮放、一個旗標位元組（其第 0 位元表示該輸出是無頭輸出），以及一個帶長度前綴的 UTF-8 名稱。作為對*每一個*列出該虛擬編碼的 `SetEncodings` 的回應傳送——這是宣告支援的唯一方式——並且每當清單、某個項目或共用輸出改變時再次傳送。項目依名稱排序，名稱或模式尚未送達的輸出不在其中。id 是 `wl_output` 全域物件，在輸出存在期間唯一，對用戶端而言是不透明的。名稱是合成器自己的，如 `DP-2` 或 `HEADLESS-1`；無頭旗標標示的是合成器建立的輸出，而不是有人坐在前面的顯示器。

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | 訊息類型，`0xE1` |
| 1 | U8 | 虛擬顯示器：伺服器最多建立的數量，0 表示不建立 |
| 2 | U16 | 計數 |
| 4 | U32 | 共用輸出的 id |

  接著是 `count` 個項目：

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U32 | id |
| 4 | U16 | 寬度，像素 |
| 6 | U16 | 高度，像素 |
| 8 | U32 | 縮放，16.16 定點 |
| 12 | U8 | 旗標——第 0 位元：無頭 |
| 13 | U8 | 名稱長度 |
| 14 | U8[] | 名稱，UTF-8 |

- **SelectOutput**，用戶端 → 伺服器，八個位元組：類型、值為 0 的操作位元組、兩個位元組的填補、要共用的輸出的 id。來自未列出該虛擬編碼的用戶端時忽略，只接受桌面上的用戶端發出的要求，而且無論哪種情況都**以一則 OutputList 回應**，旁邊的顯示器也包括在內：指名合成器已不再擁有的輸出或已經共用的輸出的要求，以清單的目前狀態回應。因此用戶端的選單跟隨的是畫布上實際顯示的內容，而不是被點按的內容。

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | 訊息類型，`0xE1` |
| 1 | U8 | 操作，0 |
| 2 | U8[2] | 填補 |
| 4 | U32 | id |

- **VirtualDisplays**，用戶端 → 伺服器，八個位元組，配置相同，操作位元組為 1，並以計數取代 id：要有這麼多個虛擬顯示器（[虛擬顯示器](#虛擬顯示器)）。依 SelectOutput 的規則受理，並以清單的目前狀態回應；它帶來的結果隨著輸出的出現和消失到達，每次一份清單。

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | 訊息類型，`0xE1` |
| 1 | U8 | 操作，1 |
| 2 | U8[2] | 填補 |
| 4 | U32 | 計數 |

一次切換會停止擷取，把新尺寸以空白狀態帶入影格緩衝區，把虛擬指標指向新輸出——`zwlr_virtual_pointer` 在建立時取得它的輸出，此後再也不會變更，因此會放開用戶端按住的內容並重新建立指標——回報幾何資訊和清單，然後重新開始擷取。在用戶端所要求輸出的一個影格到達之前，不向用戶端傳送任何內容：尺寸不同時，以一個原因為伺服器的 ExtendedDesktopSize 矩形到達用戶端；尺寸相同的輸出則以一次完整重繪到達。一開始共用哪個輸出由設定中的 `output` 決定，否則為第一個。

一個 id 恰好在可列出時才可選擇：輸出的屬性已經送達，它有名稱，而且擷取它會產生像素。同一條規則同時用於兩者，因此用戶端永遠無法指名一個清單不會向它顯示的東西，而仍在送達中的輸出也不可能變成一個沒有尺寸的桌面。

合成器移除了正在共用的輸出時，不會留下一個不指向任何東西的名稱——那樣會停止擷取，卻沒有任何東西能再次啟動它，用戶端會一直看著一幅已經悄無聲息地不再變化的畫面。桌面會在合成器擁有設定的 `output` 時移到它上面，否則移到清單顯示的第一個輸出上，經過的流程與用戶端自己發起切換時相同，因此用戶端會得知新的幾何資訊並收到新輸出的像素。沒有剩下任何輸出時，擷取停止，清單以空清單送出，最後的幾何資訊和最後的畫面保持不變，直到出現一個輸出；第一個送達的輸出會以同樣的方式被採用。

### 虛擬顯示器

RDP 用戶端的顯示器配置和 Mac 的顯示器設定會告訴主機工作階段有多少個顯示器，由主機來建立它們。`VirtualDisplays` 就是這樣的要求：桌面上的用戶端說明它想要多少個虛擬顯示器——一個或兩個，每個桌面檢視（desk）一個，因為一個輸出只顯示在一個桌面檢視上，而桌面檢視有兩個——常駐程式就讓合成器建立無頭輸出，或拔除它們，直到數量相符。只受理桌面上的用戶端的要求；旁邊的顯示器的要求，與它的 `SelectOutput` 一樣，以清單的目前狀態回應。

只有 sway 可以接受這樣的要求。用戶端繫結的 Wayland 協定中沒有任何一個能建立輸出，而 sway 的 IPC 可以：`create_output` 建立一個無頭輸出，`output NAME unplug` 銷毀一個輸出，啟動時建立的輸出也包括在內。常駐程式在 `SWAYSOCK` 中找到通訊端——sway 會為它啟動的所有程式設定這個變數，工作階段的使用者管理器（user manager）也會把它帶給自己的單元——並在啟動時檢查它是否以 sway 的身分回應；沒有任何需要設定的東西。每則 OutputList 都在第二個位元組中說明常駐程式最多建立多少個虛擬顯示器——在 sway 上為兩個，否則為零——因此用戶端在要求之前就已知道；常駐程式無法執行的要求，或要求的數量不是它所建立的數量，都以清單的目前狀態回應，且不改變任何東西。在 labwc 或其他合成器上，輸出就是合成器既有的那些。

一次一步。要求以清單的目前狀態回應，它帶來的結果隨輸出的送達而到達：傳送一個 `create_output`，它的輸出出現並被列出，然後才傳送下一個；拔除同樣要等它的輸出消失。每次出現和消失都是一份單獨的清單，因此在只有一個輸出的工作階段上要求兩個的用戶端，會在隨後的清單中看到第二個輸出，並在 zDesk 閘道中開啟它的分頁。計數的是無頭輸出，無論是誰建立的：以兩個啟動（`WLR_HEADLESS_OUTPUTS=2`）而被要求一個的工作階段會少掉一個，就像有兩個顯示器的 Windows 主機被要求一個時那樣。桌面所在的輸出永遠不會被拔除；其餘的輸出中，最後建立的最先拔除——即編號最大的，因為 wlroots 在合成器的整個生命週期內遞增計數，所以在拔除一個輸出之後建立的輸出是一個新名稱下的新輸出，永遠不會是原來那個回來了——而設定的 `output` 最後拔除。來自 sway 的拒絕會寫入記錄，並結束該要求。

要求屬於用戶端。用戶端離開或被接管時，要求隨之解除，而輸出維持原樣，直到下一個用戶端提出要求，因此視窗在重新連線前後保持在原來的位置，與 Windows 主機上一樣。有頭工作階段的監看程式可以在它的 *free* 指令中拔除剩下的輸出。

### 旁邊的另一個顯示器

一個影格緩衝區就是一個輸出，一個連線就是一個影格緩衝區，因此想同時得到兩個輸出的用戶端要連線兩次。它的第二個連線完成同樣的交握，包括登入，並在 RFB 放置共用旗標的位置傳送 `0xB5` 作為其 ClientInit 位元組。之後它不會佔據桌面：桌面上的用戶端維持不變，而這個連線顯示的是清單中第一個該用戶端不在其上的輸出。其他任何 ClientInit 值都會佔據桌面，包括 RFB 的 `1`。

它是該輸出上的一個完整的 RFB 工作階段：有自己的影格緩衝區和擷取、自己的游標工作階段、針對其輸出建立的虛擬指標、自己的編碼——在它列出 VP9 時，是帶有針對自身連線之品質遊走（walk）的 VP9——以及自己的調整尺寸和密度，遵循它所在輸出的規則。它的 ServerInit 載明的是該輸出的尺寸，因此只有在該輸出歸它所有之後才會傳送。鍵盤屬於座位（seat），來自任一連線的按鍵都會到達合成器目前聚焦的目標；每個連線離開時會放開它按住的鍵，而不會放開另一個連線按住的任何鍵。兩個連線都按住的鍵，在最後一個放開它時才抬起。剪貼簿屬於桌面，只由桌面上的用戶端設定。

它不能做的是選擇。哪個輸出在哪裡，由桌面上的用戶端決定：如果旁邊的連線列出了這個擴充，就會向它傳送一則把它自己的輸出列為共用輸出的 `OutputList`，而它的 `SelectOutput` 會以這份清單的目前狀態回應。在以下情況下它會結束，其通訊端被關閉：

- 桌面上的用戶端離開或被接管——旁邊的顯示器屬於該用戶端，新用戶端開始時沒有旁邊的顯示器；
- 桌面上的用戶端選擇了它正在顯示的輸出，因為一個輸出只在其中一個上；
- 另一個連線要求在旁邊顯示，取代了它的位置；
- 合成器移除了它的輸出。

在桌面上沒有任何人時發出要求的連線，或者沒有該用戶端不在其上的輸出時發出要求的連線，會在 ServerInit 之前被關閉。交握在一個較晚連線的旁邊顯示器已經結束之後才完成的連線也是如此：它不會取代任何人的位置。在目前桌面上的用戶端之前就已連線的連線同樣如此：它是在先前在那裡的用戶端旁邊開啟的。旁邊的顯示器只有一個，所以同時顯示兩個輸出是用戶端所能看到的最多數量。zDesk 閘道在 *All Displays* 下為第二個顯示器的瀏覽器分頁開啟它，並在其上列出像素編碼、游標、尺寸和密度，除此之外別無其他。

只有無頭輸出才會被調整尺寸或縮放，因此切換到實體顯示器後，用戶端的調整尺寸要求會得到 *prohibited* 回應，其密度宣告會以輸出的目前狀態回應——那個顯示器的模式屬於坐在它前面的人。

這個選擇在做出它的用戶端離開後仍然有效：下一個連線會在上一個連線所要求的輸出上開啟，而不是在設定的預設輸出上開啟，直到設定的輸出下次出現或常駐程式重新啟動為止。在一個有兩個顯示器的 sway 工作階段上的測量見 [zDesk 的 `docs/wlshare-outputs.md`](https://github.com/andrewtheguy/zdesk/blob/main/docs/wlshare-outputs.md)（英文），閘道那一半的實作就記錄在那裡。

## 音訊擴充

桌面的聲音，以 FLAC 或 Opus 形式，在像素所用的同一個連線上傳輸。它是私有的——虛擬編碼 `0x574c5346`（`WLSF`）和伺服器訊息類型 `0xE4`——其用戶端是 zDesk 閘道。用哪種編解碼器和格式一樣由用戶端要求，這裡沒有任何設定項目：為 FLAC，除非用戶端在該編碼旁邊列出 `0x574c4f50`（`WLOP`）。用戶端的訊息以及串流的開始和結束借用自 `rfbproto` 登記的 QEMU Audio 擴充，即訊息類型 `255` 子訊息 `1`；QEMU 的虛擬編碼 `-259` 不使用，因為它承諾的是原始樣本，而這裡不傳送任何原始樣本。只列出 `-259` 的用戶端（例如 gtk-vnc）聽不到任何聲音。

- **宣告**，伺服器 → 用戶端：一個編碼為 `WLSF` 的空虛擬矩形，放在單獨的一個 `FramebufferUpdate` 中，在任何像素之前傳送給 `SetEncodings` 列出了它的用戶端。這是宣告支援的唯一方式。

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U16 | x，0 |
| 2 | U16 | y，0 |
| 4 | U16 | 寬度，0 |
| 6 | U16 | 高度，0 |
| 8 | S32 | 編碼，`0x574c5346` |

- **設定格式、啟用、停用**，用戶端 → 伺服器，QEMU 的訊息：取樣格式、聲道數和頻率由用戶端選擇，伺服器把桌面播放的內容轉換成這些參數。格式為 QEMU 的代碼 0–3，即 U8、S8、U16 和 S16；它的 32 位元代碼會被拒絕，因為 FLAC 最多儲存 24 位元。頻率的下限為 8 kHz，即真實音訊使用的最低取樣率，上限為 96 kHz，即桌面自身音訊處理圖執行頻率的兩倍。其他代碼、1 或 2 以外的聲道數、或超出這些範圍的取樣率都是致命錯誤。啟用或停用為四個位元組，設定格式為十個位元組：

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | `255` |
| 1 | U8 | `1` |
| 2 | U16 | 操作：0 啟用，1 停用，2 設定格式 |
| 4 | U8 | 取樣格式（僅設定格式時）：0 U8，1 S8，2 U16，3 S16 |
| 5 | U8 | 聲道數，1 或 2 |
| 6 | U32 | 頻率 |

- **Opus**，用戶端 → 伺服器：虛擬編碼 `WLOP` 與 `WLSF` 一同列出時，要求以 Opus 取代 FLAC 傳送聲音。之所以是虛擬編碼而不是訊息，和 VP9 串流的各項選擇一樣，是為了讓它搭載在要求聲音本身的那個清單上。在串流執行期間改變編解碼器的清單會以新的編解碼器重新啟動該串流，中間經過一次結束和一次開始。
- **設定位元率**，用戶端 → 伺服器，操作 `3`，排在 QEMU 的三個操作之後，是 wlshare 自己的操作：Opus 編碼所用的位元率，單位為每秒位元數，範圍為 6 000 到 510 000，即 libopus 的界限；超出範圍的位元率是致命錯誤。Opus 串流沒有自己的位元率：必須在啟用之前設定過一個，沒有設定就啟用會被拒絕，寫下一行記錄且不傳送開始，和以 Opus 不編碼的頻率啟用時一樣。它可以在串流執行期間再次傳送，執行中的串流會在下一個封包時改用新位元率，不需要重新啟動。FLAC 串流沒有可改變的位元率。

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | `255` |
| 1 | U8 | `1` |
| 2 | U16 | 操作，`3` |
| 4 | U32 | 每秒位元數 |

- **開始和結束**，伺服器 → 用戶端，QEMU 的訊息：

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | `255` |
| 1 | U8 | `1` |
| 2 | U16 | 操作：0 結束，1 開始 |

- **一個訊框**，伺服器 → 用戶端，位於一次開始和一次結束之間——一個 FLAC 訊框，或一個 Opus 封包：

| 位移 | 型別 | 欄位 |
|---|---|---|
| 0 | U8 | 訊息類型，`0xE4` |
| 1 | U8[3] | 填補 |
| 4 | U32 | 訊框的長度 |
| 8 | U8[] | 一個 FLAC 訊框或一個 Opus 封包 |

每個 FLAC 訊框（frame）恰好包含 `frequency / 50` 個取樣訊框（無條件捨去）——二十毫秒，48 kHz 時為 960 個——採用固定區塊大小模式，並且訊框編號為零。FLAC 串流標頭 `STREAMINFO` 從不傳送：其中的一切都已事先約定，因此用戶端根據自己設定的格式建構它，並把該區塊大小同時作為最小值和最大值。訊框會宣告自己的取樣率，除非沒有任何訊框標頭代碼能表示該取樣率（例如 70001 Hz），此時交由那個串流標頭提供。無號格式在編碼前會翻轉每個樣本的最高位元，這把它的範圍對應到同寬度的有號範圍上，靜音對應零；用戶端再把它翻轉回來。解碼後的樣本是交錯的小端序資料，與擷取產生的資料逐位元相同。

FLAC 是無損的，而音樂約佔其 1.5 Mbit/s PCM 速率的一半，語音不到三分之一，靜音的桌面每個訊框只需幾個位元組。訊框長度超過 64 KiB 對用戶端是致命錯誤：可能的最大區塊，即 96 kHz 下 20 ms 的 16 位元立體聲，壓縮前為 7680 位元組。

編碼器只在一個地方被呼叫：[sound-flac](https://github.com/andrewtheguy/sound-flac)，一個獨立的儲存庫，本工作區和 zDesk 閘道（後者用它對 RDP 主機的聲音進行 FLAC 編碼）各自依發行標籤固定其版本。編碼器是該 crate 自己的，以純 Rust 撰寫，針對邊產生邊收聽的聲音調校：不編譯任何 C 程式碼，執行時不下載或載入任何東西，套件也不依賴任何 FLAC 函式庫。它在每個區塊湊滿的那一刻就把該區塊編成一個訊框，不帶任何先前區塊的資訊，因此途中遺失的一個訊框只損失它自己的樣本，不影響之後的任何內容，這就是每個訊框都編號為零的原因。不傳送任何標記或串流標頭：用戶端根據自己設定的格式建構串流標頭。常駐程式的測試用 symphonia 的解碼器讀回每個訊框，該解碼器與它沒有任何共用之處。

以 Opus 傳送時，每個封包同樣是二十毫秒，即 `frequency / 50` 個取樣訊框，並且頻率必須是 Opus 能編碼的頻率——8、12、16、24 或 48 kHz——否則啟用會被拒絕，寫下一行記錄且不傳送開始。取樣格式只說明擷取交給編碼器的是什麼：無號樣本像 FLAC 那樣翻轉，8 位元樣本擴展為十六位元；解碼器還原出什麼是解碼器自己的事。不傳送 `OpusHead`。用戶端根據自己設定的格式建構它，pre-skip 為 312，即編碼器在任何頻率下以 48 kHz 樣本計的前瞻量（lookahead）。封包的解碼依賴於先前的封包，而傳輸中不為任何封包編號，因此用戶端無法察覺少了一個：wlshare 不丟棄任何已編碼的封包，跟不上的用戶端遺失的是從未被編碼的聲音。

這是自身收聽端接受 Opus 的用戶端的選擇：zDesk 閘道把每個封包原樣交給瀏覽器，否則它就得自己解碼 FLAC 再編碼 Opus；它還把瀏覽器連線的速率遊走（walk）得出的位元率作為設定位元率訊息傳送：即 sound-opus 的 `walk`，唯一的一套速率遊走，閘道既為它自己編碼的聲音執行它，也為這裡執行它。編碼器是 libopus，和 FLAC 編碼器一樣只在一個地方被呼叫：[sound-opus](https://github.com/andrewtheguy/sound-opus)，本工作區和閘道（後者用於它自己編碼的聲音）各自依發行標籤固定其版本，因此這裡產生的封包和那裡產生的封包是同一種串流——針對音樂調校，圍繞該位元率的受限可變位元率，以最高複雜度編碼，靜音時每個封包只有幾個位元組。libopus 連結自其 sys crate 下載的預先建置靜態封存檔：不編譯任何 C 程式碼，執行時不載入任何東西，套件也不為此依賴任何東西。常駐程式的測試把這些封包包裝進一個 Ogg 串流，放在用戶端所建構的標頭之後，並用 FFmpeg 自己的 Opus 解碼器解碼，該解碼器與 libopus 沒有任何共用之處，因此測試需要路徑上有 `ffmpeg`。

在任何用戶端收聽期間，主機保持靜音，就像遠端桌面的聲音那樣：桌面播放到**喇叭**中——這是 wlshare 自己的一個輸出裝置（sink）——而不是主機的輸出裝置中。`audio.rs` 在第一個用戶端啟用時建立它，在最後一個用戶端停用或中斷連線時移除它——一個名為 `wlshare-speaker`、描述為 "wlshare remote audio" 的 `support.null-audio-sink`，執行在自己的執行緒上。為此主機上沒有任何變更，沒有輸出裝置被靜音，也沒有寫入任何預設值。喇叭的 `priority.session` 為 100000，而 WirePlumber 會把可用輸出裝置中優先順序最高的設為預設，計算前為使用者設定的那個加上 30000，為在它之前設定過的那些最多加上 20000；硬體輸出裝置本身的優先順序只有幾千出頭，因此喇叭存在期間就是預設裝置，無論它是否是被選中的輸出裝置，所有跟隨預設裝置的串流都會移到它上面。該節點屬於喇叭執行緒的 PipeWire 連線，因此當該執行緒結束或常駐程式終止時，PipeWire 會移除它，WirePlumber 會重新把主機的輸出裝置設為預設，各個串流也隨之移回去。應用程式固定到其自選輸出裝置上的串流會留在那裡，在主機上播放。

`audio.rs` 為每個啟用音訊的用戶端啟動一個 PipeWire 擷取，執行在自己的執行緒上。它是一個 `Stream/Input/Audio` 節點，設定了 `stream.capture.sink = "true"`，`target.object` 為喇叭，這會把它連接到**喇叭的監聽來源**——桌面正在播放的內容，無論是誰在播放——並透過 `node.latency` 要求 20 ms 的緩衝區。處理回呼執行在該執行緒的迴圈上，而不是音訊處理圖的即時執行緒上——刻意不設定 `RT_PROCESS`，因為回呼會編碼、配置記憶體、取得互斥鎖並喚醒一個工作，在資料執行緒上做其中任何一件事都可能使整個音訊處理圖停頓，讓主機上的每個應用程式都出現 xrun。在那裡編碼可以讓編碼不佔用工作階段的工作，後者還要壓縮像素；一個 20 ms 的緩衝區只需零點幾毫秒。編碼器會把不足一個訊框的部分留給下一個緩衝區——PipeWire 在採用所要求的週期大小之前會先遵循它自己的週期大小（quantum），因此工作階段最初的幾個緩衝區往往短於 20 ms，要求 960 個訊框時只有 512 個——並把它完成的每個訊框放入一個深度為十六的佇列。當用戶端跟不上時，FLAC 會丟棄最舊的訊框：每個訊框都可獨立解碼，因此丟棄一個只是一段 20 ms 的空缺，而卡住擷取回呼更糟。Opus 則在佇列滿時不對緩衝區編碼，這樣解碼器拿到的是編碼器產生的每一個封包，兩者在空缺前後保持同步。對執行中的串流傳送設定格式，或傳送改變其編解碼器的清單，會依新的要求重新啟動擷取，期間保持喇叭存在，使兩次擷取之間不會聽到主機的聲音；停用或中斷連線會停止擷取；未湊滿一個訊框的剩餘部分隨之丟棄。

工作階段在每次影格緩衝區更新之前清空該佇列，因此聲音絕不會被擋在一個比它更晚就緒的像素更新之後。無頭工作階段不需要自己的輸出裝置：喇叭就是一個。

每個列出該虛擬編碼的用戶端都會收到宣告：沒有任何設定能關閉聲音，套件相依於它所經由播放的 PipeWire、WirePlumber 和 pipewire-pulse。

## 攝影機擴充

用戶端的攝影機，借給桌面使用。RFB 從用戶端只承載輸入和剪貼簿，也沒有任何已註冊的擴充以這個方向承載視訊，因此這是第三組私有配對，形式與密度擴充和輸出擴充相同：虛擬編碼 `0x574c5343`（`WLSC`）和訊息類型 `0xE2`，雙向使用。每則訊息依序是類型、一個操作、另外兩個位元組，以及該操作攜帶的內容；整數為大端序。

| 方向 | 操作 | 第 2–3 位元組 | 接著 |
| --------- | --------- | --------- | ---- |
| 用戶端 → 伺服器 | 0，插入（plug） | 填充 | `u16` 寬度，`u16` 高度，`u32` 影格率分子，`u32` 分母 |
| 用戶端 → 伺服器 | 1，拔除（unplug） | 填充 | 無 |
| 用戶端 → 伺服器 | 2，樣本（sample） | 旗標（bit 0：關鍵影格），填充 | `u32` 長度，一個 Annex B 存取單元 |
| 伺服器 → 用戶端 | 0，可用（available） | 填充 | 無 |
| 伺服器 → 用戶端 | 1，開始（start） | 填充 | 插入時的格式，排列方式與插入訊息相同 |
| 伺服器 → 用戶端 | 2，停止（stop） | 填充 | 無 |
| 伺服器 → 用戶端 | 3，關鍵影格（keyframe） | 填充 | 無 |

- **可用**是對*每一個*列出該虛擬編碼的 `SetEncodings` 的回應——這是宣告支援的唯一方式。
- **插入**依用戶端將要傳送的 H.264 建立一個攝影機；再次插入會取代它，拔除或用戶端離開會移除它。沒有像素或沒有影格率的插入，以及超過 4 MiB 的樣本，都是致命錯誤：它們代表用戶端對這些欄位的理解不同。像素多於 4096x2304（H.264 level 5.2 的最大影格，36 864 個巨集區塊）的插入會被拒絕並寫入記錄，用戶端也就沒有攝影機：這些欄位最大可達 65535x65535，其畫面不應由任何緩衝區來容納。
- **開始**和**停止**由桌面決定，而不是由用戶端決定：某個應用程式開啟了攝影機，或者最後一個應用程式關閉了它。用戶端在兩者之間傳送樣本，在此之外什麼也不傳送，並且串流從一個關鍵影格開始。
- **關鍵影格**在出現缺口之後必須補上：H.264 無法跨越遺失的單元解碼。

`camera.rs` 把每個插入的攝影機做成一個 PipeWire 節點 `wlshare-camera-<client>`，類別為 `Video/Source`，角色為 `Camera`，描述為「wlshare remote camera」，以免被誤認為主機自己的攝影機。與音訊擷取一樣，它是一個執行 PipeWire 迴圈的獨立執行緒，其回呼在該迴圈上執行，而不在音訊處理圖（graph）的即時執行緒上，因為這些回呼要解碼和複製。它只提供一種格式——插入時的幾何尺寸和影格率下的 I420，即它背後唯一的解碼器所產生的格式——想要其他格式的應用程式要麼自行轉換，要麼不開啟它。該節點是它自己的驅動者（driver）：圖中沒有其他任何東西知道攝影機影格何時到期，因此每解碼出一幅畫面，就觸發一次傳遞它的週期。應用程式連結到它時串流進入 *streaming* 狀態，最後一個應用程式離開時串流退回原狀態，這就是工作階段傳送的開始和停止。

`decode.rs` 是系統的 libavcodec，透過 `ffmpeg-sys-next` 只使用 avcodec 並動態連結，因此套件相依於 Debian 的 `libavcodec`，而不是自帶編解碼器。解碼器以 `LOW_DELAY` 在單一執行緒上執行，因此一個單元一經解碼就成為一幅畫面，而不是晚一個影格。它接受 8 位元的 4:2:0，這涵蓋了 Constrained Baseline 所產生的一切。尺寸與插入時所指定不同的畫面是節點無法提供的，會結束該攝影機：這個情況只回報一次，不再解碼任何內容，向用戶端傳送停止，並拔除該攝影機。

樣本經由一個深度為八的佇列到達攝影機執行緒。發現佇列已滿的樣本會被捨棄，其後的每個樣本也會被捨棄，直到一個關鍵影格為止；每個缺口只向用戶端要求一次關鍵影格——如果關鍵影格本身也沒有找到空位，則再要求一次。解碼器拒絕的單元同樣需要補一個關鍵影格。這裡沒有任何東西在等待用戶端的通訊端：一個不再觀看的桌面，讓用戶端付出的代價不過是一次停止。

2026-09-14 在 PipeWire 1.4.2 的 sway 工作階段上測量：一個用戶端以 15/1 插入 640x480 並傳送 libx264 Constrained Baseline，一個 PipeWire 消費端連結到 `wlshare-camera-1` 並提供 YUY2、I420、NV12 和 BGRx。消費端協商出 15/1 下的 I420 640x480 並進入 *streaming*，wlshare 傳送了開始，消費端取得了完整的畫面——460800 位元組，跨距（stride）640——直到它離開，wlshare 傳送了停止。

應用程式透過 PipeWire 找到該節點，瀏覽器則透過 xdg-desktop-portal 的 Camera 介面找到它，該介面交給瀏覽器一個只顯示角色為 `Camera` 的節點的 PipeWire 遠端（remote）。只有當某個後端實作了 Access（用來詢問使用者）時，portal 才匯出該介面；`xdg-desktop-portal-wlr` 沒有實作，`xdg-desktop-portal-gtk` 實作了。portal 在啟動時尋找它的後端，因此安裝後端之後，必須重新啟動正在執行的 portal。套件為此建議安裝（Recommends）`xdg-desktop-portal` 和 `xdg-desktop-portal-gtk`，而不是相依於它們：常駐程式兩者都不使用，自行開啟 PipeWire 的應用程式也不需要 portal。Chrome 也只有在啟用了 `chrome://flags/#enable-webrtc-pipewire-camera` 時才透過 PipeWire 存取攝影機；沒有這個旗標，或者沒有 portal 的 Camera 介面，它就只查看 `/dev/video*`，列不出任何攝影機。2026-09-13 在 xdg-desktop-portal 1.20.3 的 labwc 工作階段上用 Chrome 153 檢查：只安裝了 `xdg-desktop-portal-wlr` 時，portal 沒有匯出 `org.freedesktop.portal.Camera`；加上 `xdg-desktop-portal-gtk` 並重新啟動 portal 後，它匯出了。

每個列出該虛擬編碼的用戶端都會收到這項宣告：沒有任何設定能關閉攝影機。

## 麥克風擴充

用戶端的麥克風，借給桌面使用——攝影機的孿生兄弟，相當於 RDP 主機從 MS-RDPEAI 得到的東西。QEMU Audio 擴充只單向承載聲音，因此這是第四組私有配對：虛擬編碼 `0x574c534d`（`WLSM`）和訊息類型 `0xE3`，雙向使用，每則訊息依序是類型、一個操作、另外兩個位元組，以及該操作攜帶的內容；整數為大端序。

| 方向 | 操作 | 第 2–3 位元組 | 接著 |
| --------- | --------- | --------- | ---- |
| 用戶端 → 伺服器 | 0，插入（plug） | 填充 | 無 |
| 用戶端 → 伺服器 | 1，拔除（unplug） | 填充 | 無 |
| 用戶端 → 伺服器 | 2，樣本（sample） | 填充 | `u32` 長度，交錯 PCM |
| 伺服器 → 用戶端 | 0，可用（available） | 填充 | 無 |
| 伺服器 → 用戶端 | 1，開始（start） | 填充 | `u16` 聲道數，`u16` 填充，`u32` 頻率 |
| 伺服器 → 用戶端 | 2，停止（stop） | 填充 | 無 |

- **可用**是對*每一個*列出該虛擬編碼的 `SetEncodings` 的回應——這是宣告支援的唯一方式。
- **插入**建立一個麥克風；再次插入會取代它，拔除或用戶端離開會移除它。超過 256 KiB 的樣本是致命錯誤，不是開始所指定格式之完整影格的樣本也是。
- **開始**和**停止**由桌面決定：某個應用程式開始錄音，或者最後一個應用程式停止了錄音。用戶端在兩者之間傳送樣本，在此之外什麼也不傳送。格式由伺服器決定，就像 RDP 中由主機決定一樣：樣本一律是有號 16 位元小端序，開始訊息指定聲道數和取樣率。wlshare 指定 48 kHz 單聲道，這正是 zDesk 閘道的 Opus 解碼出的格式，因此瀏覽器和節點之間沒有任何環節進行重新取樣。沒有關鍵影格：遺失一個樣本就是一瞬間的靜音。

`microphone.rs` 把每個插入的麥克風做成一個 PipeWire 節點 `wlshare-microphone-<client>`，類別為 `Audio/Source`，角色為 `Communication`，描述為「wlshare remote microphone」。與攝影機一樣，它是一個執行 PipeWire 迴圈的獨立執行緒，其回呼在該迴圈上執行而不在音訊處理圖的即時執行緒上，串流進入 *streaming* 和退回原狀態就是工作階段傳送的開始和停止。它不以 `AUTOCONNECT` 連接：來源是由從它錄音的程式連結的，如果自行連結，它會把用戶端的聲音播放到預設的輸出裝置（sink）中。

與攝影機不同，它不是自己的驅動者。音訊已經有一個時脈，即音訊處理圖的時脈，而一個自帶時脈的來源會與錄音應用程式同時播放到的那些輸出裝置產生漂移；因此由音訊處理圖在需要時要求一個週期（quantum），節點則從一個位於用戶端節奏和音訊處理圖節奏之間的抖動緩衝區中回應。該緩衝區在播放前先累積 60 ms——在開始之後，以及每次耗盡之後都如此——因此遲到的樣本表現為串流中的一個缺口，而不是每個週期裡的一聲喀噠聲；它在沒有內容時以靜音回應，並且最多保留 200 ms，捨棄最舊的資料，因此在停滯後突發傳送的用戶端會被即時聽到，而不是延遲聽到。停止會清空它。

2026-09-14 在 PipeWire 1.4.2 的 labwc 工作階段上測量：一個用戶端插入麥克風，並在收到開始後每次傳送 20 ms 的 440 Hz 音調；`pw-record --target wlshare-microphone-1` 以 48 kHz 單聲道錄音三秒，然後再錄兩秒。每次錄音在連結時傳送了開始，在離開時傳送了停止；在最初的半秒之後，兩段錄音都保持著 440 Hz 的音調，沒有任何靜音的 10 ms 區塊，並且拔除之後該節點從圖中消失。

每個列出該虛擬編碼的用戶端都會收到這項宣告：沒有任何設定能關閉麥克風。

## 調整尺寸

`SetDesktopSize` 在共用的輸出上設定一個自訂模式，規則相同。來自未列出 ExtendedDesktopSize 的用戶端的要求完全不予回應。指定的螢幕不是恰好一個、或沒有像素的要求，回應 *invalid layout*（無效配置）。要求目前尺寸的會立即回應 OK；針對無法重新設定的輸出的要求——只有無頭輸出，即名為 `HEADLESS-*` 的輸出，才能重新設定，而且只能透過 wlr-output-management——回應 *prohibited*；合成器拒絕的尺寸回應 *invalid layout*；合成器因配置在其執行期間發生變化而取消的尺寸，會針對新配置再執行一次，與宣告的做法相同；合成器接受的要求，在該尺寸的影格到達時回應，並附帶一個指明本用戶端為原因的 ExtendedDesktopSize 矩形。

## 輸入和剪貼簿

按鍵事件攜帶 X11 keysym。伺服器編譯設定的 XKB 鍵盤對應表，將其上傳到虛擬鍵盤，並在同一份鍵盤對應表中為每個 keysym 尋找能產生它的鍵碼，優先選擇最低的 Shift 層級。輔助鍵狀態用 `xkb_state` 追蹤，並在每次按鍵後傳送。該狀態只接收鍵碼的狀態轉換：xkb 會計算一個輔助鍵被按下的次數，並保持該輔助鍵，直到收到同樣多次的放開。傳給合成器的也是這些，不多不少：用戶端會把按住的鍵重複為多次按下——瀏覽器會像對待任何鍵一樣重複按住的輔助鍵——而這些都不會被轉送，因為 Wayland 用戶端會自行重複，而 Sway 會把每次按下當作一個單獨的按鍵，填滿它容納 32 個已按下按鍵的表，直到下一個按鍵比對不到任何按鍵繫結，而它的放開永遠到達不了應用程式。字元 keysym 指定的是用戶端已經確定了大小寫的字元——zDesk 從不轉送 Caps Lock，而是依瀏覽器解析的結果傳送 `A` 或 `a`——因此在每次按下之前，伺服器會檢查該鍵碼在目前的輔助鍵下會產生什麼，當僅靠該鍵碼會打出另一種大小寫時，就在該鍵前後按下 Shift，或暫時放開按住的 Shift。為某個按鍵而按下的 Shift 會隨該鍵一起彈起，除非用戶端在此之後自己按下了那個 Shift 鍵，這樣它就歸用戶端來放開。指定的是按鍵而不是可列印字元的 keysym 不受此規則約束，會以其鍵碼在用戶端按住的任何輔助鍵下送出：Shift+Tab 到達時是 Shift 然後 `Tab`，該鍵碼的 Shift 層級是 `ISO_Left_Tab`，而為了讓它產生 `Tab` 而放開 Shift，會打出一個普通的 Tab。用戶端離開或被取代時，會放開其按鍵和按鈕；從未完成交握的連線則不釋放任何東西。指標事件以影格緩衝區像素到達，並作為相對於影格緩衝區範圍的絕對位置注入，由虛擬指標對應到共用的輸出上——每個連線一個指標，各自在自己的輸出上，移動座位（seat）唯一的游標。這種繫結是隨指標一起建立的，而 labwc 不會保留它：每當輸出被重新配置，它都會把每個指標對應回其裝置所指名的輸出，而虛擬指標沒有指名任何輸出，於是絕對位置就會橫跨整個配置——一旦有兩個輸出，就會偏移該輸出在配置中的位置。APT 儲存庫建置的 wlroots 帶有一個修補程式，為虛擬指標賦予其輸出的名稱，labwc 會將它對應回該輸出；其他任何 wlroots 都沒有這個修補程式，因此在所有 wlroots 上，每次配置變化之後都會出現的每個 wlr-output-management `done`，都會針對各自的輸出重新建立每個桌面檢視（desk）的指標，新的先建好，舊的再移除，並放開按住的按鈕，但不放開任何按鍵。滾輪「按鈕」變成離散的軸事件，每格一個。

RFB 只能表達一格，因此觸控板上的滑動或手機上的雙指滑動會一頓一頓地捲動。知道伺服器是 wlshare 的用戶端會改為傳送一段距離：私有訊息 `0xE5`，六個位元組——類型、一個位元組的填充，以及以輸出的邏輯像素表示的 S16 水平和垂直距離，向右和向下為正——跟在指明位置的 `PointerEvent` 之後。它沒有虛擬編碼，因為伺服器不需要為它保存任何狀態，也沒有什麼要回應。邏輯像素正是軸事件所用的單位，因此距離在到達時就原樣作為連續軸事件注入：這正是插在這台機器上的觸控板所傳送的，應用程式會把它當作它本身的距離來使用。

剪貼簿透過 Extended Clipboard 以 UTF-8 文字共用，並且只透過這種方式：latin-1 剪下文字在兩個方向上都被捨棄，未列出該擴充的用戶端沒有剪貼簿。每個列出它的 `SetEncodings` 都會得到伺服器的能力（caps）作為回應——文字、所有動作，並且不主動傳送文字，這是該擴充所建議的，因此由用戶端通知變化，再由伺服器要求內容。合成器宣布的選取內容（selection）會在事件迴圈之外讀入一個管道，並保存為共用剪貼簿，同時向用戶端傳送一個通知——或者，對於能力表明不接受通知但接受主動傳送文字的用戶端，直接傳送文字本身，大小以其能力所指明的為限；否則，文字在用戶端要求時傳送，屆時傳送的是當時的共用剪貼簿。被清除或不再是文字的選取內容，會保存為空文字，並以不含任何內容的方式通知。用戶端的通知以一個要求來回應，用戶端提供的文字成為共用剪貼簿，並成為一個佔有該選取內容的資料來源；在該來源屬於我們期間，合成器回頭宣布的這個選取內容會被忽略。無法讀取的剪貼簿訊息會被捨棄，而不是中斷連線。

## 安全性

RFB 3.8，提供設定所對應的類型：設定了 `[pam]` 或 `[password]` 之一時，提供兩種寬度的 RSA-AES，`RA2_256` 在前；兩者都未設定時，只提供 None。傳統的 VncAuth 被刻意排除：它證明的是知道一台機器的秘密，不指明任何人，把密碼截斷為八個字元，並且只保護登入，不保護登入之後的任何內容。沒有設定登入時，工作階段是開放且明文的，因此依設計，監聽位址應是 loopback 位址或 VPN 位址。

RSA-AES 是 RealVNC 的類型，依 `rfbproto` 所記載、並由 TigerVNC、neatvnc 和 zDesk 閘道所使用的方式實作：伺服器的 RSA 金鑰和一個新產生的用戶端金鑰以明文交換，每一方用對方的金鑰封裝一個亂數，兩個亂數為每個方向衍生一把 AES-EAX 金鑰，從此以後，兩個方向上的每個位元組都以 `u16 len || ciphertext || tag` 影格的形式、在計數器 nonce 下傳輸。在這些影格內，每一方用一個雜湊證明它所看到的金鑰，伺服器索取設定的登入方式所需的憑證——對 `[pam]` 是子類型 1，即使用者名稱和密碼；對 `[password]` 是子類型 2，即僅密碼——接著是 RFB 的 SecurityResult、ClientInit 以及之後的一切。無論哪種方式，憑證在傳輸中都只有一種形式：帶長度前綴的使用者名稱，然後是帶長度前綴的密碼；回應子類型 2 的用戶端傳送空的使用者名稱。`crates/wlshare/src/rfb/rsa_aes.rs` 逐位元組地描述了這個交換過程。

伺服器的金鑰是長期使用的——一次性產生到 `rsa_key_file` 中，啟動時以 RealVNC 的八位元組指紋寫入記錄——因為它是用戶端唯一可以釘選（pin）的東西；zDesk 在每次連線時都會記錄它看到的指紋。

檢查憑證的是 `auth.rs`，它是兩種方式之一。`[pam]` 把憑證交給 PAM（`pam.rs`）：在設定的服務下執行 `pam_authenticate` 和 `pam_acct_mgmt`，別無其他。在詢問 PAM 之前，使用者名稱必須是處理程序執行時所用的帳號：wlshare 把輸入注入一個使用者的桌面，另一個帳號的密碼不能開啟它。`[password]` 依設定中的 Argon2 PHC 字串驗證密碼，使用該字串所攜帶的參數，並且完全不指明任何帳號——適用於這樣的主機：其桌面使用者沒有可供 VNC 用戶端使用的系統密碼，或者沒有可供使用它的 PAM 堆疊。該雜湊在啟動時解析，因此無法使用的雜湊是啟動錯誤，而不會在第一個用戶端到來時才意外暴露；`wlshare hash-password` 會印出一個。空密碼在查看雜湊之前就被拒絕。兩種檢查都會阻塞——PAM 堆疊可能會休眠，Argon2 則刻意設計得很慢——因此兩者都在阻塞執行緒上執行。拒絕會在延遲一秒後以 SecurityResult failed 和不加修飾的原因「authentication failed」回應；實際原因寫入記錄。

## 刻意不提供的功能

Tight、TightPNG、Hextile、RRE、CopyRect，以及除私有編碼（VP9 和圖塊的區域串流）之外的所有有損編碼：閘道無論如何都會重新編碼每個圖塊，而 ZRLE 是標準中最好的無損選擇。超過該串流所要求上限的 VP9 品質，無論連線有多少餘裕；對任何未列出 VP9 編碼的用戶端提供的 VP9 編碼。8 位元和 16 位元像素格式以及色彩對應表。移動用戶端的指標：PointerPos 虛擬編碼本可以承載合成器造成的指標跳躍（warp），游標工作階段也確實會回報位置，但只在輸出重繪時才回報。一個影格緩衝區中包含多個輸出——用戶端從中選擇一個，或者再連線一次，在旁邊顯示另一個。同時超過兩個輸出。控制通訊端。伺服器指定的格式之外的麥克風格式。用於用戶端攝影機的 V4L2 攝影機裝置：PipeWire 節點不需要核心模組，也不需要權限，代價是只開啟 `/dev/video*` 的應用程式看不到它。I420 之外的攝影機格式，以及把攝影機畫面縮放到應用程式所要求的尺寸。
