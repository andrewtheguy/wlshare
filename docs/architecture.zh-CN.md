# 架构

[English](architecture.md) | 简体中文 | [繁體中文](architecture.zh-TW.md)

wlshare 通过基于 wlroots 的 Wayland 合成器的公开协议连接到该合成器。它是一个进程，分为两半，两者之间共享一个帧缓冲。

```text
wlroots compositor ── Wayland socket ──▶ compositor thread ──▶ Framebuffer ──▶ session tasks ──▶ TCP
                     screencopy           (calloop)            + damage log     (tokio)          RFB clients
                     image-copy-capture                       + cursor image
                     output-management                        ◀── Commands ◀──
                     virtual keyboard/pointer
                     data-control
```

- `crates/wlshare-proto` 是 wlshare 私有扩展的字节，两个方向都在其中：VP9 和图块编码的封帧（framing）以及客户端为它们列出的内容，密度、输出、音频、摄像头和麦克风扩展，滚动消息，请求“旁边的另一个显示器”的 ClientInit 字节，以及为它们全体命名的协议版本。它是 zDesk 网关所依赖的唯一一个 crate，网关在其 `wlshare` 特性（feature）之后按它的 `proto-v<N>` 标签固定其版本，因此守护进程和网关用同一份代码构建和解析每一个私有字节（[协议版本](#协议版本)）。它只依赖 `thiserror`，不使用任何操作系统 API，每个构建函数都针对一个依据文档中的布局编写的解码器进行测试，并由它的解析器读回。
- `crates/wlshare-vp9` 是 VP9 编码器：固定由一个质量刻度（quality dial）控制的 libvpx，8 位 4:4:4 或 4:2:0，连同位于它前面的各个平面、它的解码器、质量游走（quality walk），以及会话交给它的内容的捕获文件。它不决定任何关于线路的事情，也不使用任何操作系统 API。它当前的预构建归档覆盖 macOS arm64、Linux x86_64 和 aarch64，以及 Windows x86_64 MSVC。参见[VP9 编码](#vp9-编码)。
- `crates/wlshare` 是守护进程。`rfb/` 决定线路上不属于私有扩展的每一个字节：握手、消息的解析与构建、RSA-AES 及其帧、ZRLE 编码器、基于 `wlshare-vp9` 的 VP9 编码器、图块编码器、音频扩展的编码器，以及光标和剪贴板编码。音频扩展的 FLAC 编码器是 `sound-flac` 自己的，用纯 Rust 编写；它的 Opus 编码器则是 `sound-opus` 之下的 libopus，一个预构建的静态归档。它的测试用一个独立的解码器解码每个编码器的输出，用客户端的解析器（`rfb/client.rs`）读回每条服务器消息，并针对一个依据规范编写的客户端运行 RSA-AES 交换。`compositor.rs` 是 Wayland 线程及其命令处理器；`capture.rs`、`cursor.rs`、`outputs.rs`、`input.rs` 和 `clipboard.rs` 是它所使用的各个协议，`sway.rs` 是 sway 的 IPC，用于为客户端的虚拟显示器创建和拔除无头输出；`audio.rs`、`camera.rs` 和 `microphone.rs` 是 PipeWire 一侧，`decode.rs` 是摄像头的 libavcodec 解码器，`h264.rs` 是通过同一个 libavcodec 的 H.264 编码器（使用主机的硬件或 libx264），用于图块画面中的运动区域；`framebuffer.rs` 是共享的像素和变化区域（damage）；`session.rs` 是一个客户端；`auth.rs` 检查 RSA-AES 登录，`pam.rs` 是该检查的系统那一半；`state.rs` 告诉连接到状态套接字的任何一方桌面是否被占用，`watch.rs` 是 `wlshare watch`，即跟随该套接字并为每种状态运行一条命令的进程；`shared.rs` 是在合成器线程和各会话之间传递的内容。它的分配器是 jemalloc，以静态方式链接为 `malloc` 本身，因此它所链接的 C 库也通过它分配内存：glibc 的每线程 arena 会保留每个线程释放的内存，而 zDesk 网关在它们之上的内存占用随每个会话增长。arm64 构建把 jemalloc 的页大小设为 64K，这样可以运行在 arm64 开发板所搭载的 4K、16K 和 64K 内核上。

它的客户端是 zDesk 网关，每位观看者都通过网关访问桌面。

## 同一时间一个会话

桌面属于一个客户端。完成握手的连接会接管桌面，原先占用桌面的客户端的连接会被关闭，守护进程会在日志中记录是哪一个接管了——这与 Windows 远程桌面所做的取舍相同，也是接管发生在握手*之后*的原因：未经认证的连接，或登录被拒绝的连接，永远不会取代正在进行的会话。RFB 的 ClientInit 共享标志不会被解读为任何此类含义；它没有对应的配置，也没有办法与别人一起观看。唯一不接管桌面的连接，是该客户端自己的第二个连接，它为客户端显示另一个输出（[旁边的另一个显示器](#旁边的另一个显示器)）。

合成器线程持有这两者各自的客户端 id，因此规则只是一次比较：来自其他任何一方的输入、尺寸调整和密度都会被丢弃，被取代的会话最后那些仍在途中的消息正是这类消息；输出选择和剪贴板只属于桌面上的客户端，旁边的显示器请求切换时，得到的答复是原样的列表。接管会释放前一个客户端按住的按键和按钮、它待处理的尺寸调整和排队中的声明，并结束它旁边的显示器；捕获从第一次握手开始运行，直到桌面上的客户端离开。

谁在哪里是一个 `watch`，而不是广播事件之一：一个慢到落后于广播的会话会丢失事件，而丢失这一个事件会让两个客户端同时留在桌面上。watch 只保留最新的值，因此被取代的会话会依据它在那里读到的值结束——并且在结束之前一直被忽略。

这个 watch 与整个会话竞争，而不只是与会话中的间隙竞争。会话在一个 `select!` 中让它的消息循环与接管相互竞争，因此一个已停止读取其套接字的客户端，会在阻塞于该套接字的那次写入中途被切断，而不是在它拒绝读取的整个期间一直占着它的捕获和它的任务。客户端 id 只会增加，正是这一点让会话可以通过比较而不是通过确认来作出判断：一个高于自身 id 的活动 id，就是在它之后加入的连接，无论它是否曾在那里看到过自己。这就是对竞争另一端的回答——两个连接的加入被一起排入队列，第二个在第一个尚未订阅之前就已经在桌面上了。

### 状态套接字

`state_socket` 指定一个 Unix 套接字，守护进程在上面告知是否有客户端在桌面上，以便围绕该客户端重新安排会话：可以让 sway 禁用各个显示器，这会把它们的工作区移到向客户端显示的无头输出上，并在客户端离开后重新启用这些显示器。守护进程本身不对会话做任何事，也不运行任何东西：要做什么由合成器和管理员决定，察觉守护进程已经退出也是如此，因为不能指望守护进程自己说出这一点。

无人观看时，无头输出不必存在。配置的 `output` 是一个偏好：没有该名称的输出时，守护进程会共享另一个输出，并在配置的输出每次出现时把桌面移到它上面——仅在它出现时这样做，因此之后指定了另一个输出的客户端会停留在它所要求的位置。客户端在其 ServerInit 之前而不是之后接管桌面，因此在客户端尚未被告知任何尺寸时，套接字就已经报告 `held`；设置了 `output_wait_secs` 时，找不到该名称输出的会话会等待它这么长时间：跟随该套接字的程序会启用它，而客户端最先被告知的尺寸就是该输出的尺寸，而不是某个显示器的尺寸——客户端只会被短暂地显示那个显示器，而且无法更改它的模式。出现的输出在被列出之前就已被共享，因此等待会在该输出被列出的那一刻结束，否则就会超时，客户端从在此期间共享的输出开始。已经存在但未被共享的该名称输出，是客户端选择了另一个输出的结果，任何等待都不会撤销这一选择，因此不会为它等待。桌面在整个过程中都被占用，因此等待还会与客户端关闭其连接、以及之后的连接接管桌面相互竞争，其中任何一种情况都会让会话就此结束。启用它不是守护进程的职责：合成器在报告一个被禁用的显示头（head）时不带位置，因此通过 wlr-output-management 启用它的守护进程就等于在选择把它放在哪里。

连接会被告知桌面当前的状态——`held` 或 `free`，每行一个词——并在每次状态变化时再次被告知；连接自己什么也不说，并且只有守护进程运行所用的账户才能连接。这些词跟随的是桌面，而不是连接：接管是桌面从一个客户端转到另一个客户端，前后都被占用，因此不算变化；旁边的显示器不占用任何东西。每个连接读取的都是各会话所读取的同一个座位（seat）`watch`，因此它被告知的是桌面此刻的状态，无论其间发生了多少次加入和离开。

流的结束是跟随者被告知的第三件事，也是这里使用套接字而不是由守护进程运行命令的原因。守护进程退出时，无论它是停止了、发生了 panic 还是被当场杀死，内核都会关闭这个套接字，因此一个没来得及说出桌面已空闲的守护进程，也同样说出了这一点。有序停止的守护进程会删除该文件，否则由下一个守护进程替换它。仍有应答的套接字属于另一个守护进程：第二个守护进程会拒绝在它上面启动，而不是夺走它的跟随者；守护进程只在该文件仍是它自己创建的那个时才删除它。

### 监视进程

`wlshare watch --held COMMAND --free COMMAND` 就是这个跟随者：一个独立的进程，由会话启动——作为守护进程的用户单元旁边的另一个用户单元，或者通过合成器的 `exec`——带有会话的环境，并读取同一个配置文件来确定套接字的位置。有客户端在桌面上时，它通过 `sh -c` 运行 *held*；在 `--free-after-secs` 时长内都没有客户端在桌面上时，运行 *free*。它无法连接到的守护进程不占用任何东西，套接字每秒重试一次，因此两者的启动顺序无关紧要，重启的是其中哪一个也无关紧要。

它让会话保持在某个状态，而不是报告状态的转换。它运行的第一条命令是对应它启动时桌面状态的那一条，因为它无法知道之前的监视进程留下了什么；在得知该状态之前——守护进程已经告知，或者无法连接——它什么也不运行，因此在有客户端时启动的监视进程永远不会先释放桌面；此后，只有当桌面的状态与上一条命令所表示的不同时，才会运行命令。因此，两条命令都必须能够安全地在已经处于其执行后状态的会话上运行。*free* 之前的等待，使时断时续的链路不会让显示器也跟着时开时关，也使被其单元重启的守护进程不会造成同样的情况：在这段等待之内回来的客户端，无论是通过同一个守护进程还是下一个，都不会让任何一条命令运行。

同一时间只运行一条命令。命令退出时，如果桌面*此刻*的状态与上一条命令所表示的不同，就运行对应此刻状态的命令，因此一个缓慢的 *held* 之后若发生离开，接着会运行 *free*；而一个缓慢的 *held* 之后若发生离开又返回，则什么也不运行。命令运行期间桌面仍受监视，因此等待从客户端离开时开始计时，而不是从命令结束时开始。到 `--timeout-secs` 时仍在运行的命令会被杀死，而不是继续等待它，因为把显示器恢复回来的那条命令正是管理员所依赖的；每条命令都作为自己的进程组运行，被杀死的是整个进程组，因此 shell 启动的东西也会随之结束；任务在其运行期间被丢弃的命令也会受到同样的处理。命令的退出状态会被记入日志，除此之外不改变任何东西。

在上一条命令表示桌面被占用时停止的监视进程——收到 SIGINT 或 SIGTERM 时——会在退出前运行 *free*，不经等待，并在任何仍在运行的命令之后运行。被当场杀死的监视进程会让会话保持原样，而由其单元启动来取代它的监视进程会运行对应桌面当前状态的命令，正是这一点让一切恢复正常。

## 捕获

通过 wlr-screencopy 的 `copy_with_damage` 复制到一个 `wl_shm` 缓冲区，同一时间只有一帧在途，按 `max_fps` 控制节奏。合成器只在有内容变化时才响应仅限变化区域（damage）的复制，因此空闲的桌面不产生任何开销。有变化的矩形在帧缓冲的锁下复制进帧缓冲，代计数器（generation）随之递增，并通过一个 `watch` 唤醒每个会话。

尚未持有任何像素的帧缓冲是例外，而且两方面都是。它请求的是普通的 `copy`，而不是仅限变化区域的复制，因为仅限变化区域的复制只在输出变化时才会得到响应，而一个无人操作的输出可能几分钟都不变——这会让客户端停留在空白屏幕上，或停留在它刚离开的那个输出的最后画面上，直到有人移动鼠标。而且，无论合成器报告哪里变了，返回的帧都会被整个采用：变化区域是相对上一帧衡量的，而刚创建、刚调整尺寸或刚指向另一个输出的帧缓冲没有上一帧，因此只复制报告的矩形会让其余部分保持空白。这两点都取决于 `painted`（帧缓冲在每次调整尺寸时清除它），也取决于帧的尺寸：以帧缓冲尚未具有的尺寸宣告的帧，同样会直接以普通复制请求，因为否则空闲的输出永远不会送来那个让帧缓冲调整尺寸的帧。完全不报告变化区域的帧也会被整个采用。

帧缓冲保存一份 `(generation, rect)` 日志。会话请求自己上次发送的那一代之后的变化区域，得到合并后的并集；落后于日志的会话，或尚未看到任何内容的会话，得到整个帧缓冲。会话在锁下取得所需的像素——对 Raw 和 ZRLE 是复制出来，对图块是复制进编码器自己的图像，对 VP9 是直接转换进流的平面——并在释放锁之后再编码，因此为慢速客户端编码更新永远不会拖住捕获。

### 光标

指针不包含在帧中（`overlay_cursor = 0`）。在无头输出上，这需要 wlroots 0.19 或更新版本，其无头后端把光标放在独立的平面上，而不是把它们永久画进输出。同一个 wlroots 把该平面导出为输出的 ext-image-capture-source 的指针光标，而 `cursor.rs` 在有客户端位于桌面期间，在其上保持一个 ext-image-copy-capture 光标会话：它的帧就是指针下方的应用所选择的光标图像，采用输出的像素，也就是帧缓冲的像素。同一时间总有一帧在途，wlroots 只在光标缓冲区变化（新的形状、新的缩放）时才响应它，因此只是移动的指针不产生任何开销。会话的 `enter` 和 `leave` 表明光标是否位于共享的输出上并且可见；在二者之外没有图像。会话需要一个 `wl_pointer`，而 seat 在从未有过指针之前会拒绝提供，在失去指针时会让它失效，因此会话等待 seat 给出一个指针（wlshare 自己的虚拟指针就是一个），并在每次打开时取一个新的 `wl_pointer`：每次切换输出时都是如此，此时重新指向虚拟指针会让 seat 短暂失去指针。

图像会被裁剪到它实际绘制的像素及其热点，并在每次变化时以单独的一次更新发给每个客户端。每个客户端都必须在每个 `SetEncodings` 中列出标准 Cursor 伪编码（`-239`），因此也就必须在请求帧缓冲像素之前列出；同时列出 Cursor With Alpha（`-314`）的客户端会收到原样的预乘 RGBA，以 Raw 编码，其余客户端则收到按其自身格式的像素，外加一个在 alpha 一半处截断的掩码，这会丢失阴影和抗锯齿边缘。没有图像——隐藏的指针，或位于另一个输出上的指针——就是一个空矩形。RFB 光标的尺寸以帧缓冲像素计，与捕获的图像相同，因此按其自身尺寸发送。客户端把它放在自己已经在指针事件中发送的坐标处。因此光标移动从不等待捕获的帧。

任何把输出锁定为软件光标的操作——另一个客户端以画入光标的方式进行 screencopy，例如 `grim -c`——都会把光标从其平面上移走。此时 wlroots 会把它画进该输出的每一次捕获，包括这一次捕获，而光标会话会报告光标已消失。

### 帧布局

帧缓冲始终是 XRGB8888，行从上到下排列，但捕获的帧未必两者都满足，因此 `FrameLayout` 记录在途的帧有何不同，再由复制把它理顺。这两种差异都来自合成器，而不是来自对它提出的任何要求：y 翻转按帧报告，而提供的唯一一种 shm 格式就是渲染器偏好回读的格式。因此，在 Intel 集成显卡（iGPU）上的合成器交出的红色和蓝色，与用软件合成的合成器顺序相反，而只有这次复制知道这一点：过了它，帧就是 XRGB8888、行从上到下，编码器无需区分任何情况。

`FrameLayout::bytes` 是一种置换，而不是转换——即帧缓冲的四个字节各自位于帧自身像素中的哪个位置——因此它能吸收的是每通道八位的所有 32 位排列顺序，仅此而已：

| 合成器提供的格式           | 内存中     | 来源 |
| ------------------------- | ---------- | ---- |
| `XRGB8888`, `ARGB8888`    | `B G R X`  | pixman, GLES2, Vulkan |
| `XBGR8888`, `ABGR8888`    | `R G B X`  | pixman, GLES2, Vulkan |
| `RGBX8888`, `RGBA8888`    | `X B G R`  | pixman |
| `BGRX8888`, `BGRA8888`    | `X R G B`  | pixman |

这就是 wlroots 的 screencopy 能为桌面提供的全部格式：它的 GLES2 渲染器把 `GL_IMPLEMENTATION_COLOR_READ_FORMAT` 解析为前四种之一，它的 Vulkan 渲染器报告纹理自身的格式，而它的 pixman 渲染器报告输出纹理的格式，这又增加了未使用字节在前的那四种。

#### 刻意不处理的内容

原则上，wlroots 可以报告该表之外的格式，而每一种都需要真正转换为帧缓冲的每通道八位，而不只是重新排列字节：

- **10 位**（`XRGB2101010` 及其七个同类格式）。在深色彩输出上可能遇到；这是此处唯一一个看起来有未来的条目。它需要收窄各通道，而诚实的做法是为它单独设一条路径，而不是扩宽这个置换。
- **紧凑 24 位**（`RGB888`、`BGR888`），每像素三个字节，而 `Framebuffer::apply` 中按四字节计算的行跨距（stride）假定不存在这种情况。
- **16 位**（`RGBA4444` 及其同类格式），只有非常老的 GLES 驱动会报告。
- **`RGB565`、`BGR565`、5551 系列，以及 `XBGR16161616`(`F`)**。wlroots 可以报告这些格式，但 neatvnc 同样没有处理它们的分支，因此与其说这是相对 wayvnc 的缺口，不如说是所有 wlroots VNC 服务器共同的缺口。

在所测量的普通桌面上，Sway 不会给出其中任何一种；而且未处理的格式不会悄无声息：捕获会记录提供了什么、需要的是什么，并会重试，而不是提供一个冻结的画面。

## 发送像素

客户端在已经请求（`FramebufferUpdateRequest`，或通过持续更新一次性请求）且存在变化区域时得到像素更新。每次像素更新是一个由合并后的矩形组成的 `FramebufferUpdate`，最多 32 个矩形，在该客户端自己的 deflate 流上以 ZRLE 编码；对于列表中 ZRLE、VP9 和图块都没有列出的客户端则用 Raw——或者，对于列出 VP9 编码的客户端，是覆盖整个帧缓冲的一个矩形（[见下文](#vp9-编码)），对于列出图块编码的客户端，则是它的 PNG 图块和区域流（[见下文](#图块编码)）。

协商了 Fence 时，每次像素更新都以一个由客户端回显的 fence 结束，下一轮像素等待该回显。随请求一起发送的光标、音频和几何信息通告先于该请求的任何像素，并且没有自己的 fence。同一时间只有一轮像素在途，因此慢速链路永远不会被淹没，其间各帧会在帧缓冲中合并。zDesk 同时协商 ContinuousUpdates 和 Fence。

回显意味着什么由客户端决定；当画面是 VP9 流时，zDesk 会一直压着回显，直到浏览器取走该帧，而不是在帧到达的那一刻就回应（[见下文](#客户端的绘制)）。

尺寸变化先发出，作为单独的一次更新——一个 ExtendedDesktopSize 矩形，其原因说明是谁请求的（服务器、该客户端、另一个客户端），或者对于没有该扩展的客户端是一个 DesktopSize 矩形——整个帧缓冲在下一次更新中跟上。两者都没有协商的客户端无法得到通知，会在其下一次更新时被断开连接，而不是被发送它不知道尺寸的像素。回应该伪编码的 ExtendedDesktopSize 通告也是一次更新，并像其他更新一样等待请求。

## 协议版本

下文的各个私有扩展共用一个版本，两端所说的必须完全相同：没有哪个扩展在新布局旁保留旧布局，因此版本不同的网关和守护进程不会少读一些字节，而是会把对方的字节读错。它是 `wlshare-proto` 中的 `PROTOCOL_VERSION`，也就是该 crate 的主版本号，crate 的版本为 `<N>.0.0`。对这个 crate 的任何改动都是一个新版本。带来新版本的那次发布会把它的提交打上 `proto-v<N>` 标签，zDesk 网关固定的就是这个标签，因此不改动这个 crate 的发布对网关没有任何要求；如果某次发布的 crate 与其版本已有标签中的内容不同，发布工作流会拒绝它。`wlshare --version` 会给出这个版本，守护进程开始监听时也会在日志中写出它。

- **版本**，客户端 → 服务器：伪编码 `0x574c5600`（`WLV` 加一个零字节）加上版本号，在每个列出了任何私有编码的 `SetEncodings` 中都要列出——私有编码即最高两个字节为 `WL` 的任何编码。列出了其中任何一个却没有版本，或者列出了两个版本的列表，都是致命错误。
- **应答**，服务器 → 客户端：第一个带有版本的列表会得到应答，应答先于守护进程发送的任何其他内容，也不等待请求，是一个只含一个空矩形的更新，矩形的编码给出守护进程自己的版本。如果客户端的版本与之不同，守护进程在发出应答后关闭连接，而客户端已从应答中得知守护进程的版本，会把两者都指明。之后的列表带有同一个版本，不会再次得到应答。

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | `0`，FramebufferUpdate |
| 1 | U8 | 填充 |
| 2 | U16 | 矩形数，`1` |
| 4 | U16 | x，0 |
| 6 | U16 | y，0 |
| 8 | U16 | 宽度，0 |
| 10 | U16 | 高度，0 |
| 12 | S32 | 编码，`0x574c5600` + 版本 |

zDesk 把应答当作它的列表之后的第一条消息来读取；如果某个 `wlshare` 目标的服务器先发送了别的内容，zDesk 就拒绝它：不为扩展标注版本的服务器，不是它能对其使用这些扩展的服务器。

## VP9 编码

一种私有编码 `WLSV`（`0x574c5356`），为 zDesk 网关而设：把整个桌面作为一路 VP9 流，供宁愿要会动的画面、也不要精确画面的客户端使用。在帧缓冲不超过其视频上限时，zDesk 会为设置了 `subtype = "wlshare"` 的目标上的每个浏览器列出它，并把每一帧原样传给浏览器，因为这正是 zDesk 否则要从 ZRLE 的像素编码出来的流——采用目标自己的刻度（dial）和浏览器的色度，二者由它在该编码旁边指明，见下文。不列出它的客户端不受影响。

列出它并在旁边附带一个质量（见下文）的客户端会得到它，而不是标准的像素编码，无论它在列表中的什么位置；列出它却不附带质量则是致命错误。此后每次像素更新是一个覆盖整个帧缓冲的矩形，其主体是该帧编码时的刻度、一个长度字和一个 VP9 帧：

```text
u8 quality   the 1–100 dial the frame was coded at
u32 length   the frame's bytes
u8[length]   one VP9 frame
```

质量是编码该帧时游走（walk）所处的刻度，对收敛（settle）的帧则是上限（二者均见下文）：网关不解码就转发这些帧，因此这是它无法自行从帧中读出的唯一信息，也是它在会话结束时记录下来、用于判断慢速链路的依据。连续的矩形是同一路流，每一帧都参照之前的帧编码，因此客户端用一个解码器按顺序解码全部帧。编码由 libvpx 完成，按 `wlshare-vp9` 的设置：量化器固定在刻度上，没有前瞻延迟（lag），不丢帧，不产生未经请求的关键帧，颜色在码流中声明。`crates/wlshare/src/rfb/vp9.rs` 负责帧缓冲像素的输入，以及按矩形的封帧输出帧，而封帧属于 `wlshare-proto` 的 `vp9` 模块——质量字节、长度字及其上限。帧所包含的内容是固定的：

- **8 位 4:4:4、VP9 profile 1，除非列表要求 4:2:0。** 每个像素一个颜色样本：4:2:0 给桌面带来的损失是文字的颜色——一像素宽的彩色笔画与三个背景像素共用同一个样本——而任何量化器都无法把它找回来。但没有哪个浏览器的硬件 VP9 解码器支持 profile 1，而没有软件解码器的浏览器，即 iOS 和 iPadOS 上的 Safari，会拒绝它，因此对于这样的浏览器，网关会列出 `WLSS`（见下文），流就是 4:2:0、VP9 profile 0，所有解码器都支持。
- **有限范围（studio swing）的 BT.601**，从帧缓冲的 `B, G, R, X` 转换而来，并在关键帧头中声明，因此解码器会用同一个矩阵转换回来。客户端的像素格式不适用。
- **随链路变化的量化器和帧率。** 1–100 的刻度（越大越精细）映射到 VP9 的量化器 63 到 8，与 zDesk 的刻度一样；码率控制固定在刻度所在的位置，没有比特率，没有自适应量化，也不丢帧。会话从客户端列表所指定的上限（`WLQ`，见下文）开始，从不超过它，并在客户端落后时向下游走，直到下限 20——即 `wlshare-vp9` 的 `walk`。下限是常量而不是配置项，所有自适应流都是如此：WebRTC 的质量缩放器（quality scaler）在它自己的阈值处从量化器转为调整分辨率和帧率，而这里的游走则转为调整帧率，下文的收敛会在上限处让静止的桌面重新变清晰。一帧的排队时间是它的 fence 往返时间——在客户端拿到该帧后应答，对 zDesk 来说就是浏览器取走该帧之后（[见下文](#客户端的绘制)）——减去最近一分钟中最短的往返时间，这样距离就不会被当作排队；关键帧计入这个最小值，但不作为判定。没有 Fence 时——以及对于固定的刻度，无论有没有 fence——排队时间就是写入该帧阻塞了多久，其中 20 ms 即算落后。最近四帧中有两帧落后（排队 60 ms 或更多）就降低质量：降十个点，150 ms 时降二十个点，400 ms 时降三十个点；一旦刻度已在下限，就改为把捕获的帧间隔加倍，在默认的 `max_fps` 下从 33 ms 直到 133 ms，而在 400 ms 时两者同时进行。帧间隔在下一帧到期时读取，因此上一帧的 fence 带来的一步就会决定该帧的节奏。光标、音频通告和尺寸发生变化的桌面从不等待被放慢的帧的轮次。每秒最多走一步（降低之后延迟在 150 ms 或以上时，半秒后即可再走一步，这样的一步只降低质量而不动帧率）；当延迟仍在以每秒为上一步时数值的五分之一的速度下降——即上一步留下的队列正在排空——时，不再走下一步，因为那一步已经足够；关键帧之后，判定要等两秒，因为它后面的帧要排在它的传输之后。一秒的畅通帧（30 ms 或更少），且至少四帧，会先恢复帧率，然后恢复质量，只要链路持续接受，步长就从三开始加倍直到二十四，并且在链路接受了一步之后，只要这些帧的排队都不超过 15 ms，半秒的畅通帧就足够；链路在四秒内拒绝的一步，会在 300 ms 后退回到它出发时的质量，并且在十五秒内，游走最多只回升到朝被拒绝的质量的一半处。刻度在运行中的编码器上移动，因此移动不需要关键帧，而以新尺寸创建的编码器从刻度当前所在之处开始。被放慢的会话自己为帧控制节奏；未被放慢的会话则由捕获及其唯一一个在途的 fence 控制节奏。
- **客户端在它旁边列出的内容决定流的形态**，就像 Tight 的质量等级搭载在 `SetEncodings` 上一样——用伪编码而不是消息，因为不是 wlshare 的服务器会忽略它不认识的编码，而它不认识的消息会结束连接，也因为它们搭载在指定该编码的列表上，所以第一帧就已经是所请求的样子。`0x574c5100` 加上 1–100 的质量（`WLQ` 及其值）指定游走永不超过的上限；`WLSD`（`0x574c5344`）把刻度固定在那里，此时游走对 fence 中的信息置之不理——只有写入阻塞的帧会使它移动，无论有没有 fence——收敛也只针对这种帧所造成的粗糙；`WLSS`（`0x574c5353`，subsampled）请求 4:2:0 的流。网关根据目标的配置项列出前两者，因此 `video_quality` 和 `render_adaptive` 在透传的流上与在网关自己编码的流上含义相同，并根据浏览器能解码什么列出 `WLSS`。在每次 `SetEncodings` 时读取：新的上限会移动运行中编码器的刻度，并以该刻度把画面发送一次，就像收敛那样，无论桌面是否变化；而新的游走设置只移动刻度。二者都不需要关键帧；新的色度则是一路新流，从关键帧开始。指定 VP9 却不带质量的列表是致命错误，就像格式错误的消息一样：wlshare 没有自己的质量，网关在每个列表上都会在该编码旁边指定一个，而不是网关的客户端——普通的 `vnc` 目标通过 RFB 基线读取 wlshare——根本不会列出 VP9。没有 `WLSD` 时流会游走，没有 `WLSS` 时流为 4:4:4。没有前瞻延迟，并采用带行级和 tile 级并行的多线程：编码器使用机器的核心数减二个线程，最多八个，因为一次编码是另一端的人要等待的突发任务。流的结构依照画面的宽度和这些线程而定，是为了解码器：宽度小于 1440 时一个 tile 列，1440 起两个，2048 起四个，5760 起八个，永远不超过线程数；四个或更多 tile 列的流在编码时不使用环路滤波器。编码画面一半或以上的帧间帧——滚动的页面、播放中的视频——以 libvpx 的 speed 9（其实时 VP9 最快的速度）搜索，其他每一帧，包括关键帧和收敛帧，都以 speed 7 编码，速度在运行中的编码器上切换，不需要关键帧：speed 9 为滚动或视频省下大量处理器时间，只多出少量字节，而拖动或揭开的窗口只占画面的四分之一到三分之一，在 speed 9 下会多发送很多字节，所以保持 speed 7（[测量](vp9-performance.md#done-motion-at-speed-9)，英文）。从帧缓冲像素到平面的转换由 `yuv` crate 完成，它在运行时选择 AVX2 或 NEON 路径：守护进程按目标平台的基线构建，对处理器没有更多要求。
- **静止的桌面会以上限变清晰，而游走保持原位。** 游走只在有帧发出时运行。通常只有在内容变化时才会发出帧，因此一个在链路刚把画面变粗糙后就停下来的桌面，会一直保持那个画面，直到它再次变化。一旦一个低于上限编码的帧已送达——其 fence 已得到应答，或在没有 Fence 时其写入已完成——且此后 500 ms 内没有发送任何内容，未变化的画面就会在客户端请求的下一次更新时再次发出，作为一个处于上限的帧间帧（inter frame），整体编码而不是按其变化区域编码：客户端所持有的粗糙块的残差以更精细的量化器编码，客户端已精确持有的块保持原样，因此它无需关键帧就能让整个桌面变清晰（`a_settle_sharpens_the_picture_and_leaves_the_dial` 保证了这一点）。编码器只为这一帧重新调整，之后恢复到游走的质量，而且这一帧不作为判定：屏幕停止变化并不说明链路的任何情况，而经测量，每一阵运动都从上限开始游走，会让画面在每一阵运动中都落后半秒。静止之前的畅通帧也不跨越静止期：游走的连续畅通帧计数在收敛时重新开始，因此一阵运动要凭它自己的帧赢回向上的一步，而不是在第一帧就拿到一步。以上限整体发出的帧不欠任何东西，在它之后变静止的桌面什么也不发送；以上限编码的变化区域帧只让它所编码的块变清晰，因此在它之前被变粗糙的画面仍欠一次收敛。
- **只在解码器需要时才发送关键帧**：列出该编码后的第一帧、新尺寸或新色度下的第一帧（这两种情况都会重新创建编码器），以及回应非增量请求的帧。没有周期性关键帧；在 TCP 上不会丢失任何内容。

只要有任何变化区域，就会发送一次普通的 VP9 更新；非增量请求、质量上限的变化以及上文所述的收敛也可能需要发送一次。帧是整个画面，而未变化的部分在字节和时间上都几乎不花费任何代价：会话把客户端上一帧以来的变化区域交给编码器，编码器转换变化区域中的矩形并编码它们所触及的 16×16 块，其他每个块都保持客户端所持有的样子，放在一个解码器不再读取其中任何内容的段（segment）中。转换直接从帧缓冲出发，在其锁下进入编码器的平面，锁释放之后再从这些平面编码帧：中间不会在任何地方复制像素，除非这些帧正在被捕获。编码器的测量结果就放在为其测量的常量旁边，位于 `crates/wlshare-vp9` 中。关键帧、编码器的第一帧、收敛帧，以及变化区域日志已无法追溯到的客户端，都整体编码。编码在会话的工作线程上运行，该线程被告知这是阻塞操作，而 fence 像对标准像素更新一样保持只有一帧在途。去掉该编码的 `SetEncodings` 会以它所选择的标准编码（列出 ZRLE 时为 ZRLE，否则为 Raw）回应整个帧缓冲，因为客户端持有的是有损画面。

libvpx 以 `wlshare-vp9` 链接它的方式存在于守护进程中，来自 `libvpx-prebuilt` 的静态归档，它也是 VP9 编码的测试读回每一帧所用的解码器（`wlshare_vp9::Decoder`）。如果 libvpx 没有产出帧，就不发送任何内容：变化区域保持未被看到，关键帧也仍然欠着，留给下一次变化带来的帧。

### 捕获交给编码器的内容

以 `--capture-frames DIR` 启动的守护进程会为每个会话精确写下其 VP9 编码器所收到的内容：每帧的时间、尺寸、当时的刻度（dial）、是否请求了关键帧、变化区域（damage）矩形或没有矩形这一事实，以及这些矩形所跨越的各行，按帧缓冲中保存的样子，即 `B, G, R, X`。该文件是 `wlshare-vp9` 的 `capture` 模块的捕获文件，其布局在那里有完整说明：它是本仓库自己的格式，在这里读写，与编解码器毫无关系，因为一份捕获就是编码器面前的像素，无论那是哪个编码器。每个会话一个 `<unix millis>-client<id>.wlcap`，在把像素交给编码器的那唯一一处调用中写入，因此涵盖该会话在调整尺寸过程中创建的每一个编码器。途中没有任何有损环节，这正是关键所在：编码器是在桌面实际显示的画面及其附带的矩形上重新运行，而不是在某个流的解码结果上运行。捕获只针对 4:4:4 流，这是其每一种用途所关心的色度，也是其工具回放它时所用的色度（`examples/vp9cap.rs`）：客户端请求 4:2:0（`WLSS`）的会话，在此期间不写入任何帧。这些文件未经压缩且很大——一个 4K 整帧就是 33 MB——之后再用 `zstd` 压缩。

该标志只存在于命令行上，配置中没有对应的键，这是有意为之：捕获会把每个会话的每一帧写入磁盘且不删除任何内容，因此只有在有人亲手输入它的地方才会开启，用于一次他们亲手启动并会亲手停止的运行。打包的单元不会指定它，被指定了它的单元会在启动时被拒绝：systemd 会在 `SYSTEMD_EXEC_PID` 中说明它启动的是哪个进程，在其中发现自己的 id 且设置了该标志的守护进程不会运行。在 systemd 启动的会话中从终端启动的守护进程具有另一个 id，不会被当作单元启动的守护进程。

`docker/capture/` 无需人工即可完成这一切：一个运行在 wlroots 0.19 上的无头 sway；守护进程由容器的脚本带着该标志启动，在回环（loopback）上不做身份验证；以及 `vp9-sink`（`crates/wlshare/examples/`），即容器中唯一的客户端，它以一个质量列出 VP9，并列出 Fence、ContinuousUpdates、ExtendedDesktopSize 和 Cursor，设置桌面尺寸，回显 fence，丢弃帧，按提示在一段时间内延迟读取，并输入场景要它输入的内容，使按键像人的按键一样经由守护进程到达桌面。内容是 `docker/capture/scenarios/`，每个场景一个脚本，可在任何 sway 桌面上播放，也可以在守护进程正在捕获的桌面上手动运行：安静的场景有：在终端中输入并滚动、一个放着不动的页面，以及一个位于页面上方、被移到一旁并关闭的窗口；繁忙的场景有：被随机彩色行淹没的终端（`flood.sh`，以及 `busy-lines.sh`，它会淹没运行它的任何终端）、滚动的页面、拖动的窗口，以及一段全屏并裁剪至填满屏幕的视频，从而每个像素都属于视频：即 `--video` 交给容器的文件，video 和 walk 两个场景需要它。`run.sh` 在每个尺寸下播放它们，每个场景外面都包着一个会话——第一个场景把尺寸调整到该尺寸，video 场景中途请求一个关键帧，而 walk 场景是在 sink 延迟读取时播放的视频，于是 fence 回来得晚，刻度下降，然后回升，然后视频在当前位置暂停，以便对它的一帧进行收敛（settle）——每个场景都有自己的会话，因此有自己的文件。脚本会在捕获它的会话连接之前打开窗口并声明已就绪，并在该会话收到第一帧后开始播放，这样每份捕获都以场景的窗口已绘制好开始，而不是以窗口打开期间的空白桌面开始：窗口在该尺寸下的另一个专属会话中打开，该会话随后结束、其捕获被丢弃，因为守护进程的帧缓冲只从客户端获得尺寸，并且只在有客户端连接时保留其画面，而这个画面就是新连接的客户端首先收到的内容。flood 场景的会话会超过其时长继续运行，直到满一百五十帧：它的每一帧都是全新的整幅画面，是编码最慢的情况，大桌面每秒只能得到其中几帧。失败的场景，或其 sink 失败的场景，不会留下捕获并会使整次运行失败，因此以某个场景命名的文件绝不会是别的东西。`scripts/capture-frames.sh` 构建并运行它，只针对工作区自己的编码器，别无其他。zDesk 网关并未为此加入捕获功能：它在 Standard 模式下的 Mac 和通过 RDP 的 Windows 交给它的都是同类桌面的精确像素，因此在它们的尺寸下的 wlshare 捕获可以代表它们。

要观看一份捕获，`scripts/capture-mp4.sh` 会为它制作一个 MP4：`vp9cap frames` 以恒定帧率写出捕获的画面，保留其自身的时间，送入 ffmpeg 的 libx264，因此不经过 VP9 编码器，并且在任何能构建 `vp9cap` 的地方都能运行，而不只是在守护进程旁边。

捕获是源头，用来测试解码器和为其计时的流都由它们制作而成：`vp9cap`（`crates/wlshare-vp9/examples/`）把一份捕获再次送入编码器，每帧带着它的矩形，以它当初编码时的刻度，在请求了关键帧的地方生成关键帧。因此，游走（walk）的各步及其收敛都在它生成的流中，无需重放慢速链路；而对桌面编码方式的更改——无论是在 `wlshare-vp9` 中，还是升级其 libvpx——只需在已保存的捕获上运行一次 `scripts/vp9-samples.sh`，而不必重放桌面。该脚本写出 vp9-wasm 的基准测试所读取的内容：对每个尺寸，一个安静样本和一个繁忙样本，各 120 帧，分别取终端捕获的开头和视频捕获中报告变化像素最多的那一串连续帧，每个都以当时画面的关键帧开头，并按流自身的关键帧头部所述（而不是按编码器的规则）命名为 `<scenario>-<WxH>-<tile columns>col-<lf|nolf>`。使用 `--streams` 时，它还会完整编码每份捕获，捕获在某个尺寸下持续三十帧或以上的每一段各生成一个流，以 IVF 格式输出，旁边附一个 CSV，记录每帧的时间、字节数、是否关键帧和刻度。每个流都会得到 libvpx 解码出的每一帧的 MD5（由 ffmpeg 生成），若 ffmpeg 自己的 VP9 解码器（与 libvpx 不共享任何代码）对某个流解出不同的画面，运行就在该流处停止。那里的编码器无论机器如何都使用四个线程，因为一个宽度被编码成的图块列数受线程数限制，而一个样本无论在哪里生成都必须是同一个流。编码器在捕获本身上测量，快速运行时则在捕获的部分上测量：`scripts/capture-samples.sh` 用 `vp9cap trim --frames` 把每份捕获以其原名裁剪为 120 帧，选取方式与样本相同，即安静场景取开头、繁忙场景取最繁忙的部分，裁剪后的第一帧是当时的整幅画面，并请求关键帧；`walk` 则完整复制，因为它的刻度在整个过程中下降、回升并收敛；`mixed` 也完整复制，它是在桌前的几分钟，裁剪只会留下最繁忙的部分，即全屏播放的视频。

游走也以同样的方式在捕获上测量，无需对链路整形：`walk-sim`（`crates/wlshare-vp9/examples/`）像会话那样把一份或几份捕获送入编码器和 `QualityWalk`，一帧在途，送往一个 zDesk 把流转给浏览器的模型——帧一到就交给浏览器的链路，在它之前交出的帧都已绘制时立即回应它的 fence，否则等最早的那一帧欠过链路的 ping 往返时间后再回应，最多 500 ms——链路的速率（可在给定时刻变化）和往返时间由参数给出。它报告桌面的每次变化过了多久才被绘制、每秒帧数、运动编码时的刻度和所用的链路，加上 `--timeline` 时还有每一帧，均以 JSON 行输出，每行一个 JSON 对象。时间是模型的时间，因此一次运行只需几秒；`--encode` 固定一次编码所用的时间，以便两种游走在相同的帧上比较。它测得的结果见 [VP9 performance](vp9-performance.md#the-walk-on-a-slow-link)（英文）。

### 客户端的绘制

上面的游走只有在它所计时的 fence 可信时才可信，而一帧到达时立即回显的 fence，计时的只是到网关的链路，别无其他。一个无法以桌面绘制的速度接收帧的浏览器，会被读成一个健康的客户端：服务器会继续以该刻度编码，而用户看到的是一个滞后的画面，所有测量却都说链路畅通。

因此，zDesk 会按浏览器那一侧的链路对之前各帧的处理情况来扣住每次回显，这由浏览器在其绘制器完成绘制后发送的 `paintAck` 测量。这样，一帧到达屏幕所经过的路径就处在游走所读取的往返时间之内；并且由于服务器在回显到达之前不发送任何内容，浏览器原本只会在未被看到的情况下覆盖掉的帧根本不会被编码。不在绘制的浏览器不能有办法让桌面停下，因此任何回显都不会被扣住超过 500 ms——即 zDesk 的 `FENCE_HOLD_LIMIT`，其绘制窗口的宽限期。

## 图块编码

`WLSV` 之外的第二种私有画面编码 `WLST`（`0x574c5354`），供 zDesk 网关在带宽充裕的链路上使用：桌面静止之处为精确的 PNG 图块，每个运动区域各有一路自己的视频流，即 H.264——主机的硬件，或 libx264。它是网关按目标做出的选择，而不是替代：`WLSV`，即覆盖整个桌面、随链路游走的一路流，仍是慢速链路上的画面，在那里以更少字节传输的有损流才是链路承受得起的。本编码花费链路拥有的字节，在固定其刻度的列表上换来更少的编码器时间和最终精确的画面；而在允许其刻度游走的列表上，它会像 `WLSV` 一样跟随链路：每个图块，无论静止还是运动，都是一个 RemoteFX Progressive 图块，没有流，也不欠任何精确版本，因此比起最终精确的画面更想要游走的客户端同样能得到满足。它就是 zDesk 的 Motion，那个网关之所以弃用它，是因为它夹在原生协议和页面之间——在 RDP 上，它解码主机已编码的内容只为再编码一次，在 Mac 上它叠加在 ZRLE 之上——而它属于这里，在这里合成器的像素和变化区域只编码一次。`crates/wlshare/src/rfb/tiles.rs` 是编码器，`wlshare-proto` 的 `tiles` 模块是其封帧格式。

列出它并在旁边附带质量（`WLQ` 及其值，与 VP9 相同）、并在希望刻度固定而非游走时附带 `WLSD`（与 VP9 的列表表达方式相同）的客户端，无论它在列表中的什么位置，都会得到它，而不是标准像素编码；游走的列表上每个图块都是渐进式的（见下文）。不带质量列出它是致命错误，同时列出它和 `WLSV` 的列表也是：它们是两种画面，客户端只想要其中一种。此后，一次像素更新就是任意数量的该编码矩形，按顺序绘制，每个都是桌面的一个矩形，其主体以一个种类开头：

```text
u8 kind
0 PNG     u32 length | u8[length]                          a PNG of exactly the rectangle's pixels
1 START   u8 stream | u32 length | u8[length]              a region stream's first frame
2 FRAME   u8 stream | u32 length | u8[length]              the stream's next frame
3 END     u8 stream                                        the stream is over
4 COPY    u16 x | u16 y                                    what the client holds at (x, y), drawn here
5 CACHED  u16 slot                                         the tile kept in slot N, drawn here
6 STORE   u16 slot                                         what the client holds here, kept in slot N
7 PROGRESSIVE u32 length | u8[length]                      a RemoteFX Progressive tile block of the rectangle's tile
```

PNG 就是桌面在该处的精确像素，8 位 RGB 或其调色板形式，不依赖于它之前的任何内容；它是固定刻度的列表上的每个静止部分，不在其他列表上发送。START 在其 id 上、在其矩形范围内开始一个流，内容是一个该尺寸（边长向上取整为偶数）的 H.264 关键帧，客户端从其左上角裁剪到该矩形；该 id 上的每个 FRAME 是该流在同一矩形上的下一帧；END 表示流已结束，其最后的画面一直保留，直到有内容绘制在其上。COPY 在其矩形处绘制客户端在 `(x, y)` 处持有的同样大小的内容，即它之前的矩形留下的样子：一次滚动或一个被移动的窗口，像 RFB 的 CopyRect 那样绘制，两者可以重叠，如同一幅画面画到自身上，其来源先被整块读出。STORE 把客户端在其矩形处持有的内容——从 (0,0) 起网格上的一个 64×64 图块——存入客户端 4096 个槽位的缓存中的第 N 个，覆盖该槽位原有的内容；CACHED 在其矩形处绘制第 N 个槽位保存的图块，大小相同；从没有存入过内容的槽位绘制是致命错误。PROGRESSIVE 是该矩形的图块——网格上的一个 64×64 图块，被桌面边缘裁切——作为 RemoteFX Progressive 的一个图块块（[MS-RDPEGFX] 2.2.4.2.1.5）：某个阶段的首次传递，取代客户端持有的该图块，或作为与之的差值；或一次升级，即上一阶段保留未发的那些位。编码它所用的表是协议规定的，从不发送——`wlshare-proto` 的 `progressive` 模块保存这些表，以及标准解码器从中读取一个块的流——客户端按顺序解码每个块，并在块与块之间保留每个图块的系数。除 COPY、CACHED 和 STORE 之外，它是游走的列表上的每个矩形。流的矩形上的 PNG 只会出现在其 END 之后，因此按顺序把每个矩形绘制到它所说的位置，得到的就是画面。

- **静止的部分是静止图像。** 桌面从 (0,0) 开始划分为 64×64 的图块。自客户端上次更新以来的变化区域在锁内从帧缓冲复制到编码器保留的一幅画面中，并在那里与客户端持有的内容逐图块比较，因此合成器重绘其显示的内容时不会发送任何东西。发生了变化且没有流承载的图块以静止图像发送——在固定刻度的列表上为 PNG，在游走的列表上每个图块都是渐进式的（见下文）——一行中连续的一串，在图块行的交界处切成最高 64 行的条带，合为一幅图像，使变化区域完整覆盖的图块整个落在一幅静止图像中。重新开始的画面——编码新被列出、新的尺寸、非增量请求——立即以同样方式整幅发送，而 Motion 会先以流发送它，之后反正还要把每个图块以静止图像发送：在带宽充裕的链路上，那个流是白费功夫。PNG 采用网关的图块编码器：像素最多 256 种颜色时用不加过滤的调色板，否则用 RGB 并为每行选择过滤方式，采用 `png` 的快速压缩。
- **移动过的部分是复制。** 当一次读取改变了足够多既没有流承载、也没有在原地持续变化的图块——4 个，其中没有一个在最近 8 个十分之一秒中有 2 个发生变化；除非在这 8 个十分之一秒内找到过复制：那时持续变化的可能是查找漏掉的滚动，若把它们排除在外，两次漏找就会让这次滚动余下的部分再也找不到复制——就在旧画面中查找新画面中 16 像素长的连续片段，最多 64 个，且都不是单一颜色：在变化区域内及这些图块 512 像素范围内，沿旧画面的每第四行，用滚动哈希查找；这样什么也没找到时，再沿其余各行查找。在多于 32 个位置找到的片段——位于纹理或带一条边的纯色填充中——说明不了什么，会被丢弃，而一行文字中的片段虽然会在页面的许多行上找到，仍然计入。找到某个片段的每个偏移，都会用每一个片段核对一遍，即把片段的 16 个像素与旧画面在该处的像素比较：位于扫描跳过的行上的片段在任何偏移处都找不到，而快速滚动时其余片段大多落在新露出的行上，仅靠扫描，剩下能互相印证的不到两个。两个片段一致认可的偏移，会从每个片段扩展为每一行都等于旧画面在该偏移处的最大矩形，在它完整绘制了某个变化图块时作为 COPY 在更新的静止图像之前发送，每次读取最多 8 个：只绘制图块局部的复制什么也省不下，因为每个这样的图块反正都要以静止图像发送。它的图块不是静止图像，它与其来源的图块都不计为原地变化，因此滚动或被拖动的窗口始终是复制，它露出的条带是静止图像，永远不会成为区域的流。复制只读取客户端届时持有的内容——不读取流承载的图块，不读取欠着尚未发送的静止图像的图块，也不读取同一次读取中另一个复制所绘制的部分——也不在流承载的图块上绘制；它绘制的每个图块都欠下其来源所欠的内容，因此对流的画面的复制，会像该流一样收敛。在游走的列表上，来源已收敛的复制同样已收敛，如同在全阶段存入缓存的图块：它绘制的是全阶段的像素，只是移了位置，尽管客户端在它们现在的位置不持有其渐进式系数，因此它的某个图块下一次变化时，是一次不作为差值的首次传递。滚动后停下的页面只会再发送滚动露出的部分，而不是整页以全阶段再发送一次。刻度固定的列表和游走的列表上都会查找复制：一次滚动只发送几个字节和它露出的条带，滚动一个页面所发送的字节，刻度固定时是原来的三分之一（[测量](tiles-performance.md#copies)，英文）。
- **曾经显示过的部分是缓存的图块。** 客户端保留一个 4096 个图块的缓存（64 MiB 像素），wlshare 保留它的记录：每个静止图像发出之后，其中每个完整的 64×64 图块（单一颜色的除外）都被存入一个槽位（`STORE`），槽位用满后取最近最少使用的那个，记录中保存其像素的哈希。某个变化的图块，若其完整像素在记录中能找到对应的槽位，就以绘制该槽位（`CACHED`）发送，共 15 字节，静止图像的那一串则绕开它编码：切换回来的窗口、再次打开的菜单、整图块回滚的页面、在窗口之间移动的文字。它绘制的是该槽位存入时的内容，因此欠下的也是那个静止图像所欠的：精确存入或在全阶段存入的图块已收敛，而在全阶段之下存入的渐进式图块欠一份全阶段，如同对这种图块的复制；一旦它的升级使它收敛，它就会被重新存入其槽位，并标记为已收敛。单一颜色的图块从不存入：它的 PNG 只有几个字节，一个槽位的价值高于此。客户端只保留被告知保留的内容、只绘制被告知绘制的内容，因此一切由记录决定，两端由构造保证一致；重新开始的画面会忘记记录，此后客户端的槽位只是被覆盖。在一段桌面工作的会话上测得，它承担了约七分之一的静止图像（[测量](tiles-performance.md#the-cache)，英文）。
- **在固定刻度的列表上，运动的部分是视频。** 采用 Motion 的规则：一个图块在最近 8 个十分之一秒中有 4 个发生变化时即为运动；运动图块合并为 4 连通分量，不足 5 个图块的分量交给 PNG，包围框会合并，除非合并后的框超过运动图块的两倍，并且同时最多有 4 个区域以流传输。区域最多每 500 ms 重新布局一次：缩小的区域保留其流，扩大的区域从关键帧重新开始，一秒内没有运动的区域结束。流结束时，其下发生了变化而没有被它的任何帧承载的内容，会在同一次更新中、在它的 END 之后以静止图像发送，否则客户端持有的就是流的最后一帧留下的样子，比画面更旧。一个区域最大为整个桌面，其上限与 `WLSV` 的整桌面流相同：网关只为其浏览器解码器能接受的桌面列出该编码，与列出 `WLSV` 时一样，因此 wlshare 不对区域施加自己的上限。每个区域都是仅覆盖其矩形的一个编码器，并像 `WLSV` 那样被告知其中的变化区域，因此编码器的时间取决于运动的面积而不是整个桌面。它是 4:2:0 的 H.264（见下文），所有浏览器都能解码，包括其硬件解码器；它的损失只在区域运动期间存在，因为收敛会把它再以静止图像发送一次。它的刻度就是列表的刻度，固定不变：游走的列表不以流传输任何内容。
- **刻度会游走，除非列表固定它。** 列表给出的刻度是一个上限，会话对链路的游走——与移动 `WLSV` 刻度的是同一个游走（见上文 VP9 编码一节），阈值和步长都相同——根据每次更新的 fence、在没有 fence 时根据其写入阻塞的时长，把这种画面的刻度移到上限之下。携带整幅画面的更新像关键帧一样穿越链路，不作为判据；只含定时查找所发内容——即桌面停下后所欠的内容——的更新也不作为判据，正如 `WLSV` 使静止桌面变清晰的那一帧不是判据：游走在静止期间保持原位，其判据从第一个这样的更新起重新开始。其他任何更新都是判据，含有 START 的更新也是：区域的 IDR 是运动中的桌面持续发送的负载，正是游走要评判的对象；若像关键帧那样在每个 IDR 之后让判据等待两秒，游走对窗口中的视频几乎什么也听不到（[测量](tiles-performance.md#the-walks-verdicts)，英文）。被放慢的游走像控制 `WLSV` 的帧那样控制更新的节奏，而渐进式图块的首次传递跟随的就是这个刻度（见下文）。不欠任何精确版本：列出游走的客户端想要游走胜过最终精确的画面。在全阶段之下的首次传递欠下其后的各次升级，而在游走被放慢期间这些欠款会等待：落后的链路不会再被塞入它已经拥有的内容的更精细画面。它们只等到桌面静止两秒为止，不会更久：静止的桌面不发送任何更新，也就没有能让游走回升的判据。列表旁附带 `WLSD` 时，刻度被固定，所有静止部分都精确，流保持在该刻度，被写入阻塞推动的游走只控制更新的节奏：面向带宽充裕的链路——在那里游走只会停在上限处——以及最终精确的画面。之所以使用 `WLSV` 的游走而不是自己的一套，是因为判据相同——更新在链路上的排队——而第二套阈值就是第二件需要测量的东西。

- **在游走的列表上，每个图块都是渐进式的（实验性）。** 刻度游走的列表不会收到 PNG 或流：每个发生变化的图块，无论静止还是运动，都是一个 PROGRESSIVE，就像 Windows 主机在没有 H.264 时绘制其桌面那样，复制和缓存则与上文相同。`crates/wlshare/src/rfb/progressive.rs` 是编码器：图块转为 11.5 定点的 YCbCr，经过三级 reduce-extrapolate 5/3 小波变换，按协议的表量化，并分多次传递发送。首次传递在某个阶段保留每个系数的低位不发——游走处于上限且未被放慢时为 75，刻度在 70 及以上时为 50，再往下则是协议自己的一个阶段，它在每个子带中多保留一位，比 50 少三分之一的字节，因为主机的首次传递无论链路多慢都停在 50，降低刻度的游走将什么也缩减不了——或者在全阶段的代价最多多出四分之一时（如单色图块）直接以全阶段发送。客户端已持有的、发生了变化的图块，在差值的零更多时，以其系数与客户端所持系数之差发送，这就是不用流也能承载运动的方式。编码器保存客户端持有的每个图块的内容，使每次传递都针对它编码；被复制或缓存槽位覆盖绘制的图块会被遗忘，下一次以非差值的首次传递发送。一次更新的首次传递在所有核心上预先编码，再按顺序发送。所欠的是之后的各个阶段：收敛一次发送图块的一个阶段的升级，即上一阶段保留未发的那些位，直到它处于全阶段，此后不再欠任何内容。它的测试用一个自己的解码器读回每次传递，`examples/tiles-walk-sim.rs` 对它进行游走模拟（[测量](tiles-performance.md#progressive-tiles)，英文）。

- **H.264 由 wlshare 选择：主机的硬件，或 libx264。** 固定刻度的列表上的每个区域都是 H.264，由启动时一次性找到的编码器编码；客户端没有发言权，START 也不指明编解码器。在 GPU 具有某个 VA-API 驱动可以访问的 H.264 编码器的主机上——通过配置中的 `hardware_h264 = true`（默认值）来查找——使用的就是该编码器，这正是这种画面的用途：处理器只需负担到 NV12 的转换，而不负担任何搜索。在没有这种编码器、或关闭了该键的主机上，使用的是 `ultrafast` 预设的 libx264，它每帧消耗的处理器时间约为 VP9 的三分之一，字节数约为其两倍，适用于有这些字节可用的链路（[测量](tiles-performance.md#the-regions-encoder)，英文）。`crates/wlshare/src/h264.rs` 就是该编码器，即通过已为摄像头链接的 libavcodec（Debian 的版本，它本身链接了 libx264）使用的 libavcodec 的 `h264_vaapi` 或 `libx264`，以及守护进程图块编码器的 `RegionCoder`，它为每个区域打开一个这样的流。编码方式与 VP9 一样是固定的：恒定量化参数，刻度映射到 QP 40 至 16，没有比特率，不丢弃任何帧，没有 B 帧，一帧进一帧出，流的 VUI 中为有限范围（studio swing）的 BT.601；画面为区域尺寸向上取整为偶数边长，这是 libx264 的要求，因此奇数边长的区域（例如位于奇数尺寸桌面边缘的区域）会被编码得大一个像素，下方重复其最后一行，右侧为黑色，由网关裁掉；每帧是一个 Annex B 访问单元，每个 IDR 之前都有参数集，在流的 START 处有一个 IDR；刻度在流的整个生命周期内不变。硬件编码器的是带 CABAC 的 High profile；libx264 的是 Constrained Baseline，即 `ultrafast` 最终对应的档次，调优为 `zerolatency`——没有前瞻（lookahead），画面按 VP9 编码器的线程数切片——没有场景切换检测，并在流的第一个 IDR 之前带有其版本 SEI，解码器会跳过它。网关根据该参数集声明这个流，即 `avc1.` 加上其档次（profile）和级别（level），浏览器的解码器在有硬件解码器时以硬件接收它。启动时，守护进程依次尝试每个渲染节点，先是低功耗编码器——Intel 的固定功能单元，它把执行单元留给桌面，且无需 HuC 固件即可进行 CQP 编码——然后是着色器编码器，再然后是 libx264，每个都在一幅小画面的一帧上尝试，因为驱动列出的档次多于它能打开的；日志会说明找到了什么，什么都没找到时守护进程不会启动：区域没有其他编解码器可用。无法为会话的图块画面打开的编码器、拒绝某个流的编码器，或在中途使某个流失败的编码器，都会结束该会话，与任何编码器失败时一样。每个会话自行打开设备，因此一个 VA display 只属于一个线程。整桌面的 `WLSV` 流无论列表如何都是 VP9：游走的量化参数每帧都在变化，而硬件编码器的量化参数不会。守护进程 crate 中的 `examples/tiles-sink.rs` 是一个保留每个流的客户端，供 FFmpeg 自己的解码器完整读回。守护进程的单元测试在每台机器上用 libx264 编码帧，并在硬件上编码帧，再用 libavcodec 的软件解码器解码；在没有编码器的机器上，硬件的测试附带一句说明而通过。
- **它会收敛。** 流承载过的每个图块在静止半秒后都欠一份 PNG，在全阶段之下的每个渐进式图块则欠其下一阶段的升级。每四分之一秒查找一次欠下的内容，每次查找都是一次更新，与其他更新一样等待请求和 fence：最多取欠得最久的 320 个图块，按行连成片段，最旧的片段先发，直到发出 256 KiB 为止，而游走低于上限时，链路缺字节，每次最多 40 个图块；游走被放慢期间，在桌面静止两秒之前不查找。因此停下的桌面在固定刻度的列表上会在页面上变得精确，在游走的列表上则达到全阶段，在 4K 下固定刻度时 4.3 秒内完成，而原来需要 13 秒（[测量](tiles-performance.md#the-settle)，英文），而一旦如此，就不再发送任何内容。
- **与其他编码一样按轮进行。** 每次更新以其 fence 结束，同一时间只有一个在途。新尺寸会结束所有流且不发 END——尺寸先发出，随后是整幅画面——而非增量请求以各自的 END 结束它们。去掉该编码的列表会得到以其所选标准编码发送的整个帧缓冲。

守护进程 crate 中的 `examples/motion-bench.rs` 把保存的捕获通过本编码器和 `WLSV` 播放，两者都像页面那样解码：图块的更新经过客户端的解析器，复制取自页面自己的画面，每个区域由 libavcodec 的软件 H.264 解码器解码，刻度固定，所有静止部分都精确。它与 `walk-sim` 一样输出 JSON 行，`scripts/motion-tables.py` 把两者的日志做成 Markdown 表格。它的区域是
守护进程自己的 H.264——`h264.rs`，按守护进程的方式找到，或使用 `--libx264` 时为 libx264——因此在守护进程能构建的地方它就能运行。`--tiles-only` 不编码 `WLSV`，因此对图块的改动以之前某次运行的 `WLSV` 为对照来测量。它的 `check` 要求编码器在收敛后不再发送任何内容（经过 5 s 的静默和 10 次对页面已有像素的重绘），并以精确结束；`still` 捕获是为它准备的，不用于任何测量。它测得的结果，以及 Motion 之外的规则据以选定的数据，见 [Tiles performance](tiles-performance.md)（英文）。

旁边的 `examples/tiles-walk-sim.rs` 把这些捕获通过本编码器和游走送入 `walk-sim` 对网关和浏览器链路的模型（`crates/wlshare-vp9/examples/sim`），一次更新在途，就像会话在游走的列表（每个图块都是渐进式的）或固定刻度的列表上那样，并像 `walk-sim` 那样报告一次运行的结果；它的发现见 [Tiles performance](tiles-performance.md#the-walks-verdicts)（英文）。

## 密度扩展

标准 RFB 没有表达像素密度的说法。该扩展是一个伪编码 `0x574c5348`（`WLSH`）和一个双向的消息类型 `0xE0`；缩放是 16.16 无符号定点数，因此 `0x0002_0000` 为 2.0，`0x0001_8000` 为 1.5。两条消息采用同一种布局：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | 消息类型，`0xE0` |
| 1 | U8 | 填充 |
| 2 | U16 | 宽度，像素 |
| 4 | U16 | 高度，像素 |
| 6 | U32 | 缩放，16.16 定点 |

- **OutputScale**，服务器 → 客户端，十个字节：类型、填充、以像素计的宽度和高度、缩放。作为对*每一个*列出该伪编码的 `SetEncodings` 的应答发送——这是宣告支持的唯一方式——并且每当共享输出的尺寸或缩放发生变化时（包括另一个输出成为共享输出）也会发送，且在以新尺寸捕获帧之前发送，因此该报告先于调整尺寸的矩形到达。
- **ClientDensity**，客户端 → 服务器，十个字节，采用 OutputScale 的布局：类型、填充、以像素计的宽度和高度、缩放。客户端每次都同时说明它希望输出以什么缩放绘制，*以及*它希望在该缩放下的尺寸，因此一次密度变化就是一次输出配置：只给出缩放会改变逻辑尺寸，直到随后再调整一次尺寸，而每个应用都会重绘两次。密度不变时的调整尺寸用 `SetDesktopSize`。只接受列出了该伪编码和 ExtendedDesktopSize 的客户端发来的声明，缩放只接受 0.5–8 范围内的值，尺寸不能为空。服务器通过 wlr-output-management 在一次配置中设置输出的模式和缩放，只请求有差异的部分，规则与调整尺寸相同——无头输出——并且**对每一个声明都以一条 OutputScale 应答**：在合成器的 head 缩放变化之后应答，或者在声明与当前一致、被拒绝或无法应用时，立即以输出的当前状态应答。合成器接受但没有改变缩放的配置也会得到应答：`succeeded` 之后跟着一次 `wl_display.sync` 往返，若在此之后没有到达缩放变化，就报告输出的当前状态。同一时间只有一个声明的配置在进行中，它的事件与其他声明的事件区分开来，因此每个声明只应答一次：期间到达的声明会等它落定，而更新的声明会取代它，被取代的那个以输出的当前状态应答。合成器因为布局在其下发生变化而*取消*的配置——添加或移除了一个输出，客户端的虚拟显示器就会这样——会针对新布局再做一次，仅一次；第二次取消即视为拒绝。新尺寸以一个 ExtendedDesktopSize 矩形到达客户端，其原因（reason）是该客户端，与 SetDesktopSize 的情况一样。

精确的缩放来自 wlr-output-management 的 head，包括小数缩放；当该协议不存在时，退而使用 `wl_output.scale`，而 wlroots 会将它向上取整。

## 输出扩展

一个帧缓冲就是一个输出，因此对于有两个显示器的桌面，必须询问要发送哪一个。标准 RFB 对此同样没有说法——`ExtendedDesktopSize` 描述的是*一个*帧缓冲之内的屏幕——所以这是第二个私有扩展，形式与第一个相同：一个伪编码 `0x574c534f`（`WLSO`），以及一个双向的消息类型 `0xE1`。

- **OutputList**，服务器 → 客户端：类型、服务器按请求最多创建的虚拟显示器数量（[虚拟显示器](#虚拟显示器)）、计数、共享输出的 id，然后是每个输出一个条目——id、以像素计的宽度和高度、以 16.16 定点数表示的缩放、一个标志字节（其第 0 位表示该输出是无头输出），以及一个带长度前缀的 UTF-8 名称。作为对*每一个*列出该伪编码的 `SetEncodings` 的应答发送——这是宣告支持的唯一方式——并且每当列表、某个条目或共享输出发生变化时再次发送。条目按名称排序，名称或模式尚未到达的输出不在其中。id 是 `wl_output` 全局对象，在输出存在期间唯一，对客户端而言是不透明的。名称是合成器自己的，如 `DP-2` 或 `HEADLESS-1`；无头标志标记的是合成器创建的输出，而不是有人坐在前面的显示器。

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | 消息类型，`0xE1` |
| 1 | U8 | 虚拟显示器：服务器最多创建的数量，0 表示不创建 |
| 2 | U16 | 计数 |
| 4 | U32 | 共享输出的 id |

  然后是 `count` 个条目：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U32 | id |
| 4 | U16 | 宽度，像素 |
| 6 | U16 | 高度，像素 |
| 8 | U32 | 缩放，16.16 定点 |
| 12 | U8 | 标志——第 0 位：无头 |
| 13 | U8 | 名称长度 |
| 14 | U8[] | 名称，UTF-8 |

- **SelectOutput**，客户端 → 服务器，八个字节：类型、值为 0 的操作字节、两个字节的填充、要共享的输出的 id。来自未列出该伪编码的客户端时忽略，只接受桌面上的客户端发来的请求，并且无论哪种情况都**以一条 OutputList 应答**，旁边的显示器也包括在内：指名合成器已不再拥有的输出或已经共享的输出的请求，以列表的当前状态应答。因此客户端的菜单跟随的是画布上实际显示的内容，而不是被点击的内容。

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | 消息类型，`0xE1` |
| 1 | U8 | 操作，0 |
| 2 | U8[2] | 填充 |
| 4 | U32 | id |

- **VirtualDisplays**，客户端 → 服务器，八个字节，布局相同，操作字节为 1，并以计数代替 id：要有这么多个虚拟显示器（[虚拟显示器](#虚拟显示器)）。按 SelectOutput 的规则受理，并以列表的当前状态应答；它带来的结果随着输出的出现和消失到达，每次一个列表。

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | 消息类型，`0xE1` |
| 1 | U8 | 操作，1 |
| 2 | U8[2] | 填充 |
| 4 | U32 | 计数 |

一次切换会停止捕获，把新尺寸以空白状态带入帧缓冲，把虚拟指针指向新输出——`zwlr_virtual_pointer` 在创建时获取其输出，此后再也不会更改，因此会释放客户端按住的内容并重新创建指针——报告几何信息和列表，然后重新开始捕获。在客户端所请求输出的一帧到达之前，不向客户端发送任何内容：尺寸不同时，以一个原因为服务器的 ExtendedDesktopSize 矩形到达客户端；尺寸相同的输出则以一次完整重绘到达。一开始共享哪个输出由配置中的 `output` 决定，否则为第一个。

一个 id 恰好在可列出时才可选择：输出的属性已经到达，它有名称，并且捕获它会产生像素。同一条规则同时用于两者，因此客户端永远不能指名一个列表不会向它显示的东西，而仍在到达中的输出也不可能变成一个没有尺寸的桌面。

合成器移除了正在共享的输出时，不会留下一个不指向任何东西的名称——那样会停止捕获，却没有任何东西能再次启动它，客户端会一直看着一幅已经悄无声息地不再变化的画面。桌面会在合成器拥有配置的 `output` 时移到它上面，否则移到列表显示的第一个输出上，经过的流程与客户端自己发起切换时相同，因此客户端会得知新的几何信息并收到新输出的像素。没有剩下任何输出时，捕获停止，列表以空列表发出，最后的几何信息和最后的画面保持不变，直到出现一个输出；第一个到达的输出会以同样的方式被采用。

### 虚拟显示器

RDP 客户端的显示器布局和 Mac 的显示器配置会告诉主机会话有多少个显示器，由主机来创建它们。`VirtualDisplays` 就是这样的请求：桌面上的客户端说明它想要多少个虚拟显示器——一个或两个，每个桌面视图（desk）一个，因为一个输出只显示在一个桌面视图上，而桌面视图有两个——守护进程就让合成器创建无头输出，或拔除它们，直到数量相符。只受理桌面上的客户端的请求；旁边的显示器的请求，与它的 `SelectOutput` 一样，以列表的当前状态应答。

只有 sway 可以接受这样的请求。客户端绑定的 Wayland 协议中没有任何一个能创建输出，而 sway 的 IPC 可以：`create_output` 创建一个无头输出，`output NAME unplug` 销毁一个输出，启动时创建的输出也包括在内。守护进程在 `SWAYSOCK` 中找到套接字——sway 会为它启动的所有程序设置该变量，会话的用户管理器（user manager）也会把它带给自己的单元——并在启动时检查它是否以 sway 的身份应答；没有任何需要配置的东西。每条 OutputList 都在第二个字节中说明守护进程最多创建多少个虚拟显示器——在 sway 上为两个，否则为零——因此客户端在请求之前就已知道；守护进程无法执行的请求，或请求的数量不是它所创建的数量，都以列表的当前状态应答，且不改变任何东西。在 labwc 或其他合成器上，输出就是合成器已有的那些。

一次一步。请求以列表的当前状态应答，它带来的结果随输出的到达而到达：发送一个 `create_output`，它的输出出现并被列出，然后才发送下一个；拔除同样要等它的输出消失。每次出现和消失都是一个单独的列表，因此在只有一个输出的会话上请求两个的客户端，会在随后的列表中看到第二个输出，并在 zDesk 网关中打开它的标签页。计数的是无头输出，无论是谁创建的：以两个启动（`WLR_HEADLESS_OUTPUTS=2`）而被请求一个的会话会少掉一个，就像有两个显示器的 Windows 主机被请求一个时那样。桌面所在的输出永远不会被拔除；其余的输出中，最后创建的最先拔除——即编号最大的，因为 wlroots 在合成器的整个生命周期内递增计数，所以在拔除一个输出之后创建的输出是一个新名称下的新输出，永远不会是原来那个回来了——而配置的 `output` 最后拔除。来自 sway 的拒绝会被记入日志，并结束该请求。

请求属于客户端。客户端离开或被接管时，请求随之解除，而输出保持原样，直到下一个客户端提出要求，因此窗口在重新连接前后保持在原来的位置，与 Windows 主机上一样。有头会话的监视进程可以在它的 *free* 命令中拔除剩下的输出。

### 旁边的另一个显示器

一个帧缓冲就是一个输出，一个连接就是一个帧缓冲，因此想同时得到两个输出的客户端要连接两次。它的第二个连接完成同样的握手，包括登录，并在 RFB 放置共享标志的位置发送 `0xB5` 作为其 ClientInit 字节。之后它不会占据桌面：桌面上的客户端保持不变，而这个连接显示的是列表中第一个该客户端不在其上的输出。其他任何 ClientInit 值都会占据桌面，包括 RFB 的 `1`。

它是该输出上的一个完整的 RFB 会话：有自己的帧缓冲和捕获、自己的光标会话、针对其输出创建的虚拟指针、自己的编码——在它列出 VP9 时，是带有针对自身链路的质量游走（walk）的 VP9——以及自己的调整尺寸和密度，遵循它所在输出的规则。它的 ServerInit 给出的是该输出的尺寸，因此只有在该输出归它所有之后才会发送。键盘属于座位（seat），来自任一连接的按键都会到达合成器当前聚焦的对象；每个连接离开时会松开它按住的键，而不会松开另一个连接按住的任何键。两个连接都按住的键，在最后一个松开它时才抬起。剪贴板属于桌面，只由桌面上的客户端设置。

它不能做的是选择。哪个输出在哪里，由桌面上的客户端决定：如果旁边的连接列出了该扩展，就会向它发送一条把它自己的输出列为共享输出的 `OutputList`，而它的 `SelectOutput` 会以这个列表的当前状态应答。在以下情况下它会结束，其套接字被关闭：

- 桌面上的客户端离开或被接管——旁边的显示器属于该客户端，新客户端开始时没有旁边的显示器；
- 桌面上的客户端选择了它正在显示的输出，因为一个输出只在其中一个上；
- 另一个连接请求在旁边显示，取代了它的位置；
- 合成器移除了它的输出。

在桌面上没有任何人时发出请求的连接，或者没有该客户端不在其上的输出时发出请求的连接，会在 ServerInit 之前被关闭。握手在一个更晚连接的旁边显示器已经结束之后才完成的连接也是如此：它不会取代任何人的位置。在当前桌面上的客户端之前就已连接的连接同样如此：它是在之前在那里的客户端旁边打开的。旁边的显示器只有一个，所以同时显示两个输出是客户端所能看到的最多数量。zDesk 网关在 *All Displays* 下为第二个显示器的浏览器标签页打开它，并在其上列出像素编码、光标、尺寸和密度，除此之外别无其他。

只有无头输出才会被调整尺寸或缩放，因此切换到真实显示器后，客户端的调整尺寸请求会得到 *prohibited* 应答，其密度声明会以输出的当前状态应答——那个显示器的模式属于坐在它前面的人。

这一选择在做出它的客户端离开后仍然有效：下一个连接会在上一个连接所请求的输出上打开，而不是在配置的默认输出上打开，直到配置的输出下次出现或守护进程重启为止。在一个有两个显示器的 sway 会话上的测量见 [zDesk 的 `docs/wlshare-outputs.md`](https://github.com/andrewtheguy/zdesk/blob/main/docs/wlshare-outputs.md)（英文），网关那一半的实现就记录在那里。

## 音频扩展

桌面的声音，以 FLAC 或 Opus 形式，在像素所用的同一个连接上传输。它是私有的——伪编码 `0x574c5346`（`WLSF`）和服务器消息类型 `0xE4`——其客户端是 zDesk 网关。用哪种编解码器与格式一样由客户端请求，这里没有任何配置项：为 FLAC，除非客户端在该编码旁边列出 `0x574c4f50`（`WLOP`）。客户端的消息以及流的开始和结束借用自 `rfbproto` 登记的 QEMU Audio 扩展，即消息类型 `255` 子消息 `1`；QEMU 的伪编码 `-259` 不使用，因为它承诺的是原始采样，而这里不发送任何原始采样。只列出 `-259` 的客户端（例如 gtk-vnc）听不到任何声音。

- **通告**，服务器 → 客户端：一个编码为 `WLSF` 的空伪矩形，放在单独的一个 `FramebufferUpdate` 中，在任何像素之前发送给 `SetEncodings` 列出了它的客户端。这是宣告支持的唯一方式。

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U16 | x，0 |
| 2 | U16 | y，0 |
| 4 | U16 | 宽度，0 |
| 6 | U16 | 高度，0 |
| 8 | S32 | 编码，`0x574c5346` |

- **设置格式、启用、禁用**，客户端 → 服务器，QEMU 的消息：采样格式、声道数和频率由客户端选择，服务器把桌面播放的内容转换成这些参数。格式为 QEMU 的代码 0–3，即 U8、S8、U16 和 S16；它的 32 位代码会被拒绝，因为 FLAC 最多存储 24 位。频率的下限为 8 kHz，即真实音频使用的最低采样率，上限为 96 kHz，即桌面自身音频处理图运行频率的两倍。其他代码、1 或 2 以外的声道数、或超出这些范围的采样率都是致命错误。启用或禁用为四个字节，设置格式为十个字节：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | `255` |
| 1 | U8 | `1` |
| 2 | U16 | 操作：0 启用，1 禁用，2 设置格式 |
| 4 | U8 | 采样格式（仅设置格式时）：0 U8，1 S8，2 U16，3 S16 |
| 5 | U8 | 声道数，1 或 2 |
| 6 | U32 | 频率 |

- **Opus**，客户端 → 服务器：伪编码 `WLOP` 与 `WLSF` 一同列出时，请求以 Opus 代替 FLAC 发送声音。之所以是伪编码而不是消息，与 VP9 流的各项选择一样，是为了让它搭载在请求声音本身的那个列表上。在流运行期间改变编解码器的列表会以新的编解码器重启该流，中间经过一次结束和一次开始。
- **设置比特率**，客户端 → 服务器，操作 `3`，排在 QEMU 的三个操作之后，是 wlshare 自己的操作：Opus 编码所用的比特率，单位为比特每秒，范围为 6 000 到 510 000，即 libopus 的界限；超出范围的比特率是致命错误。Opus 流没有自己的比特率：必须在启用之前设置过一个，没有设置就启用会被拒绝，记录一行日志且不发送开始，与以 Opus 不编码的频率启用时一样。它可以在流运行期间再次发送，运行中的流会在下一个数据包时改用新比特率，无需重启。FLAC 流没有可改变的比特率。

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | `255` |
| 1 | U8 | `1` |
| 2 | U16 | 操作，`3` |
| 4 | U32 | 每秒比特数 |

- **开始和结束**，服务器 → 客户端，QEMU 的消息：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | `255` |
| 1 | U8 | `1` |
| 2 | U16 | 操作：0 结束，1 开始 |

- **一帧**，服务器 → 客户端，位于一次开始和一次结束之间——一个 FLAC 帧，或一个 Opus 数据包：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | U8 | 消息类型，`0xE4` |
| 1 | U8[3] | 填充 |
| 4 | U32 | 帧的长度 |
| 8 | U8[] | 一个 FLAC 帧或一个 Opus 数据包 |

每个 FLAC 帧恰好包含 `frequency / 50` 个采样帧（向下取整）——二十毫秒，48 kHz 时为 960 个——采用固定块大小模式，并且帧号为零。FLAC 流头 `STREAMINFO` 从不发送：其中的一切都已事先约定，因此客户端根据自己设置的格式构建它，并把该块大小同时作为最小值和最大值。帧会声明自己的采样率，除非没有任何帧头代码能表示该采样率（例如 70001 Hz），此时交由那个流头给出。无符号格式在编码前会翻转每个采样的最高位，这把它的范围映射到同宽度的有符号范围上，静音对应零；客户端再把它翻转回来。解码后的采样是交错的小端序数据，与捕获产生的数据逐位相同。

FLAC 是无损的，而音乐约占其 1.5 Mbit/s PCM 速率的一半，语音不到三分之一，静音的桌面每帧只需几个字节。帧长度超过 64 KiB 对客户端是致命错误：可能的最大块，即 96 kHz 下 20 ms 的 16 位立体声，压缩前为 7680 字节。

编码器只在一个地方被调用：[sound-flac](https://github.com/andrewtheguy/sound-flac)，一个独立的仓库，本工作区和 zDesk 网关（后者用它对 RDP 主机的声音进行 FLAC 编码）各自按发布标签固定其版本。编码器是该 crate 自己的，用纯 Rust 编写，针对边产生边收听的声音调校：不编译任何 C 代码，运行时不下载或加载任何东西，软件包也不依赖任何 FLAC 库。它在每个块凑满的那一刻就把该块编成一帧，不带任何之前块的信息，因此途中丢失的一帧只损失它自己的采样，不影响之后的任何内容，这就是每一帧都编号为零的原因。不发送任何标记或流头：客户端根据自己设置的格式构建流头。守护进程的测试用 symphonia 的解码器读回每一帧，该解码器与它没有任何共享。

以 Opus 发送时，每个数据包同样是二十毫秒，即 `frequency / 50` 个采样帧，并且频率必须是 Opus 能编码的频率——8、12、16、24 或 48 kHz——否则启用会被拒绝，记录一行日志且不发送开始。采样格式只说明捕获交给编码器的是什么：无符号采样像 FLAC 那样翻转，8 位采样扩展为十六位；解码器还原出什么是解码器自己的事。不发送 `OpusHead`。客户端根据自己设置的格式构建它，pre-skip 为 312，即编码器在任何频率下以 48 kHz 采样计的前瞻量（lookahead）。数据包的解码依赖于之前的数据包，而线路上不给任何数据包编号，因此客户端无法察觉少了一个：wlshare 不丢弃任何已编码的数据包，跟不上的客户端丢失的是从未被编码的声音。

这是自身收听端接受 Opus 的客户端的选择：zDesk 网关把每个数据包原样交给浏览器，否则它就得自己解码 FLAC 再编码 Opus；它还把浏览器链路的速率游走（walk）得出的比特率作为设置比特率消息发送：即 sound-opus 的 `walk`，唯一的一套速率游走，网关既为它自己编码的声音运行它，也为这里运行它。编码器是 libopus，与 FLAC 编码器一样只在一个地方被调用：[sound-opus](https://github.com/andrewtheguy/sound-opus)，本工作区和网关（后者用于它自己编码的声音）各自按发布标签固定其版本，因此这里产生的数据包和那里产生的数据包是同一种流——针对音乐调校，围绕该比特率的受约束可变比特率，以最高复杂度编码，静音时每个数据包只有几个字节。libopus 链接自其 sys crate 下载的预构建静态归档：不编译任何 C 代码，运行时不加载任何东西，软件包也不为此依赖任何东西。守护进程的测试把这些数据包包装进一个 Ogg 流，放在客户端所构建的头之后，并用 FFmpeg 自己的 Opus 解码器解码，该解码器与 libopus 没有任何共享，因此测试需要路径上有 `ffmpeg`。

在任何客户端收听期间，主机保持静音，就像远程桌面的声音那样：桌面播放到**扬声器**中——这是 wlshare 自己的一个输出设备（sink）——而不是主机的输出设备中。`audio.rs` 在第一个客户端启用时创建它，在最后一个客户端禁用或断开连接时移除它——一个名为 `wlshare-speaker`、描述为 "wlshare remote audio" 的 `support.null-audio-sink`，运行在自己的线程上。为此主机上没有任何改动，没有输出设备被静音，也没有写入任何默认设置。扬声器的 `priority.session` 为 100000，而 WirePlumber 会把可用输出设备中优先级最高的设为默认，计算前给用户配置的那个加 30000，给在它之前配置过的那些最多加 20000；硬件输出设备本身的优先级只有几千出头，因此扬声器存在期间就是默认设备，无论它是否是被选中的输出设备，所有跟随默认设备的流都会移到它上面。该节点属于扬声器线程的 PipeWire 连接，因此当该线程退出或守护进程终止时，PipeWire 会移除它，WirePlumber 会重新把主机的输出设备设为默认，各个流也随之移回去。应用固定到其自选输出设备上的流会留在那里，在主机上播放。

`audio.rs` 为每个启用音频的客户端启动一个 PipeWire 捕获，运行在自己的线程上。它是一个 `Stream/Input/Audio` 节点，设置了 `stream.capture.sink = "true"`，`target.object` 为扬声器，这会把它连接到**扬声器的监听源**——桌面正在播放的内容，无论是谁在播放——并通过 `node.latency` 请求 20 ms 的缓冲区。处理回调运行在该线程的循环上，而不是音频处理图的实时线程上——刻意不设置 `RT_PROCESS`，因为回调会编码、分配内存、获取互斥锁并唤醒一个任务，在数据线程上做其中任何一件事都可能使整个音频处理图停顿，让主机上的每个应用都出现 xrun。在那里编码可以让编码不占用会话的任务，后者还要压缩像素；一个 20 ms 的缓冲区只需零点几毫秒。编码器会把不足一帧的部分留给下一个缓冲区——PipeWire 在采用所请求的周期大小之前会先遵循它自己的周期大小（quantum），因此会话最初的几个缓冲区往往短于 20 ms，请求 960 帧时只有 512 帧——并把它完成的每一帧放入一个深度为十六的队列。当客户端跟不上时，FLAC 会丢弃最旧的一帧：每一帧都可独立解码，因此丢弃一帧只是一个 20 ms 的空缺，而卡住捕获回调更糟。Opus 则在队列满时不对缓冲区编码，这样解码器拿到的是编码器产生的每一个数据包，两者在空缺前后保持同步。对运行中的流发送设置格式，或发送改变其编解码器的列表，会按新的请求重启捕获，期间保持扬声器存在，使两次捕获之间不会听到主机的声音；禁用或断开连接会停止捕获；未凑满一帧的剩余部分随之丢弃。

会话在每次帧缓冲更新之前清空该队列，因此声音绝不会被挡在一个比它更晚就绪的像素更新之后。无头会话不需要自己的输出设备：扬声器就是一个。

每个列出该伪编码的客户端都会收到通告：没有任何配置能关闭声音，软件包依赖它所经由播放的 PipeWire、WirePlumber 和 pipewire-pulse。

## 摄像头扩展

客户端的摄像头，借给桌面使用。RFB 从客户端只承载输入和剪贴板，也没有任何已注册的扩展以这个方向承载视频，因此这是第三组私有配对，形式与密度扩展和输出扩展相同：伪编码 `0x574c5343`（`WLSC`）和消息类型 `0xE2`，双向使用。每条消息依次是类型、一个操作、另外两个字节，以及该操作携带的内容；整数为大端序。

| 方向 | 操作 | 第 2–3 字节 | 随后 |
| --------- | --------- | --------- | ---- |
| 客户端 → 服务器 | 0，插入（plug） | 填充 | `u16` 宽度，`u16` 高度，`u32` 帧率分子，`u32` 分母 |
| 客户端 → 服务器 | 1，拔出（unplug） | 填充 | 无 |
| 客户端 → 服务器 | 2，样本（sample） | 标志（bit 0：关键帧），填充 | `u32` 长度，一个 Annex B 访问单元 |
| 服务器 → 客户端 | 0，可用（available） | 填充 | 无 |
| 服务器 → 客户端 | 1，开始（start） | 填充 | 插入时的格式，布局与插入消息相同 |
| 服务器 → 客户端 | 2，停止（stop） | 填充 | 无 |
| 服务器 → 客户端 | 3，关键帧（keyframe） | 填充 | 无 |

- **可用**是对*每一个*列出该伪编码的 `SetEncodings` 的回答——这是宣告支持的唯一方式。
- **插入**按客户端将要发送的 H.264 创建一个摄像头；再次插入会替换它，拔出或客户端离开会移除它。没有像素或没有帧率的插入，以及超过 4 MiB 的样本，都是致命错误：它们说明客户端对这些字段的理解不同。像素多于 4096x2304（H.264 level 5.2 的最大帧，36 864 个宏块）的插入会被拒绝并记入日志，客户端也就没有摄像头：这些字段最大可达 65535x65535，其画面不应由任何缓冲区来容纳。
- **开始**和**停止**由桌面决定，而不是由客户端决定：某个应用打开了摄像头，或者最后一个应用关闭了它。客户端在两者之间发送样本，在此之外什么也不发送，并且流从一个关键帧开始。
- **关键帧**在出现缺口之后必须补上：H.264 无法跨越丢失的单元解码。

`camera.rs` 把每个插入的摄像头做成一个 PipeWire 节点 `wlshare-camera-<client>`，类别为 `Video/Source`，角色为 `Camera`，描述为“wlshare remote camera”，以免被误认为主机自己的摄像头。与音频捕获一样，它是一个运行 PipeWire 循环的独立线程，其回调运行在该循环上，而不在音频处理图（graph）的实时线程上，因为这些回调要解码和复制。它只提供一种格式——插入时的几何尺寸和帧率下的 I420，即它背后唯一的解码器所产生的格式——想要其他格式的应用要么自行转换，要么不打开它。该节点是它自己的驱动者（driver）：图中没有其他任何东西知道摄像头帧何时到期，因此每解码出一幅画面，就触发一次递送它的周期。应用链接到它时流进入 *streaming* 状态，最后一个应用离开时流退回原状态，这就是会话发送的开始和停止。

`decode.rs` 是系统的 libavcodec，通过 `ffmpeg-sys-next` 只使用 avcodec 并动态链接，因此软件包依赖 Debian 的 `libavcodec`，而不是自带编解码器。解码器以 `LOW_DELAY` 在单个线程上运行，因此一个单元一经解码就成为一幅画面，而不是晚一帧。它接受 8 位的 4:2:0，这涵盖了 Constrained Baseline 所产生的一切。尺寸与插入时所给不同的画面是节点无法提供的，会结束该摄像头：这一情况只报告一次，不再解码任何内容，向客户端发送停止，并拔出该摄像头。

样本经由一个深度为八的队列到达摄像头线程。发现队列已满的样本会被丢弃，其后的每个样本也会被丢弃，直到一个关键帧为止；每个缺口只向客户端请求一次关键帧——如果关键帧本身也没有找到空位，则再请求一次。解码器拒绝的单元同样需要补一个关键帧。这里没有任何东西在等待客户端的套接字：一个不再观看的桌面，让客户端付出的代价不过是一次停止。

2026-09-14 在 PipeWire 1.4.2 的 sway 会话上测量：一个客户端以 15/1 插入 640x480 并发送 libx264 Constrained Baseline，一个 PipeWire 消费者链接到 `wlshare-camera-1` 并提供 YUY2、I420、NV12 和 BGRx。消费者协商得到 15/1 下的 I420 640x480 并进入 *streaming*，wlshare 发送了开始，消费者取得了完整的画面——460800 字节，步长（stride）640——直到它离开，wlshare 发送了停止。

应用通过 PipeWire 找到该节点，浏览器则通过 xdg-desktop-portal 的 Camera 接口找到它，该接口交给浏览器一个只显示角色为 `Camera` 的节点的 PipeWire 远程实例（remote）。只有当某个后端实现了 Access（用来询问用户）时，portal 才导出该接口；`xdg-desktop-portal-wlr` 没有实现，`xdg-desktop-portal-gtk` 实现了。portal 在启动时查找它的后端，因此安装后端之后，必须重启正在运行的 portal。软件包为此推荐（Recommends）`xdg-desktop-portal` 和 `xdg-desktop-portal-gtk`，而不是依赖它们：守护进程两者都不使用，自己打开 PipeWire 的应用也不需要 portal。Chrome 也只有在启用了 `chrome://flags/#enable-webrtc-pipewire-camera` 时才通过 PipeWire 访问摄像头；没有这个标志，或者没有 portal 的 Camera 接口，它就只查看 `/dev/video*`，列不出任何摄像头。2026-09-13 在 xdg-desktop-portal 1.20.3 的 labwc 会话上用 Chrome 153 检查：只安装了 `xdg-desktop-portal-wlr` 时，portal 没有导出 `org.freedesktop.portal.Camera`；加上 `xdg-desktop-portal-gtk` 并重启 portal 后，它导出了。

每个列出该伪编码的客户端都会收到这项宣告：没有任何配置能关闭摄像头。

## 麦克风扩展

客户端的麦克风，借给桌面使用——摄像头的孪生兄弟，相当于 RDP 主机从 MS-RDPEAI 得到的东西。QEMU Audio 扩展只单向承载声音，因此这是第四组私有配对：伪编码 `0x574c534d`（`WLSM`）和消息类型 `0xE3`，双向使用，每条消息依次是类型、一个操作、另外两个字节，以及该操作携带的内容；整数为大端序。

| 方向 | 操作 | 第 2–3 字节 | 随后 |
| --------- | --------- | --------- | ---- |
| 客户端 → 服务器 | 0，插入（plug） | 填充 | 无 |
| 客户端 → 服务器 | 1，拔出（unplug） | 填充 | 无 |
| 客户端 → 服务器 | 2，样本（sample） | 填充 | `u32` 长度，交错 PCM |
| 服务器 → 客户端 | 0，可用（available） | 填充 | 无 |
| 服务器 → 客户端 | 1，开始（start） | 填充 | `u16` 声道数，`u16` 填充，`u32` 频率 |
| 服务器 → 客户端 | 2，停止（stop） | 填充 | 无 |

- **可用**是对*每一个*列出该伪编码的 `SetEncodings` 的回答——这是宣告支持的唯一方式。
- **插入**创建一个麦克风；再次插入会替换它，拔出或客户端离开会移除它。超过 256 KiB 的样本是致命错误，不是开始所指定格式的完整帧的样本也是。
- **开始**和**停止**由桌面决定：某个应用开始录音，或者最后一个应用停止了录音。客户端在两者之间发送样本，在此之外什么也不发送。格式由服务器决定，就像 RDP 中由主机决定一样：样本始终是有符号 16 位小端序，开始消息指定声道数和采样率。wlshare 指定 48 kHz 单声道，这正是 zDesk 网关的 Opus 解码出的格式，因此浏览器和节点之间没有任何环节进行重采样。没有关键帧：丢失一个样本就是一刻静音。

`microphone.rs` 把每个插入的麦克风做成一个 PipeWire 节点 `wlshare-microphone-<client>`，类别为 `Audio/Source`，角色为 `Communication`，描述为“wlshare remote microphone”。与摄像头一样，它是一个运行 PipeWire 循环的独立线程，其回调运行在该循环上而不在音频处理图的实时线程上，流进入 *streaming* 和退回原状态就是会话发送的开始和停止。它不以 `AUTOCONNECT` 连接：源是由从它录音的程序链接的，如果自行链接，它会把客户端的声音播放到默认输出设备（sink）中。

与摄像头不同，它不是自己的驱动者。音频已经有一个时钟，即音频处理图的时钟，而一个自带时钟的源会与录音应用同时播放到的那些输出设备发生漂移；因此由音频处理图在需要时请求一个周期（quantum），节点则从一个位于客户端节奏和音频处理图节奏之间的抖动缓冲区中作答。该缓冲区在播放前先积攒 60 ms——在开始之后，以及每次耗尽之后都如此——因此迟到的样本表现为流中的一个缺口，而不是每个周期里的一声咔嗒；它在没有内容时以静音作答，并且最多保留 200 ms，丢弃最旧的数据，因此在停滞后突发发送的客户端会被实时听到，而不是延迟听到。停止会清空它。

2026-09-14 在 PipeWire 1.4.2 的 labwc 会话上测量：一个客户端插入麦克风，并在收到开始后每次发送 20 ms 的 440 Hz 音调；`pw-record --target wlshare-microphone-1` 以 48 kHz 单声道录音三秒，然后再录两秒。每次录音在链接时发送了开始，在离开时发送了停止；在最初的半秒之后，两段录音都保持着 440 Hz 的音调，没有任何静音的 10 ms 块，并且拔出之后该节点从图中消失。

每个列出该伪编码的客户端都会收到这项宣告：没有任何配置能关闭麦克风。

## 调整尺寸

`SetDesktopSize` 在共享的输出上设置一个自定义模式，规则相同。来自未列出 ExtendedDesktopSize 的客户端的请求根本不予回答。指定的屏幕不是恰好一个、或没有像素的请求，回答 *invalid layout*（无效布局）。请求当前尺寸的会立即回答 OK；针对无法重新配置的输出的请求——只有无头输出，即名为 `HEADLESS-*` 的输出，才能重新配置，而且只能通过 wlr-output-management——回答 *prohibited*；合成器拒绝的尺寸回答 *invalid layout*；合成器因布局在其执行期间发生变化而取消的尺寸，会针对新布局再执行一次，与声明的做法相同；合成器接受的请求，在该尺寸的帧到达时回答，并附带一个指明本客户端为原因的 ExtendedDesktopSize 矩形。

## 输入和剪贴板

按键事件携带 X11 keysym。服务器编译配置的 XKB 键盘映射，将其上传到虚拟键盘，并在同一份键盘映射中为每个 keysym 查找能产生它的键码，优先选择最低的 Shift 层级。修饰键状态用 `xkb_state` 跟踪，并在每次按键后发送。该状态只接收键码的状态转换：xkb 会计数一个修饰键被按下的次数，并保持该修饰键，直到收到同样多次的释放。发给合成器的也是这些，不多不少：客户端会把按住的键重复为多次按下——浏览器会像对待任何键一样重复按住的修饰键——而这些都不会被转发，因为 Wayland 客户端会自行重复，而 Sway 会把每次按下当作一个单独的按键，填满它容纳 32 个已按下按键的表，直到下一个按键匹配不到任何按键绑定，而它的释放永远到达不了应用。字符 keysym 指定的是客户端已经确定了大小写的字符——zDesk 从不转发 Caps Lock，而是按浏览器解析的结果发送 `A` 或 `a`——因此在每次按下之前，服务器会检查该键码在当前修饰键下会产生什么，当仅靠该键码会打出另一种大小写时，就在该键前后按下 Shift，或暂时松开按住的 Shift。为某个按键而按下的 Shift 会随该键一起抬起，除非客户端在此之后自己按下了那个 Shift 键，这样它就归客户端来松开。指定的是按键而不是可打印字符的 keysym 不受此规则约束，会以其键码在客户端按住的任何修饰键下发出：Shift+Tab 到达时是 Shift 然后 `Tab`，该键码的 Shift 层级是 `ISO_Left_Tab`，而为了让它产生 `Tab` 而松开 Shift，会打出一个普通的 Tab。客户端离开或被取代时，会松开其按键和按钮；从未完成握手的连接则不释放任何东西。指针事件以帧缓冲像素到达，并作为相对于帧缓冲范围的绝对位置注入，由虚拟指针映射到共享的输出上——每个连接一个指针，各自在自己的输出上，移动座位（seat）唯一的光标。这种绑定是随指针一起建立的，而 labwc 不会保留它：每当输出被重新布局，它都会把每个指针映射回其设备所指名的输出，而虚拟指针没有指名任何输出，于是绝对位置就会横跨整个布局——一旦有两个输出，就会偏移该输出在布局中的位置。APT 仓库构建的 wlroots 带有一个补丁，为虚拟指针赋予其输出的名称，labwc 会将它映射回该输出；其他任何 wlroots 都没有这个补丁，因此在所有 wlroots 上，每次布局变化之后都会出现的每个 wlr-output-management `done`，都会针对各自的输出重新创建每个桌面视图（desk）的指针，新的先建好，旧的再移除，并松开按住的按钮，但不松开任何按键。滚轮“按钮”变成离散的轴事件，每格一个。

RFB 只能表达一格，因此触控板上的滑动或手机上的双指滑动会一顿一顿地滚动。知道服务器是 wlshare 的客户端会改为发送一段距离：私有消息 `0xE5`，六个字节——类型、一个字节的填充，以及以输出的逻辑像素表示的 S16 水平和垂直距离，向右和向下为正——跟在指明位置的 `PointerEvent` 之后。它没有伪编码，因为服务器不需要为它保存任何状态，也没有什么要回答。逻辑像素正是轴事件所用的单位，因此距离在到达时就原样作为连续轴事件注入：这正是插在这台机器上的触控板所发送的，应用会把它当作它本身的距离来使用。

剪贴板通过 Extended Clipboard 以 UTF-8 文本共享，并且只通过这种方式：latin-1 剪切文本在两个方向上都被丢弃，未列出该扩展的客户端没有剪贴板。每个列出它的 `SetEncodings` 都会得到服务器的能力（caps）作为回答——文本、所有操作，并且不主动发送文本，这是该扩展所推荐的，因此由客户端通知变化，再由服务器请求内容。合成器宣布的选择内容（selection）会在事件循环之外读入一个管道，并保存为共享剪贴板，同时向客户端发送一个通知——或者，对于能力表明不接受通知但接受主动发送文本的客户端，直接发送文本本身，大小以其能力所指明的为限；否则，文本在客户端请求时发送，届时发送的是当时的共享剪贴板。被清空或不再是文本的选择内容，会保存为空文本，并以不含任何内容的方式通知。客户端的通知以一个请求来回答，客户端提供的文本成为共享剪贴板，并成为一个占有该选择的数据源；在该源属于我们期间，合成器回传宣布的这一选择会被忽略。无法读取的剪贴板消息会被丢弃，而不是断开连接。

## 安全

RFB 3.8，提供配置所对应的类型：设置了 `[pam]` 或 `[password]` 之一时，提供两种宽度的 RSA-AES，`RA2_256` 在前；两者都未设置时，只提供 None。经典的 VncAuth 被刻意排除：它证明的是知道一台机器的秘密，不指明任何人，把密码截断为八个字符，并且只保护登录，不保护登录之后的任何内容。没有配置登录时，会话是开放且明文的，因此按设计，监听地址应是回环地址或 VPN 地址。

RSA-AES 是 RealVNC 的类型，按 `rfbproto` 所记述、并由 TigerVNC、neatvnc 和 zDesk 网关所使用的方式实现：服务器的 RSA 密钥和一个新生成的客户端密钥以明文交换，每一方用对方的密钥封装一个随机数，两个随机数为每个方向派生一个 AES-EAX 密钥，从此以后，两个方向上的每个字节都以 `u16 len || ciphertext || tag` 帧的形式、在计数器 nonce 下传输。在这些帧内，每一方用一个哈希证明它所看到的密钥，服务器索要配置的登录方式所需的凭据——对 `[pam]` 是子类型 1，即用户名和密码；对 `[password]` 是子类型 2，即仅密码——随后是 RFB 的 SecurityResult、ClientInit 以及之后的一切。无论哪种方式，凭据在线路上都只有一种形式：带长度前缀的用户名，然后是带长度前缀的密码；回答子类型 2 的客户端发送空的用户名。`crates/wlshare/src/rfb/rsa_aes.rs` 逐字节地描述了这一交换过程。

服务器的密钥是长期使用的——一次性生成到 `rsa_key_file` 中，启动时以 RealVNC 的八字节指纹记入日志——因为它是客户端唯一可以固定（pin）的东西；zDesk 在每次连接时都会记录它看到的指纹。

检查凭据的是 `auth.rs`，它是两种方式之一。`[pam]` 把凭据交给 PAM（`pam.rs`）：在配置的服务下执行 `pam_authenticate` 和 `pam_acct_mgmt`，别无其他。在询问 PAM 之前，用户名必须是进程运行时所用的账户：wlshare 把输入注入一个用户的桌面，另一个账户的密码不能打开它。`[password]` 按配置中的 Argon2 PHC 字符串验证密码，使用该字符串所携带的参数，并且根本不指明任何账户——适用于这样的主机：其桌面用户没有可供 VNC 客户端使用的系统密码，或者没有可供使用它的 PAM 栈。该哈希在启动时解析，因此不可用的哈希是启动错误，而不会在第一个客户端到来时才意外暴露；`wlshare hash-password` 会打印一个。空密码在查看哈希之前就被拒绝。两种检查都会阻塞——PAM 栈可能会休眠，Argon2 则刻意设计得很慢——因此两者都在阻塞线程上运行。拒绝会在延迟一秒后以 SecurityResult failed 和不加修饰的原因“authentication failed”作答；实际原因记入日志。

## 刻意缺少的功能

Tight、TightPNG、Hextile、RRE、CopyRect，以及除私有编码（VP9 和图块的区域流）之外的所有有损编码：网关无论如何都会重新编码每个图块，而 ZRLE 是标准中最好的无损选择。超过该流所请求上限的 VP9 质量，无论链路有多少余量；面向任何未列出 VP9 编码的客户端的 VP9 编码。8 位和 16 位像素格式以及颜色映射表。移动客户端的指针：PointerPos 伪编码本可以承载合成器造成的指针跳转（warp），光标会话也确实会报告位置，但只在输出重绘时才报告。一个帧缓冲中包含多个输出——客户端从中选择一个，或者再连接一次，在旁边显示另一个。同时超过两个输出。控制套接字。服务器指定的格式之外的麦克风格式。用于客户端摄像头的 V4L2 摄像头设备：PipeWire 节点不需要内核模块，也不需要特权，代价是只打开 `/dev/video*` 的应用看不到它。I420 之外的摄像头格式，以及把摄像头画面缩放到应用所要求的尺寸。
